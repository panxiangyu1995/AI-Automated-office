## Executive Summary

### 产品愿景

**AI-Automated-office** 是一款**以通用 Agent 为核心的 AI ERP 平台**，旨在为企业提供一个固定平台壳、统一消息机制、动态业务渲染和多租户治理一体化的办公系统。系统不为每个部门重复实现一套 AI 内核，而是以**一个统一 Agent Runtime** 作为任务执行入口，再通过部门能力包、知识范围、权限策略和页面资源来适配不同业务场景。

**核心理念：**
- **一个通用 Agent**：平台只有一套 Agent Runtime，统一承载会话、规划、工具调用、权限校验、审计、记忆和结果写回。
- **产品形态借鉴主流 Agent 工作台范式，而非代码助手复刻**：平台复用 Cursor、Claude Code、OpenCode、OpenClaw 一类产品的 Agent、审阅、暂存改动、接受/拒绝与可扩展能力模型，但承载对象是企业业务内容而非代码文件。
- **部门是能力包，不是独立内核**：核心部门能力内置，扩展部门能力按需开通；部门差异主要体现在 Tools / Skills / MCP、知识库、模板资产、消息端点和权限边界上。
- **UI 采用固定 + 混合 + 动态三层承载**：固定 UI 负责治理与配置，混合 UI 承载业务壳层，动态 UI 承载表单、卡片、模板、报表和实时渲染内容。
- **跨部门协作通过统一消息和数据中台完成**：部门间内容可由 Agent 在权限范围内获取、总结、发起协作和提交建议，而不是依赖孤立模块之间的硬编码串联。

**目标用户：** B2B企业客户，覆盖全员使用场景——从一线员工到管理层，不同部门获得差异化的AI能力支持。

**核心问题：**
- 钉钉/飞书等工具提供的是"工具集合"，各部门独立使用，数据孤岛
- 企业需要的是"ERP整合"，跨部门数据联动，全流程AI赋能
- 传统ERP系统僵化，企业需适应软件逻辑，定制成本高

**解决路径：** 统一 Agent 平台 + 部门能力包 + 动态 UI，实现：
- 核心部门能力内置，覆盖企业基本职能
- 扩展能力按需开通，灵活适配企业组织架构
- Tools / Skills / MCP / 模板 / 知识库作为统一能力供给层
- 固定 UI、实时渲染 UI 与混合 UI 共同承载 Agent 结果
- 跨部门数据联动、统一消息机制与多租户治理形成平台基础设施

### 差异化核心

| 维度 | 钉钉/飞书 | 本产品 |
|-----|----------|-------|
| **产品本质** | 工具集合 | **AI赋能ERP** |
| **部门关系** | 各部门独立使用工具 | **跨部门数据联动** |
| **AI定位** | 局部功能增强 | **全流程AI赋能** |
| **数据流** | 各应用数据孤岛 | **统一数据中台** |
| **权限模型** | 应用级权限 | **部门级权限模型** |
| **定制化** | 有限配置 | **部门职能按需扩展** |

**核心洞察：** 
- 钉钉/飞书给企业一堆工具，企业自己拼凑流程
- 我们给企业一个以通用 Agent 为核心的 AI ERP，跨部门数据自动联动，部门差异通过能力包表达
- 定制化方式：看企业有哪些部门，就开通对应能力包、知识范围和页面资源即可

**一句话价值主张：** *"我们不是卖一堆工具，也不是给每个部门做一套独立 AI，而是为企业提供一个面向业务对象、借鉴主流 Agent 产品范式的通用 Agent 工作平台：按部门开通能力包，数据自动联动，结果以可审阅、可接受、可拒绝的方式进入真实业务界面。"*

### 产品定位澄清（并入铁律，不新增FR）

> 本产品可以借鉴 Cursor、Claude Code、OpenCode、OpenClaw 一类 Agent 产品的**运行逻辑、交互模型和能力扩展方式**，但不能把产品错误定义为“企业版代码助手”。

- **借鉴对象是通用 Agent 范式**：主 Agent / Sub-Agent、对话驱动执行、Tools / Skills / MCP、候选改动审阅、可恢复执行、规则与记忆体系、可扩展能力供给。
- **不是复刻 coding 场景**：产品不以代码文件、终端命令、仓库操作为核心对象；这些模式仅作为交互和运行时参考。
- **真正服务对象是企业部门职员**：销售、财务、审批、人事、仓储、售后、招投标、管理层等真实业务角色，而不是开发者。
- **真正承载对象是企业业务内容**：审批单、表单、客户档案、合同、工单、台账、报表、看板、流程图、知识条目、消息卡片等，而不是源代码。
- **真正的产品差异化来自企业定制层**：统一 Agent Runtime 之上叠加租户、部门、权限、云端数据、知识库、消息协作、能力包和审计治理，满足单个企业的真实业务场景。
- **定制化原则**：只有“通用 Agent Runtime + 企业定制上下文 + 企业定制能力包 + 企业定制治理规则”的组合，才能满足不同企业部门职员的特定需求。

### VSCode工作台体验借鉴（并入铁律，不新增FR）

> 本产品可以参考 VSCode 开源项目中已经被验证的复杂桌面工作台体验模式，但只能迁移“工作台方法论”，不能把产品重心带偏到 IDE 专属场景。

- **借鉴的是复杂工作台，不是 IDE 功能集**：重点吸收稳定壳层、命令式导航、状态反馈分层、工作场景恢复和受控扩展贡献点。
- **命令即入口**：Command Center / Quick Ask / Quick Open 应成为长尾功能和跨模块资产的统一入口，降低菜单层级依赖。
- **状态必须可见且可恢复**：用户应随时知道当前在哪个部门、在处理什么任务、草稿是否已保存、哪里有问题、能否恢复。
- **生态增长必须守序**：Skills / MCP / 插件 / 模板 / 自定义编辑器只能通过受控贡献点进入固定工作台，不能破坏 TopBar、ActivityBar、Workbench 的稳定空间语言。
- **不直接照搬 IDE 专属模块**：调试器、Git、终端、Remote SSH、Notebook 等能力不作为本产品核心范围，除非未来某个业务场景明确需要。

### 典型业务闭环澄清（并入铁律，不新增FR）

> 本产品的核心价值不只是在聊天中给建议，而是帮助企业员工围绕真实业务对象完成“获取资料 → 生成内容 → 审阅应用 → 资产沉淀 → 后续复用”的完整闭环。

#### 样板场景：标书制作

以招投标专员为例，平台应支持以下业务闭环：

1. 用户提出新的标书制作任务或上传新的投标要求。
2. 主 Agent 在当前用户权限范围内读取云端历史标书、资质材料、案例库、知识库和模板资产。
3. 如用户本地电脑存在旧标书或招标文件，Agent 可协助导入并上传到可控的云端或知识空间。
4. Agent 基于历史资料、企业知识、模板和 Skills 生成候选标书内容。
5. 候选内容先在聊天区解释和预览，再同步投射到编辑器页或对应业务页面中供用户审阅。
6. 用户通过变更清单执行逐条或整体接受/拒绝，只有接受后的内容才正式保存。
7. 高质量的标书结构、章节规则、常用措辞、填写逻辑可被进一步抽象为可复用 Skill、模板或知识条目。
8. 后续相似标书任务可直接复用这些沉淀资产，而不是从零开始。

#### 通用闭环模式

上述闭环并不限于标书制作，也适用于合同起草、审批单生成、客户方案编制、财务台账整理、售后工单总结等场景。

平台应统一支持以下模式：

- **历史资产读取**：访问云端历史业务内容、知识库、模板库和权限范围内的数据接口。
- **本地资料摄入**：协助用户导入本地文件并纳入可治理的企业知识或工作区资源。
- **内容生成与编辑**：Agent 围绕业务对象生成候选内容，而不是只输出抽象建议。
- **页面审阅与确认**：候选改动进入页面审阅流，接受后生效，拒绝后撤销。
- **经验沉淀**：把高质量过程沉淀为 Skill、模板、知识条目或规则。
- **后续复用**：后续相似任务由通用 Agent 结合沉淀资产快速完成。

## Product Scope

### 产品架构：统一 Agent 平台 + 部门能力包

本产品采用**统一 Agent 平台 + 部门能力包**架构。部门仍然是业务组织、权限分配和数据协同的核心边界，但 AI 内核只有一套；各部门通过能力包向平台提供业务工具、技能编排、MCP 连接、模板资产、知识绑定和页面资源。

**架构理念：**
- **统一 Agent Runtime**：平台共用一套会话、规划、执行、权限、记忆、消息和审计机制
- **核心部门能力包（内置）**：所有企业必备的基础能力，随平台交付，不可卸载
- **扩展部门能力包（可安装）**：按企业实际组织架构按需开通
- **部门权限模型**：用户权限 = 基础权限（人事权限） + 部门权限 + 审批发起权限
- **结果写回业务界面**：Agent 输出必须进入工作台、详情页、审批页、模板区或编辑器宿主，而不是只停留在对话中

### MVP - 最小可行产品

**平台核心：**
- 桌面端UI（类VSCode布局）
- 通用 Agent Runtime（工具调用、MCP接入、会话管理、记忆管理、定时任务、心跳机制、规划执行）
- 每用户主 Agent + 可配置 Sub-Agent 体系
- 统一消息机制（人 / Agent / 系统 / 群组参与者模型）
- 固定 UI + 混合 UI + 动态 UI 宿主体系
- AI 暂存写回与审阅机制（聊天预览 + 页面候选改动 + 接受/拒绝清单）
- 部门能力包系统（核心能力内置、扩展能力可安装）
- 开放能力供给层（内置能力 + 用户可配置 Skills / MCP / 插件 / 私有资源源）
- 部门权限系统（部门级权限模型）
- 公告和消息通知系统（系统公告、消息推送、未读提醒、免打扰模式）
- 多租户架构
- 部门市场（扩展能力浏览安装）

**核心部门能力包（6个，内置不可卸载）：**

| 部门 | 核心职能 | AI赋能场景 | 依赖关系 |
|-----|---------|-----------|---------|
| **人事部** | 员工管理、部门架构、考勤管理、入职离职 | 智能入职引导、考勤异常预警 | 无（基础层） |
| **审批中心** | 自由流程创建、AI生成流程、审批/驳回、历史记录 | 对话生成审批流程、智能路由、动态数据表生成 | 人事部 |
| **销售部** | 报价单AI生成、合同AI生成、订单处理、销售自动化、客户管理 | AI生成报价单/合同、客户跟进提醒、第三方平台接入 | 人事部 + 仓储部 |
| **财务部** | 发票/合同OCR、台账生成、应收应付、与销售联动（获取报价单/合同） | 智能对账、发票自动识别、财务数据分析 | 人事部 + 销售部 |
| **仓储部** | 入库、出库、库存管理、物流仓储、库存预警 | 库存预警、智能补货建议、物流追踪 | 人事部 |
| **管理层（老板端）** | 数据看板、经营分析、预警机制、跨部门数据汇总 | AI经营洞察、风险预警、决策支持 | 访问所有部门数据接口 |

**扩展部门能力包（3个，可安装）：**

|-----|---------|-----------|---------|

**知识库RAG** 作为平台能力，可被多个部门调用（售后、招投标等），并支持 Agent 在权限和审核约束下提交沉淀内容。

### 产品定位补充（并入铁律，不新增FR）

> 本产品的目标形态不是“ERP 里附带一个聊天框”，也不是“给每个部门单独做一个 AI 助手”，而是一个**企业化、部门化、非 coding 场景的通用 Agent 工作平台**。

- **Agent 主体模型**：每个用户默认拥有 1 个主 Agent，并可创建多个面向特定任务的 Sub-Agent。
- **部门定位**：部门是业务上下文边界、权限边界、能力边界和数据边界，不是独立 Agent 实体。
- **业务对象优先**：平台主要承载文档、表单、审批单、详情页主体、台账、报表、看板、流程图、消息卡片等企业业务对象，而非代码文件对象。
- **数据位置**：企业关键业务数据多数存储于云端，用户与 Agent 在租户和权限约束下访问对应内容。
- **企业治理**：管理员负责配置权限、知识库、工作流规则、资源来源白名单和敏感数据限制；普通用户只能在被允许的边界内自定义能力。

### 旅程 1：财务人员 - 小李

**角色背景：** 小李是一家中型企业的财务专员，负责处理发票、合同、报销单，公司有3个不同的抬头，每个月要处理上千张票据。

#### 开场：痛点初现

周一早上8:30，小李的办公桌上堆满了上周积累的发票和报销单。她叹了口气，打开Excel，准备开始手动录入。这已经是她连续第三周加班了——每到月底，她都要花整整一周时间整理票据、核对金额、生成台账，然后还要应付老板随时可能问的"这个月我们付了多少款？应收还有多少？"

她最怕的是：**录错一个数字，整个台账都要重查。**

#### 上升行动：遇见改变

公司引入了AI-Automated-office。小李第一次打开软件时，有些怀疑——"又是一个工具？"

她按照引导，安装了**财务OCR插件**。然后尝试把一叠发票放在扫描仪前，点击"批量识别"。

**30分钟后**——她惊呆了。

- 发票信息自动识别，准确率98%
- 自动匹配公司抬头
- 自动分类（增值税发票、普通发票、报销单）
- 一键生成台账，导出Excel

她原本要花**2天**的工作，现在**半小时**搞定了。

#### 高潮：价值时刻

月底，老板突然问："小李，这个月应付账款是多少？"

以前，小李会说："张总，我查一下，下午给您。"

现在，她打开**数据看板**，实时数据一目了然："张总，本月应付账款186万，其中已付120万，待付66万，主要供应商是..."

老板点点头："很好，这个系统不错。"

小李心里想：**"我终于可以准时下班了。"**

#### 结局：新现实

- 工作时间：从每周加班3天 → 准时下班
- 错误率：从每月5-10处 → 几乎为0
- 老板满意度：从"怎么又错了" → "效率很高"

## Innovation & Novel Patterns

### 创新类型：架构创新 + AI深度融合

本产品不是"技术突破型创新"，而是**架构创新 + AI深度融合**：

| 创新维度 | 说明 |
|---------|------|
| **统一 Agent Runtime** | 用一套 Agent 核心覆盖多业务场景，避免每部门重复建设 AI 内核 |
| **部门能力包建模** | 从“功能堆砌”转向“能力包开通”，符合企业组织架构认知 |
| **跨部门数据联动** | 打破数据孤岛，统一数据中台 |
| **部门权限模型** | 权限 = 基础权限 + 部门权限 + 审批权限 |
| **动态 UI 承载** | Agent 结果进入固定 UI、混合 UI 和动态 UI，而不是停留在聊天框 |
| **AI深度赋能** | 通用 Agent 结合部门上下文、知识与工具，而非局部增强 |
| **AI生成流程** | 审批流程可通过对话生成，自动创建数据表 |

### 核心护城河

**护城河不是单点技术，而是"统一 Agent 平台 + 部门整合 + 服务深度"：**

| 护城河维度 | 钉钉/飞书 | 本产品 |
|-----------|----------|---------|
| 产品本质 | 工具集合 | **AI赋能ERP** |
| 部门关系 | 各部门独立使用 | **跨部门数据联动** |
| AI定位 | 局部功能增强 | **全流程AI赋能** |
| 数据流 | 数据孤岛 | **统一数据中台** |
| 权限模型 | 应用级权限 | **部门级权限模型** |
| 定制化 | 有限配置 | **部门按需开通** |
| 服务深度 | 标准化SaaS | **软件+垂直服务** |

**核心差异化：**
- 钉钉/飞书：给企业一堆工具，企业自己拼凑流程
- 本产品：给企业一个通用 Agent 驱动的 AI ERP，看企业有哪些部门，就开通对应能力包、权限边界和页面承载资源

### 定制化优势

**按能力包与组织边界定制，而非按零散功能定制：**
- 传统ERP：按功能模块收费，企业买一堆用不上的功能
- 本产品：**看企业有哪些部门，开通对应能力包即可**

**定制化流程：**
1. 了解企业组织架构（有哪些部门）
2. 开通对应的核心部门能力包
3. 按需安装扩展部门能力包
4. AI辅助配置审批流程
5. 跨部门数据自动联动

### 验证方法

| 验证点 | 方法 |
|-------|------|
| 统一 Agent + 能力包模式是否接受 | MVP阶段验证企业对“通用 Agent + 部门能力包”认知是否自然 |
| 跨部门联动价值 | 验证销售→财务→仓储的数据联动是否产生效率提升 |
| AI生成流程可用性 | 验证用户是否愿意通过对话创建审批流程 |
| 客户粘性 | 客户续费率、部门扩展率、服务深度 |

### 风险与应对

| 风险 | 应对策略 |
|-----|---------|
| **大厂复制** | 通用 Agent 与部门能力包的深度整合需要强业务抽象与落地服务能力，大厂难以快速跟进 |
| **技术同质化** | 用服务深度和部门联动绑定客户 |
| **客户流失** | 深度服务绑定，跨部门数据联动形成切换成本 |
| **服务规模化难** | 能力包化和统一 Runtime 降低边际成本，标准服务+定制配置 |

## 部门模块（插件）系统设计规范

### 核心定义

**部门模块（能力包/插件）** = **领域能力定义** + **页面承载资源** + **Agent调用接口（Tools/Skills/MCP）** + **知识与模板绑定**

> 每个部门模块首先是一个面向统一 Agent Runtime 的能力包，而不是独立的 Agent 内核。它既向平台暴露标准化的 Tools / Skills / MCP / 模板 / 知识库绑定能力，也向固定 UI、混合 UI、动态 UI 提供可承载的业务资源。用户既可以直接操作界面完成工作，也可以通过同一平台 Agent 驱动执行、总结、协作和回写。

### 架构设计

```text
平台固定壳层 / 页面宿主 / 统一消息
  -> 通用 Agent Runtime
  -> 部门模块标准接口
     - Tools
     - Skills
     - MCP
     - Templates / Dynamic UI Schema
     - Knowledge / Data Binding
  -> 部门能力包
     - 人事部
     - 销售部
     - 财务部
     - 仓储部
     - ...
  -> 结果写回
     - 工作台
     - 审批页
     - 详情页
     - 编辑器 / 模板区
```

### 接口类型定义

| 接口类型 | 用途 | 示例 | 特点 |
|---------|------|------|------|
| **Tools** | 单一功能调用 | 创建订单、查询库存、添加员工 | 原子操作，返回结构化结果 |
| **Skills** | 复杂技能封装 | AI生成报价单、OCR识别合同、生成审批流程 | 多步骤组合，含AI推理 |
| **MCP** | 外部服务接入 | 第三方API、数据库连接、邮件服务 | 外部系统对接 |

### 开放能力供给原则（并入铁律，不新增FR）

> 平台不能只依赖内置能力。产品必须像主流 AI coding 工具一样，允许用户在权限范围内扩展 Agent 能力，但所有扩展都必须经过统一治理链路。

- **默认内置 + 用户扩展并存**：系统提供安全默认能力，同时允许用户或管理员引入自定义 Skills、MCP 服务、插件和私有资源。
- **作用域分层配置**：能力配置至少支持租户级、部门级、用户级、项目/工作区级、Sub-Agent 级作用域。
- **多来源接入**：能力来源支持内置资源、本地导入、企业私有市场、外部兼容市场。
- **运行时按需装配**：Agent 在执行时从“已安装能力 + 当前作用域启用能力 + 权限放行能力”中选择候选集，而不是默认暴露全部能力。
- **治理优先**：任何外部 Skill / MCP / 插件都必须经过权限声明、签名/来源校验、Approve 策略、审计记录、版本控制、限额和隔离执行。
- **UI 贡献点受控**：扩展能力只能通过 Sidebar 视图、Bottom Panel 标签、StatusBar 条目、Command Palette 命令、上下文菜单、编辑器类型、模板资产等受控入口进入，不得改写 TopBar、ActivityBar、Workbench 核心壳层。
- **内置能力不是上限**：平台内置功能只提供默认起点，不构成产品能力边界。

### 平台内置 Skills 基线（并入铁律，不新增FR）

> 平台不能只有 Skill 兼容、导入和安装能力，还必须交付一组可直接使用的内置 Skills 作为默认起点。

- **内置 Skills 是默认基线，不是能力上限**：平台预置可直接复用的基础 Skills，同时允许部门能力包和用户扩展继续叠加。
- **数量要少而精**：平台级内置 Skills 在 MVP 阶段应控制在 6-10 个，优先覆盖高频、跨部门、可复用场景。
- **Skill 不得绕过治理**：内置 Skill 仍必须通过统一 Tool Registry、权限检查、Approve 策略、审计记录和上下文预算控制执行。
- **Skill 只编排，不私藏能力**：Skill 应尽量复用现有原子工具、平台工具和部门工具，不应通过隐藏私有能力形成新的能力黑箱。
- **三层来源并存**：平台级内置 Skills、部门能力包内置 Skills、用户/管理员安装 Skills 同时存在，但统一纳入同一治理链路。

**建议的 P0 平台级内置 Skills 基线：**

| Skill ID | 作用 | 典型用途 |
|---------|------|---------|
| `resource-intake` | 导入并整理本地或云端资料 | 收集历史文件、招标要求、客户材料 |
| `document-draft` | 按要求起草业务文档 | 标书、合同、方案、报告初稿 |
| `structure-extract` | 从现有文档抽取结构和规则 | 抽取章节、字段、填写约束 |
| `template-abstract` | 从实例沉淀模板 | 将优秀文档抽象成通用模板 |
| `knowledge-summarize-submit` | 总结结果并提交知识草稿 | 形成待审核知识条目 |
| `cross-department-brief` | 生成跨部门协作摘要 | 给其他部门或其他 Agent 发送上下文摘要 |
| `review-change-package` | 把生成结果整理成可审阅变更包 | 对接页面暂存写回和变更清单 |
| `meeting-followup-summary` | 沉淀会议或沟通后的行动项 | 输出待办、纪要、后续任务 |

### Tool Calling 2.0 工具分层基线（并入铁律，不新增FR）

> Tool Calling 2.0 的核心不是“工具越多越强”，而是**工具尽量少、保持原子化、覆盖面足够广、避免让 Agent 在大量相似工具之间失去选择能力**。

- **少而强**：优先维护少量高能力原子工具，而不是为每个场景堆积专用工具。
- **原子化**：每个工具只做一类清晰动作，组合复杂流程应交给 Skill 或 Agent 规划，而不是继续拆出大量场景工具。
- **参数化**：业务领域工具优先通过 `entity / action / filters / data` 等参数扩展能力，而不是继续增加工具数量。
- **强能力保留**：平台应保留主流 Agent 产品常见的强操作工具，以保证 Agent 的通用执行能力。
- **审阅动作不工具化**：接受/拒绝/回滚/发布等动作属于人类审阅流程，不属于 AI 可调用工具。

**Layer 1: 通用高能力原子工具（P0，AI 可调用）**

| 工具 | 用途 |
|------|------|
| `file_read` | 读取文件内容 |
| `file_write` | 写入文件 |
| `file_edit` | 对文件做局部编辑 |
| `dir_list` | 查看目录与资源结构 |
| `pattern_search` | 搜索文本、规则、关键词 |
| `sandbox_execute` | 在受控沙箱中执行命令或脚本 |
| `web_search` | 搜索外部公开信息 |
| `web_fetch` | 抓取网页内容 |
| `http_request` | 访问标准 HTTP 接口 |
| `browser_interact` | 在受控浏览器上下文中进行页面交互 |
| `sys_time` | 获取系统时间与时区信息 |
| `document_parse` | 解析文档内容与结构 |
| `document_convert` | 在支持格式间做文档转换 |

**Layer 2: 企业平台增强工具（P0/P1，AI 可调用）**

| 工具 | 用途 |
|------|------|
| `resource_query` | 查询云端或工作区资源 |
| `resource_upload` | 上传本地或外部资料到受控资源空间 |
| `knowledge_query` | 查询绑定知识库 |
| `knowledge_submit_draft` | 提交知识草稿，走后续审核或发布流程 |
| `message_query` | 查询用户与 Agent 消息上下文 |
| `message_send` | 向用户、群组或 Agent 发送消息 |
| `workspace_stage_change` | 将候选改动暂存写回到页面或编辑器 |
| `agent_delegate` | 委派给其他 Sub-Agent 或协作 Agent |

**Layer 3: 部门能力包工具（按部门装配，AI 可调用）**

| 工具类型 | 命名格式 | 说明 |
|---------|---------|------|
| 查询 | `{dept}_query` | 通用数据查询 |
| 聚合 | `{dept}_aggregate` | 统计与汇总 |
| 变更 | `{dept}_mutate` | 创建、更新、删除 |
| 业务动作 | `{dept}_action` | 审批、发货、入库等特殊业务逻辑 |
| 导出 | `{dept}_export` | 导出报表、文件、结果包 |

**Layer 4: 受限工具（非普通用户默认基线）**

- `db_query` 一类低层数据库工具不应进入普通用户默认工具集，只能作为管理员、受控调试或特定私有能力场景下的受限能力。
- 任何高风险写入、删除、外发或敏感数据处理工具，仍需接受权限检查、Approve 策略和审计链路约束。

### 审阅动作与工具边界（并入铁律，不新增FR）

> AI 可以生成并暂存候选改动，但不能替代用户做最终接受或拒绝决定。

- **AI 可执行**：读取上下文、生成候选内容、调用 `workspace_stage_change` 暂存写回页面或编辑器。
- **用户专属动作**：单条接受、单条拒绝、全部接受、全部拒绝、展开/收起变更清单、checkpoint 回滚、最终发布。
- **边界要求**：`accept / reject / rollback / publish` 不进入 Tool Registry，不作为 AI 可调用工具暴露给 Skill、MCP 或插件。
- **状态要求**：只有用户接受后的改动才正式保存；拒绝后的改动不应保留有效变更。

### 工具调用可见性设计

#### 设计原则

- **透明性**：所有用户都能看到AI调用了哪些工具、怎么调用的

### 错误处理与用户干预

#### 错误处理流程

```
工具调用失败
     │
     ├─► 自动重试 (最多3次)
     │        │
     │        ├─► 成功 → 继续执行
     │        │
     │        └─► 失败 → 提示用户
     │                    │
     │                    ├─► [重试] 手动重试
     │                    ├─► [手动输入] 用户直接输入结果
     │                    ├─► [跳过] 跳过此步骤
     │                    └─► [切换方案] 使用备用工具
     │
     └─► 降级处理 → 通知用户并记录
```

#### 用户干预机制

| 场景 | 用户操作 | 说明 |
|-----|---------|------|
| **工具调用失败** | 重试 / 手动输入 / 跳过 / 切换方案 | 多种选择 |
| **AI结果需确认** | 预览 → 修改 → 确认提交 | 结果可控 |
| **结果不准确** | 编辑纠偏 / 重新生成 | 纠偏机制 |
| **工具不可用** | 手动设置参数 | 降级操作 |
| **批量操作中断** | 从断点继续 / 全部重试 | 支持断点续传 |

#### AI纠偏反馈学习机制

> **核心理念：** 用户手动修改AI结果时，通过对话告诉AI"为什么改"，AI将纠正记录到"错题集"，实现越用越智能。

**设计原理：**

当用户发现AI输出有误并手动修改时，这不仅是一次纠偏，更是AI学习的机会。通过VSCode风格的右键菜单，用户可以选择修改内容并与AI对话，解释修改原因。AI将这些反馈存入"错题集"，在后续类似场景中避免重复犯错。

## ClawHub生态兼容性设计

### 背景与目标

本项目灵感来源于 OpenClaw，旨在为企业提供 AI 赋能的 ERP 系统。在实际部署中发现，OpenClaw 更适合技术用户，而企业需要面向全员（包括非技术人员）的解决方案。

**核心诉求：**
- 保持企业级 ERP 系统的定位
- 兼容 ClawHub 丰富的生态资源
- 降低企业用户使用门槛
- 提供企业级安全保障

**设计目标：**

| 目标 | 说明 |
|------|------|
| **生态兼容** | 支持 ClawHub 的 Skills、Plugins、SOULs 等资源 |
| **安全增强** | 针对企业场景增强安全审计和权限控制 |
| **平滑迁移** | 支持现有 ClawHub 资源的直接使用或适配转换 |
| **扩展能力** | 支持企业自建私有市场和管理 |
| **用户友好** | 提供图形化界面，降低非技术用户使用门槛 |

### Skill适配层设计

Skill 是 ClawHub 生态中最核心的资源类型，采用 SKILL.md 格式定义 Agent 可执行的技能。

**Skill 解析流程：**
1. 解析 YAML frontmatter 获取元数据
2. 提取 Description、Triggers、Tools、Examples 等章节
3. 转换为内部工具格式
4. 注册到统一工具层

**Skill 工具映射：**
- Skill 中的 Tools → 内部工具 (InternalTool)
- Skill 中的 Triggers → 触发器规则 (InternalTrigger)
- Skill 执行代理 → SkillExecutor

### Plugin适配层设计

OpenClaw 插件是 TypeScript 模块，需要适配转换为部门模块组件。

**Plugin 组件映射：**

| OpenClaw Plugin Type | AI-Automated-office Component |
|---------------------|------------------------------|
| Agent Tool | 部门工具 (Department Tool) |
| Channel Plugin | 消息通道适配器 |
| Provider Plugin | LLM提供商适配器 |
| CLI Command | 桌面端命令/菜单项 |
| Background Service | 后台任务服务 |
| Hook | 事件处理器 |
| HTTP Route | API端点 |

**安全隔离：**
- Plugin 在沙箱环境中执行
- 文件系统访问需白名单授权
- 网络访问需白名单授权
- 执行超时和内存限制

### SOUL适配层设计

SOUL.md 用于定义 Agent 的人设（Persona），可直接作为 Agent 人设模板导入。

**SOUL 内容映射：**
- Identity → 系统提示词身份部分
- Personality → 系统提示词性格部分
- Expertise → 系统提示词专业领域
- Communication Style → 系统提示词沟通风格
- Boundaries → 系统提示词边界约束

### 安全机制设计

**资源安全验证流程：**
1. **来源验证** - 检查来源是否可信（ClawHub官方/私有市场/本地）
2. **签名验证** - 验证资源签名（如果有）
3. **静态分析** - 检测敏感API调用、可疑模式
4. **沙箱测试** - 在隔离环境中运行测试
5. **审计记录** - 记录资源加载和执行日志

**企业级安全增强：**
- 资源加载前强制安全扫描
- 敏感操作需管理员审批
- 执行日志完整记录
- 支持资源黑白名单

### 市场集成设计

**三层市场架构：**

| 层级 | 说明 | 特点 |
|-----|------|------|
| **本地资源库** | 本地导入的Skill/Plugin/SOUL | 完全离线可用 |
| **私有市场** | 企业自建市场 | 支持ClawHub格式，租户隔离 |
| **ClawHub市场** | ClawHub官方市场 | 外部资源市场接入 |

**资源安装流程：**
1. 用户从市场浏览/搜索资源
2. 系统进行安全验证
3. 适配层转换资源格式
4. 安装到本地资源库
5. 注册到统一工具层

## Project Scoping & Phased Development

#### Heartbeat/Cron 实施基线（并入铁律，不新增FR）

> 本节用于并入 `_bmad-output/soul/03-heartbeat-mechanism.md` 与 `_bmad-output/soul/04-cron-scheduling-mechanism.md` 的治理模式，作为 FR1127-FR1145 的实施约束。

- Heartbeat 执行前必须通过预检查（用户状态、活跃时段、上下文预算、资源可用性）；不满足条件时跳过并记录原因。
- 心跳在无待办时返回 `HEARTBEAT_OK` 并静默处理；默认不打扰用户，通知策略遵循免打扰与角色权限。
- Cron 任务采用隔离执行上下文，支持超时、重试与退避；失败路径必须可观测并可审计。
- Heartbeat 与 Cron 的自动执行不得绕过敏感操作确认策略，涉及高风险动作必须走人工确认或审批流。

#### Agent角色模型与审阅式写回（并入铁律，不新增FR）

> 本节用于明确产品真正的交互目标，避免后续实现回退到“纯聊天建议”或“直接无审阅写入”两种错误模式。

- **主 Agent 模型**：每个用户默认拥有一个主 Agent，承担对话、调度、协作与结果汇总职责。
- **Sub-Agent 模型**：Sub-Agent 是主 Agent 的任务分工单元，用于处理特定领域任务，不改变“每用户一个主 Agent”的产品主入口。
- **部门边界模型**：部门不是 Agent，而是主 Agent / Sub-Agent 组装上下文、能力和权限时的边界条件。
- **交互入口模型**：AI 的解释、计划、局部预览先出现在聊天区域。
- **页面写回模型**：AI 可以把候选改动直接投射到编辑器页、动态表单、详情页主体、审批内容区或工作台内容区。
- **暂存改动原则**：页面中的 AI 生成内容默认属于“候选改动”，在用户确认前不算最终生效数据。
- **审阅清单原则**：聊天区上方提供可展开/收起的变更清单，展示本轮候选改动。
- **确认机制**：用户可对每条改动执行“接受/拒绝”，也可执行“全部接受/全部拒绝”。
- **拒绝语义**：拒绝后不应留下该候选改动对目标页面或目标资源的有效变更。
- **接受语义**：接受后对应改动正式写入并保存到目标内容。

## 记忆层功能需求

> **架构说明：** 记忆层采用三层架构设计，分别服务于不同范围的数据存储和检索需求：
> - **L1 个人记忆层**：用户级别，仅本人可访问
> - **L2 企业知识库层**：租户级别，全员可访问
> - **L3 图记忆层**：租户级别，支持实体关系和知识推理

### 三层记忆架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                       记忆层分层架构                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │              L3: 图记忆层 (Graph Memory)                      │   │
│  │              实体关系图谱、知识推理                            │   │
│  │              范围：租户级别（Post-MVP）                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                              ▲                                      │
│                              │ 实体关联                              │
│  ┌───────────────────────────┴─────────────────────────────────┐   │
│  │              L2: 企业知识库层 (RAG)                           │   │
│  │              高质量知识存储、混合检索                          │   │
│  │              范围：租户级别，全员可访问                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                              ▲                                      │
│                              │ 知识引用                              │
│  ┌───────────────────────────┴─────────────────────────────────┐   │
│  │              L1: 个人记忆层 (Personal Memory)                 │   │
│  │              会话记忆、用户偏好、错题集                        │   │
│  │              范围：用户级别，仅本人可访问                      │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 层级职责对比

| **L1** | 个人记忆层 | 用户 | 仅本人 | 会话历史、偏好、错题集 | P0 |

#### 记忆融合实施基线（对齐草案，不新增FR）

- MVP 生命周期采集采用 Hook 无感机制：`SessionStart`、`UserPromptSubmit`、`PostToolUse`、`Stop`、`SessionEnd`。
- 向量实现允许多实现映射：MVP 可采用 `sqlite-vec` 作为本地嵌入式实现，云端独立模式可映射到 Qdrant 等实现。
- 认知状态重建能力（如 `tunnel_state`）作为记忆层高级能力纳入实施范围，需满足审计与权限要求。

## LLM提供商与MCP配置管理

> **设计背景：** 作为AI Agent应用，用户需要能够灵活配置和管理LLM提供商、MCP服务和工具。这是Agent应用的核心能力配置层，直接影响Agent的可用性和安全性。

### 能力供给开放模型（并入铁律，不新增FR）

平台在该层必须明确支持“**内置能力 + 用户自定义能力**”的双轨模式，而不是只允许使用平台预装功能。

- **可配置对象**：LLM 提供商、MCP 服务、Skills、Plugins、SOUL 模板、提示词模板、规则集。
- **安装来源**：内置资源、本地文件导入、企业私有市场、外部兼容市场。
- **配置主体**：租户管理员、部门管理员、普通用户、开发者，各自受角色权限限制。
- **配置作用域**：全局默认、租户默认、部门默认、个人默认、项目/工作区覆盖、Sub-Agent 覆盖。
- **最终生效规则**：内置默认值 < 租户/部门策略 < 用户启用状态 < 会话/项目/Sub-Agent 覆盖，同时仍受权限、审批和审计链路约束。
- **生效解释可见性**：任何配置界面都应显示当前值来自哪一层作用域、被哪一层覆盖，以及为何当前生效。
- **企业边界要求**：普通用户可以自定义，但不能绕过管理员设定的黑名单、风险策略、数据访问范围和资源来源白名单。

### MCP工具Approve策略需求（FR825系列）

> **设计理念：** MCP工具的执行需要用户控制。不同的工具有不同的风险级别，用户需要能够为每个工具设置合适的approve策略。

**三种Approve策略：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **⚡ 自动** | 工具调用时自动执行，无需用户确认 | 读取类操作、查询类操作 |
| **✋ 需确认** | 工具调用前弹出确认卡片，用户确认后执行 | 写入操作、发送消息 |
| **🚫 禁止** | 工具被禁用，Agent无法调用 | 高风险操作、敏感数据操作 |

### Sub-Agent配置管理（FR890系列）

> **设计背景：** 用户可以创建多个专业化的子代理（Sub-Agent），每个子代理有独立的角色提示词、工具权限和调用描述。主Agent可以根据任务类型自动选择合适的子代理来执行任务。

#### 核心概念

**Sub-Agent定义：** 一个独立配置的Agent实例，具有：
- **角色提示词**：定义该子代理的专业能力和行为方式
- **调用描述**：告诉主Agent该子代理能做什么、何时调用
- **工具权限**：该子代理可以使用的MCP工具、Skills
- **知识库范围**：该子代理可以访问的知识库
- **调用触发条件**：主Agent何时应该调用该子代理

**应用场景示例：**
| 子代理名称 | 角色定位 | 工具权限 | 触发条件 |
|-----------|---------|---------|---------|
| 财务助手 | 专业财务处理 | 财务MCP、OCR、台账生成 | 涉及发票、财务、报表 |
| 销售助手 | 销售业务处理 | 销售MCP、客户管理、报价生成 | 涉及客户、报价、订单 |
| 通用助手 | 日常问答 | 通用MCP、知识库检索 | 通用问答、信息查询 |
| 技术助手 | 技术问题处理 | 代码MCP、文档检索 | 涉及代码、技术问题 |

## Phase 2 执行主线补充说明

本节用于明确 `Epic 41 / 39 / 40 / 42` 完成后的正式研发主线，作为后续自动化执行和 OpenSpec 拆分的依据。

### 主线目标

Phase 2 的目标不是继续堆叠固定业务页面，也不是为单个部门先做专用 Agent，而是构建一个可覆盖所有业务功能的通用 Agent 平台，并让该平台通过动态 UI 能力进入真实业务场景。

### Phase 2 前置平台能力

在进入通用 Agent Runtime 大规模建设前，以下能力必须完成并进入正式交付范围：

1. `Epic 41` 页面容器与渲染宿主
2. `Epic 39` 内置编辑器与文档编辑
3. `Epic 40` 编辑器系统与动态模板渲染
4. `Epic 42` 动态表单与动态详情渲染

### 执行约束

1. 后续自动化执行应优先读取上述 Epic 及其 OpenSpec changes，不应绕过这些基础设施直接进入大规模部门页面固化开发。
2. 后续 Agent 建设应采用“统一 Agent Runtime + 多部门工具/上下文适配”的模式，而不是“每个部门独立实现一套 Agent”。
3. 通用 Agent 的结果必须能够进入工作台内容区、审批单内容区、详情页主体区、模板区和编辑器区，而不是只停留在对话消息中。
4. 若页面宿主、模板运行时、动态表单/详情页协议未完成，则 Phase 2 自动化执行不得直接推进跨部门业务页面全面开发。

### 推荐 Phase 2 顺序

```text
Epic 41
  -> Epic 39 / Epic 40
  -> Epic 42
  -> 通用 Agent Runtime
  -> Tool Registry / Context / Memory / Audit
  -> 各部门业务接入
```

### 产品边界确认

- 产品目标仍然是“一个通用 Agent 覆盖所有业务功能”。
- 部门差异通过工具集、上下文、模板和动态页面承载方式实现。
- 动态 UI 基础设施属于通用 Agent 的前置条件，而不是可选附属功能。

## 自定义字段与 AI 字段感知能力（FR1303-FR1329）

### 背景

为了让动态表单、动态详情和 AI 任务真正适配企业差异化业务对象，平台需要在统一 Agent Runtime 下建立“字段定义 + 场景显示 + AI 消费”的一体化能力。

如果只支持新增字段而不支持 AI 理解字段语义，企业仍然需要在聊天中反复解释字段含义，AI 输出也无法稳定贴合真实业务上下文。

### 目标

1. 支持管理员按业务对象扩展字段模型
2. 支持字段显示规则与 AI 使用规则分离治理
3. AI 只能消费被授权、被解释、命中任务范围的字段
4. 动态页面在新增字段后无需前端改代码即可生效
5. 提升 AI 输出对企业上下文和行业差异的贴合度

### 功能需求

| 编号 | 需求 | 说明 |
|-----|------|------|
| FR1303 | 系统支持按业务对象新增自定义字段 | 字段扩展 |
| FR1304 | 系统支持基础字段类型：文本、长文本、数字、金额、日期、日期时间、单选 | MVP 类型范围 |
| FR1305 | 每个字段必须维护唯一的 `field_key` 作为稳定标识 | 唯一标识 |
| FR1306 | 系统支持字段启用与停用 | 生命周期 |
| FR1307 | 字段定义至少包含名称、标识、类型、默认值、必填、帮助说明、状态等元数据 | 字段模型 |
| FR1308 | 系统支持按场景配置字段显示规则 | 列表/详情/创建/编辑/审批 |
| FR1309 | 系统支持按场景配置字段显示顺序 | 展示顺序 |
| FR1310 | 系统支持字段在创建和编辑场景下的必填控制 | 表单约束 |
| FR1311 | 动态表单与动态详情运行时按字段配置自动渲染 | 动态 UI 生效 |
| FR1312 | 系统支持将字段标记为 AI 可用或 AI 不可用 | AI 边界 |
| FR1313 | 字段被标记为 AI 可用时必须填写 AI 语义说明 | AI 语义 |
| FR1314 | 系统支持为字段配置 AI 使用范围 | 生成/摘要/建议/问答 |
| FR1315 | 系统支持将字段标记为 AI 优先参考字段 | AI 优先级 |
| FR1316 | AI 任务触发时系统按当前业务对象加载可用字段 schema | 运行时 |
| FR1317 | 系统只向当前任务注入命中范围且 AI 可用的字段 | 最小暴露 |
| FR1318 | 系统向 AI 注入的字段上下文必须包含字段定义摘要与当前记录值 | 结构化上下文 |
| FR1319 | 字段定义摘要至少包含 `field_key`、字段名称、类型、语义说明与允许任务范围 | Schema 摘要 |
| FR1320 | 字段无值时必须显式传递为空，不得伪造业务值 | 空值处理 |
| FR1321 | AI 不得使用未授权字段 | 使用边界 |
| FR1322 | AI 不得对空字段编造内容 | 内容约束 |
| FR1323 | 字段语义说明不足时，AI 应返回补充提示而不是强行推断 | 兜底策略 |
| FR1324 | AI 使用关键自定义字段时，应在可解释区域展示字段引用说明 | 透明可控 |
| FR1325 | 字段停用后，创建与编辑场景默认不再展示，历史数据保留 | 生命周期 |
| FR1326 | 字段停用且 AI 不可用后，不得继续进入 AI 上下文 | 生命周期 |
| FR1327 | 本期不提供字段彻底删除能力，仅支持停用 | MVP 边界 |
| FR1328 | 字段定义与 AI 配置必须按租户隔离 | 安全性 |
| FR1329 | 新增字段、场景配置和 AI 配置变更必须写入审计日志 | 审计治理 |

### 影响范围

本能力将影响以下模块：

1. 业务对象配置
2. 动态表单系统
3. 动态详情系统
4. AI 上下文组装层
5. AI 输出可解释区域
6. AI 审计与权限治理

### 依赖关系

1. 依赖已有 `Epic 42` 的动态表单与动态详情渲染基础设施
2. 需要与 Agent Runtime 协同，在 AI 任务执行前组装字段 schema
3. 需要与字段级权限、脱敏和治理方向协同
4. 需要审计日志能力记录字段配置与 AI 使用边界
