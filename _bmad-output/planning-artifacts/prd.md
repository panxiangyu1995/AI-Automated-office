## Executive Summary

### 产品愿景

**AI-Automated-office** 是一款**面向 Agent 的企业级云服务 SaaS**，旨在为企业提供一个无前端界面、通过自然语言 Agent 驱动业务流程的经营管理平台。

**核心理念：**
- **无前端 SaaS**：不提供传统 Web/桌面 UI，企业员工通过本地 Agent（Claude Code、Codex、Gemini、OpenCode、OpenClaw、Hermes 等）对话来操作系统
- **Agent→CLI→API 唯一交互链路**：所有业务操作必须通过"用户与 Agent 对话 → Agent 调用 CLI Skill → CLI 发送 HTTPS 请求到 Go API"的链路完成。Agent 禁止直接调用业务 API（curl/HTTP 客户端），必须通过 `ao-cli skill execute` 执行所有业务操作。CLI 统一管理认证凭证生命周期，Agent 不接触任何凭证。服务器端验证请求来源 Header `X-Request-Source: ao-cli`，拒绝非 CLI 请求
- **数据即服务**：Agent 调用 API 获取数据后，可生成 HTML/文档进行可视化展示
- **权限即壁垒**：完善的多租户隔离 + RBAC 权限体系，确保 Agent 只能访问授权范围内的数据
- **开源+局域网部署**：代码开源（AGPL v3），支持社区局域网部署

**目标用户：**
- **云服务运营商（你）**：运营整个平台，创建集团/企业，管理所有租户
- **集团老板**：拥有一个或多个企业，查看跨企业经营数据
- **企业管理员**：管理企业员工、部门、业务数据
- **部门经理**：管理本部门员工和业务
- **员工**：使用业务功能（无管理权限）

**核心问题：**
- 传统 SaaS 系统需要开发维护复杂的前端界面
- 企业员工需要学习多种多样的前端操作方式
- Agent 时代，Agent 可以替代人完成大量操作，但缺乏企业级后端 API 支持

**解决路径：**
- 纯后端 API 服务（云端）+ 本地 CLI（唯一入口）+ 消息轮询
- CLI 是 Agent 与 API 之间的唯一桥梁：Agent 只能通过 CLI Skill 调用 API，CLI 负责认证、请求签名、错误重试
- 完善的权限体系确保 Agent 访问安全
- 支持多种主流 Agent 的 CLI Skill 调用
- 开源（AGPL）+ 商业授权双轨，支持局域网部署

### 差异化核心

| 维度 | 传统 SaaS | 本产品 |
|------|----------|--------|
| **产品形态** | Web/桌面 UI + 后端 | **纯后端 API + 本地 CLI** |
| **用户交互** | 人操作界面 | **用户与 Agent 对话 → Agent 调用 CLI → CLI 调用 API** |
| **数据展示** | 前端渲染 | **Agent 生成 HTML/文档** |
| **消息通知** | WebSocket/Push | **CLI 轮询 + Agent 通知** |
| **部署方式** | 仅云端 | **云端 + 局域网部署** |
| **开源程度** | 闭源 | **AGPL v3 + 商业授权** |

**核心洞察：**
- Agent 时代，人不再需要直接操作界面，而是通过自然语言指挥 Agent
- 传统 SaaS 的前端界面是给"人"看的，而 Agent SaaS 的"前端"是 CLI + API
- CLI 是 Agent 与 API 之间的唯一桥梁——Agent 不直接接触 API，CLI 管理认证、签名、错误恢复
- 后端足够强大 + 权限控制到位 = 超过传统 SaaS 的体验
- 本地 CLI 轮询解决 Agent 不支持定时任务的问题，确保消息实时性

**🔒 CLI 唯一入口原则（架构铁律）：** CLI 是访问业务 API 的**唯一网关**。Agent 不得直接通过 `curl` 等 HTTP 客户端调用业务端点。所有业务操作必须通过 `ao-cli skill execute` 执行。用户在 CLI 中一次输入凭证（`ao-cli auth login`），CLI 统一管理 token 生命周期、自动刷新、权限校验，Agent 不接触也不存储任何凭证。服务器端应验证请求来源为 CLI（通过自定义 Header `X-Request-Source: ao-cli`），拒绝非 CLI 的 HTTP 请求。CLI 同时记录所有 Skill 执行的操作日志（JSONL 格式，按日期归档），供 Agent 回忆操作历史，确保对话连续性。

**一句话价值主张：** *"让 Agent 成为企业的数字员工，后端 API 成为 Agent 的工作台。"*

## User Journeys

### Journey 1: Operator 初始化平台

**角色：** 云服务运营商（你）

**Opening Scene：** 平台刚部署完毕，需要初始化整个系统。

**Rising Action：**
1. 创建首个集团账号
2. 集团老板注册并绑定集团
3. 老板创建自己的企业
4. 配置企业管理员账号
5. 监控平台运营状态

**Climax：** 平台上有多个企业正常运行，运营商可以查询所有企业经营数据。

**Resolution：** 平台稳定运营，持续有新企业入驻。

---

### Journey 2: Group Owner 多企业管理

**角色：** 集团老板

**Opening Scene：** 老板拥有 A 公司和 B 公司，需要统一管理。

**Rising Action：**
1. 登录系统，看到所有企业列表
2. 切换到 A 公司视角，查看销售数据
3. 切换到 B 公司视角，查看生产情况
4. 为跨企业员工 X 开通 B 公司访问权限
5. 生成跨企业经营汇总报告

**Climax：** 一个平台、一个账号，管理所有企业经营。

**Resolution：** 跨企业经营数据一目了然，管理效率大幅提升。

---

### Journey 3: Enterprise Admin 企业初始化

**角色：** 企业管理员

**Opening Scene：** 新企业入驻，需要在系统上建立组织架构。

**Rising Action：**
1. 创建部门结构（销售部、财务部、生产部...）
2. 设置各部门经理
3. 导入员工档案（批量导入）
4. 配置审批工作流（合同审批、请假审批...）
5. 测试系统功能

**Climax：** 员工开始使用系统，通过 Agent 处理业务。

**Resolution：** 企业正常运转，管理员持续优化配置。

---

### Journey 4: Department Manager 部门管理

**角色：** 部门经理

**Opening Scene：** 销售部经理需要管理本部门日常工作。

**Rising Action：**
1. 查看本月销售订单
2. 处理待审批的报价单
3. 查看员工业绩数据
4. 收到新员工入职通知，分配工位和设备
5. 安排下周部门会议

**Climax：** 通过 Agent 说"查看本月销售数据"，自动生成 HTML 报告。

**Resolution：** 部门运转顺畅，经理有更多时间思考策略。

---

### Journey 5: Employee 日常使用

**角色：** 员工

**Opening Scene：** 员工张三入职第一天，不知道如何使用系统。

**Rising Action：**
1. 通过 Claude Code 说"查看我的个人信息"
2. Agent 调用 API，张三看到自己的档案
3. 说"帮我提交一个请假申请"
4. Agent 创建申请单，提交审批
5. 部门经理审批通过，张三收到通知

**Climax：** 张三发现只需要说话就能完成所有操作。

**Resolution：** Agent 成为张三的工作助手，处理各种日常事务。

---

### Journey 6: Agent 处理业务流程

**角色：** Claude Code / Agent

**Opening Scene：** 用户对 Agent 说"帮我处理今天的所有待审批事项"。

**Rising Action：**
1. Agent 调用 `ao-cli skill execute approval --action list_pending`
2. CLI 发送请求到 `/api/v1/approvals/pending`，获取所有待审批事项列表
3. Agent 为用户展示审批摘要
4. 用户逐个确认或拒绝
5. Agent 调用 `ao-cli skill execute approval --action approve --id {id}`

**Climax：** 批量处理完成，所有审批结果反馈给用户。

**Resolution：** Agent 定期轮询消息，主动通知用户新消息。

---

### Journey 7: CLI 消息轮询机制

**角色：** 本地 CLI

**Opening Scene：** CLI 在后台持续运行，Agent 不支持定时任务。

**Rising Action：**
1. CLI 每 30 秒轮询 `/api/v1/messages/unread`
2. 如果有新消息，CLI 通知 Agent
3. Agent 将消息内容告知用户
4. 用户通过 Agent 处理消息相关业务
5. 处理完成后，消息标记为已读

**Climax：** 即使 Agent 不支持定时任务，用户也能实时收到消息通知。

**Resolution：** 消息实时性得到保障，Agent 体验流畅。

---

### Journey 8: 跨部门沟通与消息通知

**角色：** 销售部员工 / 跨部门协作

**Opening Scene：** 销售部员工张三与客户洽谈产品 A 的订单，客户表示有意向采购 100 台，但张三需要了解公司仓库的实际库存情况。

**Rising Action：**

1. 张三对 Agent 说"帮我查询一下仓库里产品 A 还有多少库存"
2. Agent 调用库存 API 查询仓库数据，返回：产品 A 当前库存 50 台
3. 张三发现库存不足，但客户已确认采购意向，于是与客户签订销售合同（100 台）
4. 销售订单已创建，产品 A 需要补货 50 台
5. 张三对 Agent 说"帮我通知生产部经理张三，生产产品 A 100 台"
6. Agent 解析用户意图，调用消息 API，将生产任务通知发送给生产部经理
7. 生产部经理张三收到消息通知（通过 CLI 轮询），查看具体生产任务内容
8. Agent 持续跟踪任务状态，如有更新及时通知相关方

**Climax：** 跨部门协作通过 Agent 代理完成，无需繁琐的内部沟通流程，销售、生产、仓库信息实时同步。

**Resolution：** Agent 成为跨部门协作的中枢，自动协调各部门资源，提升企业整体运营效率。

## Innovation & Novel Patterns

### Agent-First SaaS 模式

```
传统 SaaS：人 → 界面 → API → 数据库
Agent SaaS：人 → Agent → API → 数据库 → Agent → HTML/文档 → 人
```

**核心差异：**
- 人不直接操作界面，而是通过自然语言指挥 Agent
- Agent 负责任务编排、API 调用、结果汇总、生成报告
- 数据展示由 Agent 生成可视化文档实现

### 无界面设计原则

| 原则 | 说明 |
|------|------|
| **API 即界面** | 所有功能通过 REST API 暴露 |
| **权限即视图** | RBAC 决定 Agent 能看到什么数据 |
| **文档即展示** | Agent 生成的 HTML/文档作为展示层 |
| **工作流即流程** | 审批流替代前端操作流程 |

### 多租户隔离模式

```
运营商
    ↓
├── 集团 A（老板拥有多个企业）
│   ├── 企业 A1
│   │   ├── 部门：销售部
│   │   ├── 部门：财务部
│   │   └── 员工：张三、李四
│   └── 企业 A2
└── 集团 B
```

**隔离策略：**
- 数据库级隔离：每个企业独立 PostgreSQL schema
- 认证隔离：OAuth 2.0 + 企业专属 Client ID
- 权限隔离：RBAC 绑定企业上下文

### 交互架构

```
┌─────────────────────────────────────────────────────────────┐
│                       User（用户）                            │
│                  "帮我修改合同标题"                           │
│  用户第一次使用时在 CLI 输入一次凭证（ao-cli auth login）      │
└────────────────────────────┬────────────────────────────────┘
                             │ 自然语言
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                    Agent（本地 Agent）                        │
│          Claude Code / Codex / Gemini / OpenCode...         │
│  1. 理解用户意图  2. 选择 Skill  3. 组装参数               │
│  ⚠ Agent 不接触任何凭证，不直接调用 HTTP API               │
└────────────────────────────┬────────────────────────────────┘
                             │ ao-cli skill execute
                             ▼
┌─────────────────────────────────────────────────────────────┐
│              ═══ CLI Skill（唯一网关） ═══                   │
│  $ ao-cli skill execute modify_contract                    │
│     --contract_id="xxx" --field="title" --value="新标题"    │
│  → CLI 统一管理 Token（自动刷新、权限校验）                 │
│  → 服务器验证请求来源为 CLI，拒绝非 CLI 请求                │
└────────────────────────────┬────────────────────────────────┘
                             │ HTTPS REST API（仅接收 CLI 请求）
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                     Cloud Backend（云端）                      │
│  PATCH /api/v1/contracts/{id} → 权限检查 → 事务处理 → DB  │
└─────────────────────────────────────────────────────────────┘
```

## 组织架构与权限模型

### 组织层级

```
云服务运营商（System）
    ↓ 创建
集团（Group）
    ↓ 捆绑
    ├── 企业 A（子公司）
    │   ├── 部门 1
    │   │   ├── 部门经理
    │   │   └── 员工
    │   └── 部门 2
    └── 企业 B（子公司）
```

### 角色定义

| 角色 | 范围 | 权限 |
|------|------|------|
| **Operator（运营商）** | 全局 | 创建集团、捆绑企业、查看运营数据 |
| **Group Owner（集团老板）** | 集团 | 创建/管理多个企业、开通员工跨企业权限 |
| **Enterprise Admin（企业管理员）** | 企业 | CRUD 员工/部门、配置审批流、管理业务数据 |
| **Department Manager（部门经理）** | 部门 | CRUD 本部门员工和部门本身、处理审批 |
| **Employee（员工）** | 个人 | 使用业务功能（无管理权限） |

### 跨企业权限

```
员工 X（在企业 A 工作）
    ↓ 获得跨企业权限
可访问企业 B 的指定范围
    ↓ 权限来源
├── 开通权限：集团老板（拥有企业 A 和 B）
└── 分配范围：企业 B 的管理员
```

### 权限检查流程

```
Agent 请求 API
    ↓
API Gateway 验证 Token
    ↓
提取企业 ID + 用户 ID + 角色
    ↓
RBAC 权限检查
    ↓
资源归属检查（企业/部门/个人）
    ↓
操作允许？ ─┬─ 是 → 执行操作
           │
           └─ 否 → 返回 403 Forbidden
```

### 25.6 CLI 初始化与 Skill 下载（FR-CLI）

> **新用户首次使用 CLI 时，需要一键初始化环境：下载 Skill、生成 CLAUDE.md 和 agent.md。** 零配置开箱即用。

| FR-ID | 需求描述 |
|-------|---------|
| FR-CLI-001 | CLI 提供 `ao-cli init` 初始化命令：引导用户输入 API 地址、执行 OAuth 登录、下载该企业专属 Skill 矩阵、生成 CLAUDE.md 和 agent.md 配置文件 |
| FR-CLI-002 | CLI 初始化时自动下载企业专属 Skill 定义文件到本地 `~/.ai-office-cli/skills/` 目录，Skill 定义包含所有操作、参数、开场白，Agent 可直接读取 |
| FR-CLI-003 | CLI 初始化时自动生成 `CLAUDE.md` 文件：内容包含企业信息、可用 Skill 列表、调用规范、认证方式、API 地址，使 Agent 在 Claude Code 环境中自动识别可用能力 |
| FR-CLI-004 | CLI 初始化时自动生成 `agent.md` 文件：内容包含 Agent 行为规范（角色设定、交互风格、权限边界、错误处理策略），确保 Agent 行为符合企业要求 |
| FR-CLI-005 | CLI 支持 `ao-cli init --update` 命令：当运营商修改了企业 Skill 矩阵或配置后，员工可执行此命令更新本地 Skill 文件和 CLAUDE.md，保持与云端同步 |
| FR-CLI-006 | CLAUDE.md 和 agent.md 的内容由运营商可通过 `operator_skill_configure` Skill 客制化：不同企业的 CLAUDE.md 模板不同（含企业名称、行业特性、操作规范等），行业模板包含预设模板 |
| FR-CLI-007 | CLI 初始化时自动生成 `README.md` 客制化使用指南：内容基于企业已开通模块和已配置 Skill 动态生成，包含企业信息、已开通功能列表、各 Skill 使用说明与示例、常见问答、快捷指令速查表，面向企业员工（非技术人员）可读 |
| FR-CLI-008 | README.md 由服务端模板渲染生成：运营商可通过 `operator_skill_configure` Skill 中的 `customize_readme` 操作客制化 README.md 模板内容（如添加企业专属注意事项、禁止操作说明、内部术语表等），行业模板包含预设 README.md 模板 |
| FR-CLI-009 | CLI 自动记录所有 Skill 执行操作日志：每次 `ao-cli skill execute` 执行时，CLI 将操作详情（时间戳、Skill 名称、action、参数摘要、执行结果状态、响应摘要）写入本地日志文件，供 Agent 回忆已执行的操作历史。日志格式为 JSON Lines（.jsonl），每行一条操作记录，Agent 可直接读取和解析 |
| FR-CLI-010 | CLI 操作日志按日期归档保存：日志文件按日期存储在 `~/.ai-office-cli/logs/` 目录下，文件名格式为 `YYYY-MM-DD.jsonl`（如 `2026-07-08.jsonl`）。当日日志追加写入，跨日自动创建新文件。CLI `skill help` 输出中明确说明日志查看位置和格式，Agent 可通过读取日志文件回忆操作历史 |

#### CLI 配置模式

CLI 使用 `~/.ai-office-cli/config.yaml` 作为配置文件，支持 YAML 格式的配置定义：

```yaml
# CLI 配置文件
api_url: "https://api.example.com"       # API 地址（必填）
enterprise_id: "uuid"                      # 企业 ID（init 时自动填充）
language: "zh-CN"                          # 语言偏好（zh-CN / en-US）
poll_interval: 30                          # 消息轮询间隔（秒，默认 30，可配置 10-300）
tls_skip_verify: false                     # TLS 证书验证跳过（仅局域网自签名证书时使用）
log_level: "info"                          # 日志级别（debug/info/warn/error）
skills_dir: "~/.ai-office-cli/skills/"     # Skill 文件存储目录
cache_dir: "~/.ai-office-cli/cache/"       # 本地缓存目录
logs_dir: "~/.ai-office-cli/logs/"         # 操作日志目录（按日期存储 JSONL 格式）
```

配置通过 `ao-cli init` 初始化生成，用户可手动编辑。配置变更后需执行 `ao-cli init --update` 同步云端配置。

#### CLI 输出格式

CLI Skill 执行结果支持以下输出格式，Agent 可根据场景选择：

| 格式 | 适用场景 | 说明 |
|------|----------|------|
| `json` | 程序化处理 | 结构化 JSON 输出，Agent 可直接解析 |
| `table` | 人类阅读 | 表格化输出，适合 Agent 直接展示给用户 |
| `text` | 简单结果 | 纯文本输出，适合简短状态信息 |
| `markdown` | 文档生成 | Markdown 格式，适合生成报告或文档 |

默认输出格式为 `json`。Agent 可通过 Skill 参数 `output_format` 指定格式。CLI 自动检测 stdout 是否为终端，如为终端则默认使用 `table`。

| FR-ID | 需求描述 |

| FR-DEPLOY-001 | 系统提供跨平台 Docker Compose 部署方案：支持 Linux（Ubuntu/CentOS）、Windows（Server 2019+/Docker Desktop）、macOS（Docker Desktop），同一套 docker-compose.yml 三平台通用 |
| FR-DEPLOY-002 | 系统提供原生二进制部署方案（不依赖 Docker）：为 Linux（amd64/arm64）、Windows（amd64）、macOS（amd64/arm64）分别编译独立可执行文件，企业可直接运行，适合无 Docker 环境的 Windows Server |

| FR-DEPLOY-004 | 系统支持指定数据目录：数据库数据目录、文件上传目录、日志目录均可通过配置文件指定，支持 Windows 路径（`D:\ai-office\data`）和 Unix 路径（`/data/ai-office`） |
| FR-DEPLOY-005 | 系统提供 `ao-cli deploy` 部署引导命令：交互式引导选择部署模式（Docker/原生二进制）、配置端口和数据目录、初始化数据库、创建超级管理员，一键完成局域网部署 |
| FR-DEPLOY-006 | 系统支持局域网内 TLS 自签名证书部署：提供 `ao-cli deploy --tls` 自动生成自签名 CA + 服务端证书，或支持导入企业自有 CA 签发的证书，确保内网通信加密 |
| FR-DEPLOY-007 | 系统支持私有化部署的在线升级：提供 `ao-cli deploy --upgrade` 命令，自动检测当前版本、下载新版本二进制/镜像、执行数据库迁移、滚动重启服务，升级过程不丢失数据 |
| FR-DEPLOY-008 | 系统提供私有化部署健康检查 API：`GET /api/v1/system/health` 返回各组件状态（API/DB/Redis/Disk/Version），局域网运维人员可通过 Agent 按组件逐项排查部署问题 |

### 28. 多语言支持（FR-I18N）

> **Agent-First SaaS 的多语言维度与传统 SaaS 完全不同 — 没有前端 UI 翻译问题，但整条交互链路（Skill 定义 → 错误码 → 生成文件 → Agent 对话提示）都需要语言适配。** MVP 支持中文和英文。

| FR-ID | 需求描述 |
|-------|---------|
| FR-I18N-001 | 系统支持语言偏好设置：用户级别和企业级别均可设置首选语言（zh-CN / en-US），用户偏好优先于企业偏好，企业偏好优先于系统默认（zh-CN） |
| FR-I18N-002 | Skill 定义支持多语言：每个 Skill 的 display_name、description、examples、opening_message 均提供中英文版本，CLI 下载 Skill 时根据用户语言偏好下载对应语言版本 |
| FR-I18N-003 | API 错误码支持多语言：结构化错误码的 user_message 字段根据请求头 `Accept-Language` 返回对应语言的错误描述，开发者可通过 error_code 做程序化处理，用户通过 user_message 理解错误 |
| FR-I18N-004 | CLAUDE.md / agent.md / README.md 生成时支持多语言：根据用户语言偏好生成对应语言版本的文件，企业英文员工获得英文指南，中文员工获得中文指南 |
| FR-I18N-005 | 系统消息和通知支持多语言：审批通知、预警推送、公告等消息内容根据接收者的语言偏好发送对应语言版本，同一企业内中英文员工收到各自语言的推送 |
| FR-I18N-006 | 运营商可通过 `operator_skill_configure` Skill 管理多语言内容：为 Skill 定义、消息模板、行业模板补充或修改英文翻译，确保中英文内容同步 |

### 29. Agent 数据导出（FR-EXPORT）

> **Agent-First SaaS 的核心交互模式之一：用户通过自然语言告诉 Agent 要导出什么数据，Agent 调用导出 API 生成文件。** 传统 SaaS 的导出是"点按钮选筛选条件"，我们的导出是"说一句话，Agent 帮你搞定"。导出权限必须与 RBAC 绑定——Admin 可导出所有数据，员工只能导出与自己相关的业务数据。

| FR-ID | 需求描述 |
|-------|---------|
| FR-EXPORT-001 | 系统支持 Agent 对话式数据导出：用户通过自然语言描述导出需求（如"帮我导出2026年6月所有合同清单"），Agent 将自然语言翻译为导出 API 参数（实体类型、筛选条件、格式），调用导出 API 生成文件 |
| FR-EXPORT-002 | 系统支持单实体导出：用户可导出任意核心业务实体的数据列表，包括但不限于客户、合同、售后工单、报价单、采购单、销售单、产品、供应商、应收/应付、发票、员工等，支持按任意可查询字段筛选（时间范围、状态、负责人等） |
| FR-EXPORT-003 | 系统支持跨实体关联导出：以客户为锚点，导出该客户的所有关联业务数据（合同、售后工单、报价单、销售订单、往来款等），生成单个 Excel 文件，每个实体一个 Sheet |
| FR-EXPORT-004 | 系统支持以员工为锚点的业务记录导出：导出指定员工创建/负责的所有业务单据（合同、工单、报价单、采购单、销售单等），生成单个 Excel 文件，每个实体一个 Sheet |
| FR-EXPORT-005 | 系统支持员工操作日志导出：导出指定员工的操作日志清单（操作时间、操作类型、操作对象、变更前后值），格式为 Excel/CSV |
| FR-EXPORT-006 | 导出权限与 RBAC 绑定：企业管理员（admin 角色及拥有 `*_export` 权限的角色）可导出企业内所有数据；普通员工只能导出与自己相关的数据（自己是创建人/负责人/参与人的记录），无权导出他人数据 |
| FR-EXPORT-007 | 导出格式支持 .xlsx 和 .csv：单实体导出默认 .xlsx，多实体关联导出为 .xlsx（多 Sheet），用户可在对话中指定格式 |
| FR-EXPORT-008 | 系统支持导出任务异步执行：数据量较大时（>1000 条），导出任务异步执行，Agent 通过消息轮询获取导出完成通知，下载导出文件 |
| FR-EXPORT-009 | 系统支持导出字段选择：Agent 可根据用户对话意图选择导出字段子集（如"只导出合同编号、名称和金额"），而非必须导出全部字段 |
| FR-EXPORT-010 | 系统支持导出数据脱敏：导出时对敏感字段（手机号、身份证号、银行卡号等）按企业脱敏规则处理，与 FR-SEC2-002 脱敏配置一致 |

## API Design

### 交互架构

```
User（自然语言） → Agent（理解意图） → CLI Skill（唯一网关，ao-cli） → Cloud API（业务处理）
```

**各层职责：**

| 层级 | 职责 | 执行者 |
|------|------|--------|
| User | 自然语言表达需求；首次使用时在 CLI 输入一次凭证 | 人 |
| Agent | 理解意图、选择 Skill、组装参数、调用 `ao-cli skill execute`；不接触凭证、不直接调用 HTTP API | Claude Code 等 |
| CLI Skill | 标准化指令格式、统一管理 Token 生命周期、发起 API 请求（唯一网关） | 本地 `ao-cli` 工具 |
| Cloud API | 业务逻辑处理、数据持久化；验证请求来源为 CLI | 云端服务器 |

### API 规范

| 规范 | 要求 |
|------|------|
| 协议 | HTTPS REST JSON |
| 版本 | URL 路径版本 `/api/v1/` |
| 认证 | OAuth 2.0 Bearer Token |
| 文档 | OpenAPI 3.0 |
| 错误码 | HTTP Status + 业务错误码 |
| 分页 | Cursor-based + Offset |

### 认证流程

```
Agent 请求登录
    ↓
POST /api/v1/auth/login
{
  "client_id": "enterprise_xxx",
  "client_secret": "xxx",
  "username": "employee@enterprise.com",
  "password": "xxx"
}
    ↓
返回 Access Token + Refresh Token
    ↓
Agent 携带 Access Token 调用 API
Authorization: Bearer <access_token>
    ↓
Token 过期 → 使用 Refresh Token 刷新
POST /api/v1/auth/refresh
```
