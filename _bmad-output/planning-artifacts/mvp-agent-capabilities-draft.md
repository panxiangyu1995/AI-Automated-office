## 一、讨论目标

### 产品核心定位：一句话入口

> **"所有任务和工作都在 AI Chat Panel 中跟 AI 对话，之后 Agent 帮我们完成"**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    产品核心定位                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  用户视角：                                                                  │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │   "帮我处理今天的审批"                                              │   │
│  │          ↓                                                         │   │
│  │   AI Chat Panel ← → Agent ← → 完成所有任务                        │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  交互模式：                                                                  │
│  ├── AI Chat Panel：主要入口，对话驱动所有任务                            │
│  ├── 工作区编辑面板：辅助编辑，必要时的手动编辑                           │
│  └── 一切以对话为核心，UI 编辑为辅                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**两步走策略：**
1. **Phase 1**：先实现 OpenClaw 所有功能（定时任务 + 心跳 + 工具 + 会话管理等）
2. **Phase 2**：基于此 Agent 框架扩展权限控制，适配办公场景（部门隔离、权限矩阵等）

**核心交互原则：**
- **AI 即入口**：用户通过自然语言对话完成所有操作
- **透明可控**：Agent 执行过程可见，用户可干预
- **零学习成本**：说话就能完成任务
- **编辑为辅**：仅在必要时使用工作区编辑面板进行手动调整

### 2.3 主 Agent 与 Subagent 的 tools 差异

### 2.4 Agent 两级分类

| 维度 | Department Agent | Personal Agent |
|------|------------------|---------------|
| **创建者** | 管理员/插件 | 用户本人 |
| **使用范围** | 部门内所有用户共享 | 仅创建者本人 |
| **数据存储** | 云端 + 本地同步 | 仅本地 |
| **权限来源** | 部门 × 角色 × 能力矩阵 | 继承主 Agent 权限 |
| **配置入口** | 管理员后台 / 插件 manifest | 用户设置页面 |
| **生命周期** | 随插件安装/卸载 | 用户自行管理 |

### 2.5 权限域设计（角色 × 部门 × 能力三维矩阵）

```
    ↓

    ↓
检查部门归属权限
    ↓

    ↓
```

### 2.6 核心企业场景：部门间数据共享与云端同步

**需求描述：**
- 所有部门共享的数据和重要数据，能通过 AI 对话让 AI 调用工具上传到云端
- 跨部门数据可见性控制
- 统一数据中台，打破数据孤岛

**典型场景：**

| 操作 | 部门 | 数据类型 | 可见范围 | 云端同步 |
|------|------|----------|----------|----------|
| 上传客户合同 | 销售部 | 合同文件 | 销售+财务 | 同步 |
| 上传入库单 | 仓储部 | 入库记录 | 仓储+销售 | 同步 |
| 上传员工档案 | 人事部 | 人事档案 | 人事+管理层 | 同步 |
| 上传发票 | 财务部 | 财务凭证 | 财务+管理层 | 同步 |
| 上传审批文件 | 审批中心 | 审批附件 | 按审批流程 | 同步 |

### 2.7 数据访问权限配置

**需求描述：**
- 管理员可以配置权限到具体的员工角色
- 管理员也可以配置权限到个人
- 双重配置机制：角色权限 + 个人权限

**权限配置层级：**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    权限配置层级                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  第一层：角色权限（默认继承）                                                │
│  ├── hr_manager: 可访问所有 HR 数据                                         │
│  ├── sales_rep: 可访问客户、合同、订单                                      │
│  ├── finance_staff: 可访问发票、台账（不含薪资）                            │
│  └── warehouse_keeper: 可访问库存、入库、出库                               │
│                                                                             │
│  第二层：个人权限（覆盖或补充）                                             │
│  ├── user_001: 额外可访问竞品数据（超出角色）                              │
│  ├── user_002: 限制访问薪资数据（收紧角色权限）                            │
│  └── user_003: 仅可访问指定客户                                            │
│                                                                             │
│  权限优先级：个人配置 > 角色配置                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**权限配置结构：**

```yaml
权限配置模型：

角色权限（Role-based Access Control）：
─────────────────────────────────────────
role: hr_manager
department: hr
data_access:
  - resource: employee档案
    level: full       # 读写
  - resource: contract合同
    level: full
  - resource: salary薪资
    level: read       # 仅读
  - resource: attendance考勤
    level: full

个人权限（User-based Access Control）：
─────────────────────────────────────────
user_id: user_001
extends:
  role: hr_manager    # 继承角色权限
  department: hr
customize:
  # 扩展权限（超出角色）
  - resource: employee档案
    level: full
    action: [read, write, export]  # 增加导出权限
  - resource: salary薪资
    level: full   # 提升为完全访问

restrictions:
  # 限制权限（收紧角色）
  - resource: attendance考勤
    level: read   # 降级为仅读
```

```
│  ┌─────────────────────────┐  ┌─────────────────────────────────────────┐│

│  └─────────────────────────┘  └─────────────────────────────────────────┘│

│  │ ✅ 合同信息 - 读写                    ✅ 合同信息 - 读写                ││

│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                             │
│  数据范围配置（可选）                                                       │
│  ┌─────────────────────────────────────────────────────────────────────────┐
│  │ 员工档案范围：                                                           │
│  │ ○ 全部员工   ○ 仅本部门   ● 仅指定员工（选择...）                       │
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                             │
│  [保存配置]  [重置]  [导出配置]                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**权限检查流程：**

```
用户请求访问数据
    ↓
检查个人权限配置
    ↓
├─ 有个人配置 → 使用个人配置
└─ 无个人配置 → 使用角色配置
    ↓
检查数据范围（如：仅本部门）
    ↓
├─ 超出范围 → 返回权限不足
└─ 在范围内 → 执行操作
    ↓
记录审计日志
```

## 三、多会话并行架构

## 四、智能推荐：定时任务推荐机制

**需求描述：**
- 系统在工作过程中智能推荐用户是否需要设置定时任务
- 提升系统智能化程度，减少用户手动配置

**推荐触发场景：**

| 工作场景 | 推荐定时任务 | 推荐理由 |
|----------|-------------|----------|
| 用户提交审批后 | "审批完成提醒" | 审批可能有多个节点，需要跟踪进度 |
| 用户创建合同 | "合同到期提醒" | 合同周期长，容易忘记续签 |
| 用户录入发票 | "发票对账提醒" | 发票处理需要跟进 |
| 用户添加客户 | "客户跟进提醒" | 7天未跟进需要提醒 |
| 用户创建订单 | "订单发货提醒" | 需要跟进物流状态 |
| 用户提交周报 | "周报截止提醒" | 下周提醒提交下期周报 |
| 用户完成库存录入 | "库存盘点提醒" | 月末需要盘点 |

**智能推荐流程：**

```
工作场景触发
    ↓
主 Agent 分析当前操作上下文
    ↓
判断是否需要设置定时任务
    ↓
向用户推荐（温和、不打断流程）
    ↓
用户确认或忽略
```

**推荐时机与方式：**

```yaml
推荐策略：

时机选择：
├── 任务完成后推荐（非打断）
│   └── "完成审批后，推荐设置审批结果提醒"
├── 周期性回顾推荐（非打断）
│   └── "您今天处理了3个审批，设置定时提醒更便捷"
└── 主动询问（非强制）
    └── "是否需要设置定时提醒？"

推荐方式：
├── AI 对话推荐（轻量）
│   └── "💡 建议：设置'审批超时提醒'，避免遗漏"
├── 通知卡片（可点击）
│   └── 卡片包含[立即设置] [下次提醒] [忽略]
└── 设置页面推荐（持久）
    └── 定时任务管理页面显示推荐

推荐频率控制：
├── 每个场景仅推荐一次
├── 重复操作≥3次才推荐
└── 用户忽略后7天内不再推荐
```

```yaml

id: hr_overdue_contract_check
name: 合同到期检查
description: 检查即将到期的劳动合同，提前提醒续签

schedule:
  kind: cron
  expr: "0 9 * * *"       # 每天早上9点
  tz: Asia/Shanghai

department: hr
enabled: true

# 触发时的 Agent 行为
agent:
  type: department        # department | primary | personal
  department: hr

# 触发时的工具调用
tools:
  - hr_contract_query      # 查询合同
  - hr_contract_expiry_check # 检查到期
  - notification_send        # 发送通知

# 通知配置
notification:
  channel: ai_panel       # ai_panel | system | email
  targets:
    - role: hr_manager    # HR 经理
    - users: [user_id_1] # 指定用户

# 执行条件
conditions:
  - type: data_check
    query: contracts_expiring_within_30_days
    operator: exists

# 失败处理
failure:
  retry: 3
  retry_interval: 1h
  alert_on_failure: true
```

```rust
enum DeliveryChannel {
    // AI Chat Panel - 对话式投递
    AiChatPanel {
        session_id: Option<SessionId>,  // 可指定会话
        append_to_history: bool,
    },

    // 动态通知卡片 - 弹窗式投递
    NotificationCard {
        title: String,
        urgency: Urgency,               // high / normal / low
        actions: Vec<CardAction>,      // 可操作按钮
        auto_dismiss: Option<Duration>,// 自动消失时间
    },

    // 消息列表 - 列表式投递
    MessageList {
        category: MessageCategory,     // 消息分类
        persist: bool,                  // 是否持久化
    },

    // 组合投递
    Multi {
        channels: Vec<DeliveryChannel>,
        primary: DeliveryChannel,      // 主要展示渠道
    },
}

struct DeliveryStrategy {
    // 紧急程度判定
    fn determine_urgency(&self, event: &Event) -> Urgency {
        match event.event_type {
            EventType::ApprovalOverdue => Urgency::High,
            EventType::InventoryAlert => Urgency::High,
            EventType::TaskCompleted => Urgency::Low,
            EventType::DailySummary => Urgency::Normal,
            _ => Urgency::Normal,
        }
    }

    // 选择投递渠道
    fn select_channel(&self, context: &DeliveryContext) -> DeliveryChannel {
        match (context.urgency, context.user_status) {
            (Urgency::High, _) => DeliveryChannel::NotificationCard {
                urgency: Urgency::High,
                ..Default::default()
            },
            (Urgency::Normal, UserStatus::Online) => DeliveryChannel::AiChatPanel {
                append_to_history: true,
            },
            (Urgency::Low, _) => DeliveryChannel::MessageList {
                category: MessageCategory::Info,
                persist: true,
            },
            _ => DeliveryChannel::AiChatPanel::default(),
        }
    }
}
```

```typescript
export class SessionManager {
  private sessions = new Map<string, StoredSession>()

  create(ws: WebSocket, cols: number, rows: number): string | null {
    if (this.isFull) return null
    if (this.isUserRateLimited(userId)) return null

    const pty = this.spawnPty(cols, rows)
    const session = this.store.register(pty, userId)
    this.wirePtyEvents(session)
    this.wireWsEvents(session)
    return session.token
  }

  resume(token: string, ws: WebSocket): boolean {
    const session = this.store.reattach(token, ws)
    if (!session) return false

    // 重放滚动缓冲
    const scrollback = session.scrollback.read()
    if (scrollback.length > 0) {
      ws.send(scrollback)
    }
    return true
  }
}
```

```typescript
export function shouldExtractMemory(messages: Message[]): boolean {
  const currentTokenCount = tokenCountWithEstimation(messages)

  if (!isSessionMemoryInitialized()) {
    if (!hasMetInitializationThreshold(currentTokenCount)) {
      return false
    }
  }

  const hasMetTokenThreshold = hasMetUpdateThreshold(currentTokenCount)
  const toolCallsSinceLastUpdate = countToolCallsSince(messages, lastMemoryMessageUuid)
  const hasMetToolCallThreshold = toolCallsSinceLastUpdate >= getToolCallsBetweenUpdates()

  // 检查最后助手消息是否有工具调用（安全提取点）
  const hasToolCallsInLastTurn = hasToolCallsInLastAssistantTurn(messages)

  return (hasMetTokenThreshold && hasMetToolCallThreshold) ||
         (hasMetTokenThreshold && !hasToolCallsInLastTurn)
}
```
