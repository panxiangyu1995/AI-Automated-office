# UX Design Specification - VSCode Reference Summary

**Author:** Codex
**Date:** 2026-03-25

---

## Executive Summary

### 项目愿景

**VSCode（Code - OSS）** 的 UX 核心不是“做一个功能很多的 IDE”，而是构建一个**可扩展、可定制、低摩擦的工作台（Workbench）**，服务开发者的 edit-build-debug 主循环。

从源码与官方 README 可以总结出它的体验定位：

- 用一个稳定的工作台承载编辑、导航、调试、终端、扩展与设置
- 让键盘驱动、命令驱动与鼠标直操作三种交互方式并存
- 让扩展能力进入主界面，但不破坏整体工作台秩序
- 让用户能逐步把界面“调成自己的工作环境”

**一句话定位：**
> *VSCode 的 UX 本质是“一个可编排的开发工作台”，而不是“一个固定流程的软件界面”。*

### 目标用户

| 角色 | 场景 | 核心诉求 | UX 重点 |
|------|------|----------|---------|
| **日常开发者** | 编码、查找文件、运行调试 | 快速进入状态，少打断 | 快捷键、Quick Open、稳定布局 |
| **重度用户 / Power User** | 多项目、多分屏、高频命令 | 极致效率与可定制性 | 命令面板、布局控制、Zen Mode |
| **新手开发者** | 学习语言、安装扩展、理解错误 | 可发现、可恢复、不过载 | 默认布局、侧边栏、Problems/Terminal |
| **扩展作者** | 注入视图、命令、主题、图标 | 接入一致、不破坏系统 | 扩展点、视图容器、状态栏入口 |
| **跨平台使用者** | Windows/macOS/Linux/Web | 行为一致、平台差异可接受 | 标题栏/菜单栏适配、Web/Desktop 共构 |

### 核心功能模块

| 分类 | 模块 | 核心 UX 价值 |
|------|------|--------------|
| **工作台骨架** | Title Bar、Activity Bar、Side Bar、Editor、Panel、Auxiliary Bar、Status Bar | 提供稳定的空间心智模型 |
| **命令式入口** | Command Palette、Quick Open、Quick Pick | 用搜索代替深层菜单导航 |
| **编辑工作区** | Editor Groups、Tabs、Pinned/Sticky、Split、Centered Layout | 支持从单文件到多分屏的连续工作流 |
| **上下文面板** | Explorer、Search、Source Control、Run and Debug、Extensions、Terminal、Problems | 将任务相关信息靠近主编辑区 |
| **反馈系统** | Status Bar、Badges、Notifications、Dirty Indicator | 高频轻反馈 + 低频强提醒 |
| **可定制系统** | Theme、File Icon Theme、Product Icon Theme、Layout Controls | 让“我的工作台”成为长期资产 |
| **扩展系统** | View Containers、Panels、Status Bar Entries、Commands | 把产品边界做成可增长的 UX 结构 |

### 关键设计挑战

| 挑战 | 说明 |
|------|------|
| **高密度信息不过载** | 工作台包含文件树、编辑器、终端、调试、问题、通知，容易产生视觉拥挤 |
| **发现性与效率并存** | 新手需要可见入口，高手希望直接搜索与快捷键完成操作 |
| **可定制但不失一致性** | 用户可隐藏、移动、替换大量 UI；扩展也会注入 UI |
| **扩展生态带来的复杂性** | 扩展加入视图、命令、状态项后，主界面仍要保持秩序 |
| **多平台一致性** | Electron/Web 与不同 OS 的标题栏、菜单栏、窗口行为存在差异 |
| **不中断的工作流** | 文件未保存、通知过多、模式切换频繁都会打断开发“流” |

### 设计机会

| 机会 | 说明 |
|------|------|
| **命令即导航** | Command Palette / Quick Open 把“找入口”转为“输入意图” |
| **稳定空间 + 动态内容** | 外壳稳定，内容可变，降低扩展增长带来的认知成本 |
| **渐进式专业化** | 默认即能用，深入使用时再开启分组、置顶、布局、Zen Mode |
| **主题与图标成为语义层** | 颜色、文件图标、产品图标不仅美化，还承担识别与状态表达 |
| **恢复与持续性体验** | 工作区状态、编辑器视图状态、关闭确认等机制让中断成本更低 |

## 核心用户体验

### 定义性体验

**定义性体验：** 在一个稳定的工作台中，通过搜索、快捷键或直接点击，快速切换上下文并完成开发循环。

这一定义带来三个直接 UX 结论：

- **工作台是主角**：VSCode 先给你一个稳定壳层，再把功能放进壳层里
- **命令是一级入口**：Command Palette、Quick Open 并不是辅助能力，而是核心导航机制
- **编辑器是中心**：侧边栏、面板、状态栏都围绕编辑器协作，而不是与编辑器竞争主焦点

### 平台策略

| 维度 | 策略 |
|------|------|
| **主平台** | 桌面端优先 |
| **补充平台** | Web 工作台可用，保留核心心智模型 |
| **交互主轴** | 键盘优先，鼠标完整支持 |
| **布局基线** | 大屏工作环境，不以移动端为目标 |
| **状态持久化** | 重视工作区恢复、编辑器恢复、布局恢复 |

### 轻松交互

VSCode 的“轻松”不是降低功能密度，而是通过以下方式减少摩擦：

- 用 **Quick Access / Quick Pick** 减少层层点击
- 用 **预览编辑器、临时打开、最近命令历史** 减少错误成本
- 用 **布局控制、菜单栏模式、Zen Mode** 让用户按场景裁剪界面
- 用 **Problems / Status Bar / Notification Toasts** 分层提供反馈，不把所有反馈都做成弹窗

### 关键成功时刻

**成功时刻 1：** 打开工作区后，用户立刻知道“文件在哪、编辑区在哪、运行与问题在哪”。

**成功时刻 2：** 用户按下快捷键，几乎不离开当前焦点，就能打开文件、执行命令、跳转视图。

**成功时刻 3：** 扩展加入新能力后，用户仍感觉它属于原生工作台，而不是“外来弹层”。

**成功时刻 4：** 长时间开发后重新打开窗口，用户能回到之前的上下文，而不是重新搭台。

### 体验原则

| # | 原则 | 说明 |
|---|------|------|
| **1** | **稳定壳层** | 标题栏、活动栏、侧边栏、编辑区、面板、状态栏构成稳定框架 |
| **2** | **搜索优先于找入口** | 高频动作应可通过命令与搜索完成 |
| **3** | **键盘优先但不是键盘专属** | 所有关键能力都应支持鼠标直达 |
| **4** | **渐进暴露复杂度** | 默认简单，深度需求再暴露高级布局与设置 |
| **5** | **扩展接入必须守序** | 新能力通过既有容器进入，不随意创造新的主结构 |
| **6** | **状态要可感知、可恢复** | 脏状态、通知、布局与窗口关闭行为都要清晰 |

## 期望情感响应

### 核心情感目标

| 情感 | 说明 | 设计含义 |
|------|------|----------|
| **掌控感** | 工作台复杂，但始终感觉在自己控制之中 | 可配置、可隐藏、可恢复 |
| **流畅感** | 连续编码时尽量不被界面打断 | 键盘流、命令流、轻反馈 |
| **可靠感** | 文件状态、错误、关闭行为都可预期 | dirty 标记、关闭确认、恢复机制 |
| **归属感** | 用户会把 VSCode 调成“自己的环境” | 主题、图标、布局、扩展、设置同步 |

### 避免的负面情感

**核心负面情感：** 用户觉得自己在和“一个失控增长的 UI 系统”对抗。

**触发原因：**

- 入口太多、位置不稳定
- 扩展把界面挤满
- 关键状态被隐藏
- 关闭或切换时丢失上下文

**设计对策：**

- 用固定工作台区域承载增长
- 用命令面板承接功能扩张
- 用状态栏、徽标、Problems 做分层反馈
- 用恢复机制与确认机制降低不可逆操作焦虑

### 确认策略

| 操作类型 | 确认策略 |
|----------|----------|
| **高频无损操作** | 直接执行，强调速度 |
| **可恢复操作** | 允许先做后撤回，如编辑器切换、布局调整 |
| **潜在数据损失操作** | 通过 dirty 状态与关闭确认保护用户 |
| **噪声控制** | Zen Mode 支持静默通知，仅保留必要提醒 |

### 成就反馈机制

| 反馈类型 | 示例 |
|----------|------|
| **即时状态反馈** | 状态栏显示分支、编码、语言模式、问题计数 |
| **空间反馈** | 徽标、活动项高亮、激活边框 |
| **结果反馈** | Problems、Output、Terminal、Notifications |
| **操作闭环反馈** | Quick Pick 选择后立即生效，编辑器/布局即时更新 |

### 情感旅程设计

| 阶段 | 期望情感 | 设计目标 |
|------|----------|----------|
| **首次打开** | 清晰、专业 | 一眼理解工作台区域 |
| **开始编码** | 顺手、稳定 | 文件切换与编辑无阻塞 |
| **进入复杂任务** | 可控、不慌 | 分屏、面板、调试、终端协同 |
| **遇到错误** | 可诊断、可解决 | Problems + 状态栏 + 输出面板形成闭环 |
| **长期使用** | 越用越像自己的工具 | 主题、图标、布局、扩展沉淀个性化环境 |

### 情感设计原则

| # | 原则 | 说明 |
|---|------|------|
| **1** | **让复杂看起来有秩序** | 功能多，但空间结构必须稳定 |
| **2** | **让高频操作几乎无摩擦** | 高频任务应该短路径完成 |
| **3** | **让状态永远有迹可循** | 活动高亮、dirty、问题、通知都要可见 |
| **4** | **让用户感觉界面会记住自己** | 历史、恢复、布局与主题形成长期关系 |

## UX 模式分析与灵感

### 灵感产品分析

VSCode 的 UX 更像多个优秀模式的“编排”：

- **代码编辑器**：编辑器是主舞台，效率与可读性优先
- **命令中枢**：Quick Access / Command Palette 把操作入口统一抽象成搜索
- **面板式工作台**：像专业桌面工具一样，通过固定边界与可停靠区域管理复杂度
- **平台生态入口**：扩展、主题、图标都通过统一扩展点进入

### 可迁移的 UX 模式

| 模式 | VSCode 中的体现 | 可迁移价值 |
|------|----------------|-----------|
| **稳定工作台骨架** | 标题栏、活动栏、侧边栏、编辑区、面板、辅助栏、状态栏 | 复杂产品要先有固定空间语言 |
| **搜索驱动导航** | Command Palette、Quick Open、Quick Pick | 功能越多，越要减少菜单层级依赖 |
| **渐进式专业模式** | Zen Mode、Centered Layout、Panel/Sidebar Toggle | 同一产品兼容新手与高手 |
| **插件守序接入** | View Container、Panel、Status Bar Entry、Theme Extension Point | 把“增长”变成“可管理增长” |
| **状态分层反馈** | 徽标、状态栏、Problems、Notifications | 高频轻反馈、低频强反馈分层 |

### 要避免的反模式

| 反模式 | 说明 | VSCode 的应对 |
|--------|------|---------------|
| **入口碎片化** | 每个功能都独立占主导航位置 | 用命令面板吸收长尾入口 |
| **扩展无边界生长** | 新能力随意改主框架 | 通过 view/container/status item 统一承载 |
| **强依赖模态窗口** | 频繁弹窗打断流 | 优先用面板、状态栏、通知、Quick Pick |
| **状态黑箱** | 用户不知道哪里出错、哪里在运行 | Problems、Output、Status Bar、Dirty Indicator 公开状态 |

### 设计灵感策略

- 先设计**稳定壳层**，再设计内部功能
- 用**命令式入口**承接规模增长
- 把高级能力设计成**可选层**，而非强行暴露给所有用户
- 把主题、图标、扩展当成 UX 组成部分，而不是皮肤系统

## 设计系统基础

### 设计系统选择

VSCode 采用的是一套**自研、token 驱动、扩展友好的工作台设计系统**，而不是固定组件库叠加主题皮肤。

这套系统的特点是：

- 所有主要区域都有明确的主题 token
- Theme Service 驱动颜色变化
- Color Theme、File Icon Theme、Product Icon Theme 都是一级扩展点
- 工作台部件复用统一的 Part / Pane Composite / Composite Bar 结构

### 选择理由

| 理由 | 说明 |
|------|------|
| **主题可扩展** | 色彩不是写死在组件里，而是绑定到 token |
| **图标可扩展** | 文件图标与产品图标都可替换 |
| **工作台结构统一** | Sidebar、Panel、Auxiliary Bar 都通过相似的容器范式工作 |
| **利于生态生长** | 扩展进入既有系统，不必复制整套 UI 规范 |

### 实施方法

| 层级 | 说明 |
|------|------|
| **主题层** | Color Theme 决定整体颜色语义 |
| **图标层** | File Icon Theme / Product Icon Theme 决定识别语言 |
| **布局层** | Workbench Parts 与 Editor Groups 决定空间结构 |
| **内容层** | View、Panel、Editor、Quick Pick 承载具体任务 |

### 定制化策略

VSCode 的定制化不是“换皮肤”，而是四层定制：

1. **视觉定制**：颜色主题、图标主题、窗口边框等
2. **布局定制**：活动栏位置、面板位置、菜单栏模式、布局控制
3. **交互定制**：快捷键、命令中心、预览标签、滚动行为
4. **能力定制**：扩展、视图、状态项、命令、Webview 面板

## 核心交互定义

### 定义性体验

**定义性体验：** 用户在不离开当前任务上下文的前提下，快速完成“定位目标 -> 打开内容 -> 编辑/运行 -> 查看反馈 -> 再次跳转”。

### 用户心智模型

VSCode 的心智模型可以抽象为：

**工作区 > 视图容器 > 视图 / 面板 > 编辑器组 > 编辑器 > 命令**

这套模型的好处是：

- 空间结构稳定
- 功能增长不必重做导航
- 用户知道每类能力通常出现在哪个区域

### 成功标准

| 标准 | 说明 |
|------|------|
| **文件与命令能被快速找到** | 搜索优先，命令优先 |
| **编辑区可按任务扩展** | 单编辑器、分屏、多组并存 |
| **辅助信息不抢主焦点** | Panel / Status Bar / Notifications 分层表达 |
| **状态可见** | 激活项、dirty、徽标、错误、通知清晰 |
| **中断可恢复** | 关闭、重开、切换后可回到原上下文 |

### 交互模式分析

| 模式 | 表现 |
|------|------|
| **空间导航** | 通过活动栏、侧边栏、面板切换任务领域 |
| **命令导航** | 通过 Command Palette / Quick Open 直达目标 |
| **局部直操作** | 标签拖拽、分屏、面板停靠、显示隐藏 |
| **上下文工具栏** | 标题栏、编辑器标题、状态栏承载当前语义动作 |
| **扩展注入** | 新能力以命令、视图、状态项或面板形式进入 |

### 核心交互流程

**流程 1：打开并定位文件**

1. 用户打开工作区
2. 通过 Explorer 或 Quick Open 搜索目标文件
3. 文件进入编辑器组，必要时以预览方式打开
4. 用户继续通过标签、分屏或最近历史切换上下文

**流程 2：执行命令**

1. 用户调出 Command Palette
2. 输入命令或关键词
3. 从历史、建议或匹配结果中选择
4. 命令直接作用于当前上下文

**流程 3：从问题到修复**

1. 状态栏 / Problems 提示问题数量
2. 用户打开 Problems 或相关文件
3. 在编辑器中修复
4. 问题计数和反馈即时更新

### 检查点与回滚交互

VSCode 没有以“检查点”命名该能力，但其 UX 上存在等价机制：

- **临时预览打开**：Quick Access 中可先预览，再决定固定
- **编辑器视图状态恢复**：切回原编辑器时恢复 view state
- **窗口/工作区恢复**：重新打开后继续上次工作环境
- **关闭前确认**：对潜在数据丢失进行保护

这说明它的回滚哲学不是显式时间轴，而是**弱中断、强恢复**。

### 上下文压缩与关键事实提示

VSCode 使用的不是“大段摘要”，而是**界面级上下文压缩**：

- 标签页显示当前编辑对象
- 编辑器标签支持文件图标、修改态、置顶态、预览态
- Breadcrumbs、标题、文件标签承担路径压缩
- Status Bar 提示当前语言模式、编码、分支、问题等关键事实
- Command Palette 历史与输入保留提供轻量上下文延续

### 审核界面设计

VSCode 的“审核界面”分散在多个位置：

- **Problems**：错误与警告汇总
- **Panel**：终端、输出、调试控制台等过程型反馈
- **Source Control / Diff**：变更审查与比对
- **Status Bar**：全局状态摘要

其策略不是做一个超级审核面板，而是把审核信息放在最贴近任务的地方。

## 视觉设计基础

### 颜色系统

VSCode 的颜色系统是**主题驱动而非品牌锁定**，但默认工作台仍呈现出明确倾向：

| 层级 | 特征 |
|------|------|
| **基础底色** | 中性深浅背景，强调长期使用的低疲劳感 |
| **激活表达** | 用前景变化、边框、选中态区分激活对象 |
| **重点提示** | Activity Bar / Panel Badge 默认采用蓝色 `#007ACC` |
| **高对比支持** | 为 hcDark / hcLight 提供单独 token |
| **反馈色** | 错误、警告、信息由通知与 Problems 使用语义色表达 |

### 字体系统

VSCode 的字体策略可总结为：

- **UI 字体**：紧凑、平台适配、不过分强调品牌个性
- **编辑器字体**：以代码可读性为第一优先级
- **标签与状态字体**：服务信息密度与扫描效率，而非展示感

### 间距与布局

从源码可见，VSCode 在布局上强调**可压缩但不拥挤**：

| 区域 | 关键特征 |
|------|----------|
| **Activity Bar** | 固定窄栏，默认图标式导航，单项尺寸稳定 |
| **Side Bar** | 最小宽度约 170，偏好宽度不少于 300 |
| **Editor** | 最小编辑尺寸约 220 x 70，支持多组网格布局 |
| **Panel** | 最小宽度约 300，默认偏好高度约主容器 40% |
| **Title Bar** | 兼容命令中心、布局控制、全局动作与编辑器动作 |

### 圆角与边框

视觉风格偏向**平直、专业、工程化**：

- 区域间主要依赖 **1px 边框** 与背景层级区分
- 高亮更常通过底边、前景色、badge 表达
- 少用大圆角和大阴影，避免工具界面显得“漂浮”

### 无障碍考虑

VSCode 的无障碍策略不是附加功能，而是内建约束：

- 为主要部件设置合适 role
- 对不需要高频朗读的区域使用更克制的 aria 策略
- 状态栏使用 `role="status"`，同时设置 `aria-live="off"` 避免噪声
- 支持高对比主题与屏幕阅读器优化
- 焦点可见性与键盘导航是一级要求

## 设计方向决策

### 参考设计

VSCode 形成了一条非常明确的设计方向：

- 不追求消费级“轻装饰”
- 不追求传统 IDE 的厚重控制面板
- 选择**轻外壳 + 强结构 + 高扩展性** 的专业工具路线

### 选定布局方案

源码中的工作台主结构为：

**Title Bar → Banner → Activity Bar → Side Bar → Editor → Panel → Auxiliary Bar → Status Bar**

这是一种典型的**四周环抱编辑区**布局：

- 左右用于任务导航与补充视图
- 中间用于主编辑工作
- 下部用于过程输出与问题诊断
- 顶部与底部承接全局控制和全局反馈

### 设计理由

| 决策 | 理由 |
|------|------|
| **编辑区居中** | 保持“代码/内容”是主舞台 |
| **侧栏与面板可停靠** | 让复杂度可伸缩 |
| **标题栏集成命令中心与布局控制** | 把全局入口上提，减少分散 |
| **状态栏长期驻留** | 高频反馈应低成本可见 |

## 用户旅程流程

### 关键旅程选择

本次总结选择三个最能代表 VSCode UX 的旅程：

1. 打开工作区并快速找到文件
2. 在编辑、运行、诊断之间切换
3. 把默认环境逐步调成个人工作台

### 旅程 1：开发者 - 快速定位并开始编辑

| 阶段 | 用户动作 | UX 支撑 |
|------|----------|---------|
| **进入工作区** | 打开项目 | 固定工作台骨架提供定位感 |
| **寻找目标** | 用 Explorer 或 Quick Open 搜索 | 命令式导航减少路径长度 |
| **进入编辑** | 文件在编辑器中打开 | 标签、文件图标、dirty 态支持识别 |
| **切换上下文** | 通过最近历史、标签、分屏切换 | 编辑器组与状态恢复降低切换成本 |

### 旅程 2：开发者 - 编辑到诊断闭环

| 阶段 | 用户动作 | UX 支撑 |
|------|----------|---------|
| **编辑代码** | 在主编辑器中修改 | 编辑器为视觉与交互中心 |
| **运行/调试** | 打开 Terminal / Run and Debug | Panel 承接过程输出 |
| **发现问题** | 查看 Problems / 状态栏计数 | 问题被汇总并可跳转 |
| **修复并验证** | 返回编辑器继续修改 | 编辑器、面板、状态栏形成闭环 |

### 旅程 3：重度用户 - 形成个性化工作台

| 阶段 | 用户动作 | UX 支撑 |
|------|----------|---------|
| **调整布局** | 移动面板、隐藏栏位、开启 Zen Mode | 布局控制 + 设置项 |
| **替换视觉系统** | 选择主题、文件图标、产品图标 | 多层主题扩展点 |
| **安装扩展** | 加入语言、调试、视图能力 | 扩展以既有容器接入 |
| **长期沉淀** | 保留历史、布局和工作习惯 | 持久化配置与恢复机制 |

### 旅程模式总结

VSCode 的旅程共性是：

- 起点经常是**命令 / 搜索**
- 过程围绕**编辑器中心**
- 反馈沉淀在**状态栏 / 面板 / Problems**
- 长期价值来自**定制与恢复**

## 组件策略

### 设计系统基础组件

| 组件 | 角色 |
|------|------|
| **Workbench Part** | 工作台一级区域容器 |
| **Composite Bar** | 活动项、面板项、视图项的统一承载 |
| **Editor Group** | 多文档与多分屏的核心单元 |
| **Quick Input / Quick Pick** | 搜索式操作入口 |
| **Status Bar Entry** | 轻量、持续的全局反馈单元 |
| **Notification Toast / Center** | 短期提醒与汇总反馈 |

### 自定义组件需求

VSCode 的“自定义组件”大多不是视觉个性组件，而是**工作台结构组件**：

- Command Center
- Activity Bar badges
- Editor tabs / pinned / sticky 机制
- Panel title composite bar
- View container / pane composite
- Theme / icon contribution surfaces

### 核心自定义组件规范

| 组件 | 规范方向 |
|------|----------|
| **Activity Bar** | 图标优先、强状态感、窄宽度、支持 badge |
| **Side Bar** | 容纳视图树、表单、列表，支持标题区动作 |
| **Editor Tabs** | 兼顾文件识别、修改态、预览态、置顶态 |
| **Panel Tabs** | 支持标签/图标切换、位置切换、对齐切换 |
| **Status Bar Items** | 左右对齐、优先级排序、支持 hover 与扩展注入 |
| **Quick Pick** | 搜索、列表、最近历史与上下文命令统一入口 |

### 实施路线图

如果把 VSCode 的 UX 抽象成可复用参考，其优先级应是：

1. 先搭稳定工作台骨架
2. 再实现命令式入口
3. 再做编辑器组与辅助面板
4. 最后开放扩展、主题、图标和高级布局能力

## UX 一致性模式

### 按钮层级

| 层级 | 表现 |
|------|------|
| **一级入口** | 命令中心、Command Palette、主导航活动项 |
| **二级动作** | 标题栏工具栏、编辑器标题动作、面板标题动作 |
| **三级动作** | Hover、右键菜单、状态栏条目、溢出菜单 |

### 反馈模式

| 模式 | 用途 |
|------|------|
| **激活高亮** | 当前视图、当前面板、当前标签 |
| **徽标** | 未读、数量、异步状态 |
| **状态栏** | 持续性轻反馈 |
| **通知** | 需要用户注意的即时反馈 |
| **Problems / Output** | 深度诊断与过程结果 |

### 表单模式

VSCode 尽量避免传统长表单作为高频入口，更偏向：

- Quick Pick
- 设置搜索
- 行内编辑
- 右键上下文操作

这让配置行为也更接近“命令式工作流”。

### 导航模式

| 模式 | 说明 |
|------|------|
| **空间导航** | 活动栏、侧边栏、面板 |
| **搜索导航** | Command Palette、Quick Open |
| **文档导航** | 标签、分组、最近历史 |
| **上下文导航** | Breadcrumbs、标题、状态栏 |

### 空状态与加载状态

空状态通常保持简洁，不抢占工作台结构：

- 无编辑器时可显示 tips / watermark
- 空编辑器组仍保留边界与可聚焦语义
- 加载与运行过程更多通过状态栏、面板和通知表达

### 确认模式

VSCode 只在确有风险时加强确认：

- 数据丢失风险时关闭确认
- 其余多数动作通过可逆性或状态恢复解决，而非频繁弹窗

## 响应式设计与无障碍

### 响应式策略

VSCode 的“响应式”不是移动端适配，而是**桌面工作台缩放与裁剪**：

- 允许隐藏或折叠工作台区域
- 允许调整 Panel / Sidebar 位置
- 标题栏可在菜单、命令中心、布局控制之间切换密度

### 断点策略

可归纳为三档：

| 档位 | 策略 |
|------|------|
| **宽屏** | 全工作台展开，适合多分屏 |
| **中等宽度** | 保留核心区域，次要栏位可收起 |
| **紧凑宽度** | 强依赖命令面板与临时视图切换 |

### 无障碍策略

| 策略 | 表现 |
|------|------|
| **语义角色控制** | 不同部件使用不同 role，减少读屏噪声 |
| **焦点可见** | focus-visible 与键盘导航是系统级要求 |
| **高对比支持** | hcDark / hcLight tokens |
| **状态朗读优化** | 通过更克制的 aria-live 策略避免信息洪流 |
| **屏幕阅读器适配** | 提供专门优化配置与平台集成 |

### 测试策略

UX 层面适合验证：

- 键盘完整导航是否闭环
- 栏位隐藏/显示后是否仍可恢复定位
- 主题切换、图标切换是否仍保持识别性
- 扩展加入新视图后是否破坏主结构
- 读屏与高对比模式下是否仍可用

---

## 固定 UI / 混合 UI / 动态 UI 边界补充说明

| 层级 | 在 VSCode 中的表现 | 设计含义 |
|------|-------------------|----------|
| **固定 UI** | Workbench 外壳、主要 part 结构 | 作为长期稳定心智模型 |
| **混合 UI** | Sidebar、Panel、Editor Groups、Status Bar | 壳层稳定，内容可变 |
| **动态 UI** | 扩展视图、Webview Panel、主题与图标扩展 | 增长空间必须被容器化管理 |

### UX 铁律

1. 新能力优先进入既有容器，而不是新建主结构。
2. 高频交互优先支持命令式入口。
3. 编辑器永远保持中心地位。
4. 状态必须轻量可见，风险必须明确可知。
5. 可定制性不能破坏空间秩序。

## 分析依据

本总结主要依据以下源码事实形成：

- `workbench.ts` 定义了工作台主要 Part 结构
- `workbench.contribution.ts` 定义了布局控制、命令面板、菜单栏与 Zen Mode 等关键配置
- `quickaccess.ts` 体现了 Quick Access / Command Palette 的上下文与历史设计

- `editor.ts`、`editorPart.ts`、`editorGroupView.ts` 体现了多编辑器、多分屏、预览、置顶与恢复策略
- `theme.ts` 与 `themeExtensionPoints.ts` 体现了 token 化主题系统与多层主题扩展点
- `window.ts` 体现了关闭确认与窗口生命周期中的恢复保护
