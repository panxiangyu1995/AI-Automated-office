# UX Design Specification - AI-Automated-office

**Author:** Codex  
**Date:** 2026-03-25  
**Status:** Canonical UX Specification

## Executive Summary

### 项目愿景

**AI-Automated-office** 的 UX 不再沿用旧版“功能说明式”文档表达，而正式切换为**Workbench 驱动的产品体验模型**。

新模型的核心是：

- 固定平台壳层参考 VSCode Workbench
- AI 对话是一级入口，而不是附属组件
- 部门模块在固定壳层中运行，而不是各自发明页面框架
- 业务内容区根据企业差异做混合或动态渲染
- 平台治理、安全、权限、审计、配置统一采用固定 UI

**一句话定位：**
> *AI-Automated-office 是一个“以 VSCode 式工作台为固定壳层、以 AI 为第一入口、以部门业务内容动态渲染为核心”的企业级 AI ERP。*

### 目标用户

| 角色 | 场景 | 核心诉求 | UX 重点 |
|------|------|----------|---------|
| **财务人员** | OCR、台账、发票、回款 | 少录入、少对账错误、可追踪 | 业务工作台、文档视图、AI 纠偏 |
| **销售人员** | 客户、报价、合同、订单 | 快速推进商机，减少文书时间 | 列表壳、详情主体、模板化报价/合同 |
| **审批发起人与审批人** | 发起流程、批注、驳回、加签 | 清晰、可追溯、低学习成本 | 审批壳层固定，审批主体动态 |
| **仓储人员** | 出入库、盘点、预警 | 状态清晰、操作准确 | 列表壳、库位视图、动态表单 |
| **管理层** | 经营驾驶舱、预警、洞察 | 一眼看懂关键指标 | 固定驾驶舱壳 + 动态指标主体 |
| **平台管理员** | 用户、权限、模型、插件、审计 | 安全、统一、可治理 | 全固定 UI |
| **模板设计者 / 开发者** | 模板设计器、动态页面、编辑器扩展 | 结构清晰、边界明确 | 固定设计器壳 + 动态画布 |

### 核心功能模块

| 分类 | 模块 | 核心 UX 价值 |
|------|------|--------------|
| **固定工作台壳层** | TopBar、ActivityBar、Sidebar、Workbench、AI Chat Panel、StatusBar、Command Palette | 提供稳定空间语言 |
| **AI 一级入口** | AI Chat Panel、Quick Ask、命令式输入、建议动作 | 让“说出任务”成为主入口 |
| **部门模块容器** | 人事、审批、销售、财务、仓储、管理层、售后、招投标、市场宣传 | 用统一壳层承接部门差异 |
| **动态业务内容** | 表单、详情主体、图表、流程图、文档模板、业务卡片 | 支撑企业差异化 |
| **平台治理能力** | 权限、审计、MCP、插件、模型、租户、日志、同步 | 高一致性与高安全性 |
| **编辑器与模板系统** | 编辑器工作区、模板设计器、文档工作区 | 把动态 UI 变成可治理资产 |

### 关键设计挑战

| 挑战 | 说明 |
|------|------|
| **AI 与 ERP 的主入口冲突** | 既要有 AI 对话入口，又不能丢掉企业系统必需的结构化页面 |
| **部门差异化与平台一致性冲突** | 每个部门都不同，但不能让 UI 结构碎片化 |
| **固定 UI 与动态 UI 的边界必须清晰** | 否则权限、测试、审计、可用性都会失控 |
| **复杂功能下的零学习成本目标** | 面向普通办公用户，不能按开发工具门槛设计 |
| **多租户与权限治理约束强** | 平台侧页面必须可审计、可控、可配置 |
| **动态模板带来的可维护性风险** | 需要通过壳层、Schema、模板资产治理来收敛复杂度 |

### 设计机会

| 机会 | 说明 |
|------|------|
| **用 Workbench 壳层解决复杂系统导航问题** | 先固定壳层，再让内容生长 |
| **用 AI 减少传统 ERP 的表单摩擦** | 用户先表达意图，再进入结构化确认 |
| **用模板系统承接企业差异** | 差异放在内容区，不放在全局壳层 |
| **用固定 UI 做治理与安全** | 权限、审计、模型配置、插件配置统一纳入平台壳层 |
| **用混合 UI 控制迁移成本** | 外壳先固定，内容逐步动态化，而不是一次性全重构 |

## 核心用户体验

### 定义性体验

**定义性体验：** 用户在一个稳定的桌面工作台中，通过 AI 对话、导航栏或命令式搜索，进入部门容器页，在固定壳层中完成业务，并在动态内容区看到与自己部门、角色、企业配置相匹配的真实业务界面。

这一定义有五个直接含义：

- **Workbench 是固定壳层**
- **AI 是一级入口**
- **部门页面不得自建全局框架**
- **业务差异主要发生在内容区，不发生在平台壳层**
- **权限、治理、审计、设置永远采用固定 UI**

### 平台策略

| 维度 | 策略 |
|------|------|
| **主平台** | 桌面端优先 |
| **布局基线** | 类 VSCode Workbench |
| **交互主轴** | AI 对话 + 结构化工作台 |
| **移动端** | 不纳入当前 UX 主设计范围 |
| **状态持久化** | 保留布局状态、对话上下文、部门入口偏好、最近工作区 |
| **内容分层** | 固定 UI / 混合 UI / 动态 UI 三层并存 |

### 轻松交互

AI-Automated-office 的“轻松”不是删功能，而是重写路径：

- 从“先找模块、再找按钮”改为“先说任务、再看结构化确认”
- 从“每个部门一套导航”改为“统一工作台壳层 + 部门容器页”
- 从“所有内容写死”改为“固定壳层 + 动态业务主体”
- 从“设置分散”改为“平台治理页集中管理”

### 关键成功时刻

**成功时刻 1：** 用户第一次进入系统，不需要培训就能理解顶部栏、活动栏、左侧栏、中间工作区、右侧 AI 面板、底部状态栏分别做什么。

**成功时刻 2：** 用户只说一句“帮我生成报价单”或“我要提交报销”，系统能把他带到正确的部门容器页和正确的动态主体。

**成功时刻 3：** 审批、财务、销售等复杂模块虽然内容不同，但外壳一致，用户不会迷路。

**成功时刻 4：** 平台管理员进入用户、权限、模型、插件、审计等页面时，始终看到稳定、固定、可治理的后台结构。

**成功时刻 5：** 企业差异化需求通过模板、动态卡片、动态表单、动态图表完成，而不会破坏整个产品壳层一致性。

### 体验原则

| # | 原则 | 说明 |
|---|------|------|
| **1** | **固定壳层优先** | TopBar、ActivityBar、Sidebar、Workbench、AI Chat Panel、StatusBar 必须稳定 |
| **2** | **AI 即入口** | AI 对话必须能触发任务、导航、解释、纠偏 |
| **3** | **治理页不得动态化** | 权限、租户、审计、模型、MCP、插件等必须固定 UI |
| **4** | **业务差异只放内容区** | 部门差异化主要发生在表单、详情主体、图表和模板 |
| **5** | **先有壳，再有内容** | 所有模块先接入平台壳层，再扩展业务内容 |
| **6** | **零学习成本不等于零结构** | 界面可复杂，但结构必须稳定、可解释、可恢复 |
| **7** | **UI 占位不用模拟数据** | 占位状态只展示结构、规则与能力，不展示伪业务数据 |

## 期望情感响应

### 核心情感目标

| 情感 | 说明 | 设计含义 |
|------|------|----------|
| **被辅助** | AI 像业务助理，不是聊天玩具 | AI 建议、自动补全、纠偏、导航 |
| **可控** | 系统会做事，但不会越权替用户决定 | 透明状态、确认策略、可回退 |
| **专业** | 像企业主系统，而不是堆砌卡片的 SaaS 页面 | 稳定壳层、统一部件语言、明确状态体系 |
| **安心** | 权限、审批、审计、配置都可追踪 | 固定 UI 治理页 + 审计视图 |
| **高效** | 少跳转、少重复录入、少找入口 | AI 入口、命令式导航、模板复用 |

### 避免的负面情感

**核心负面情感：** 用户觉得系统像“很多业务页面拼起来的后台集合”，而不是一个统一的企业工作台。

**触发原因：**

- 各部门页面风格和结构不同
- 业务页面自带独立导航
- AI 面板是外挂，不进入主任务流
- 动态内容反客为主，侵蚀治理一致性

**设计对策：**

- 固定 UI 结构全面统一
- 动态渲染限定在明确内容边界内
- AI 面板与工作区建立标准交互协议
- 平台治理页全部固定化

### 确认策略

| 操作类型 | 确认策略 |
|----------|----------|
| **普通导航与查看** | 直接执行 |
| **结构化业务填写** | AI 先建议，用户确认后提交 |
| **审批、删除、导出、发起跨部门动作** | 明确二次确认 |
| **敏感配置变更** | 审计提示 + 明确确认 |
| **AI 自动执行** | 默认透明显示“做了什么、准备做什么、还差什么” |

### 成就反馈机制

| 反馈类型 | 示例 |
|----------|------|
| **时间节省** | “报销单已自动生成草稿，您只需确认 3 个字段” |
| **流程推进** | “报价单已生成并同步到审批流程” |
| **经营结果** | “本周回款率高于上周 12%” |
| **风险可见** | “库存预警已生成，建议补货” |
| **治理闭环** | “该配置变更已记录审计日志” |

### 情感旅程设计

| 阶段 | 期望情感 | 设计目标 |
|------|----------|----------|
| **首次进入** | 清晰、可信 | 立即理解工作台壳层 |
| **第一次向 AI 提需求** | 被理解、少操作 | AI 正确导航到业务场景 |
| **第一次完成表单 / 流程** | 省事、顺畅 | 少录入、少切页、少解释 |
| **遇到复杂审批或错误** | 可解释、可修复 | 错误中心、状态栏、AI 解释协同 |
| **长期使用** | 稳定、专业、像企业主系统 | 布局、配置、模块都沉淀为长期资产 |

### 情感设计原则

| # | 原则 | 说明 |
|---|------|------|
| **1** | **AI 要像助手，不像黑箱** | 所有 AI 动作都要可见、可解释 |
| **2** | **专业感来自秩序，不来自装饰** | 工作台结构优先于视觉花样 |
| **3** | **差异化只能长在被允许的位置** | 动态内容必须受壳层约束 |
| **4** | **治理体验必须比业务体验更稳定** | 因为它决定系统可信度 |

## UX 模式分析与灵感

### 灵感产品分析

AI-Automated-office 的新 UX 体系吸收三类产品模式：

- **VSCode**：稳定 Workbench、可停靠区域、命令式入口、统一壳层
- **企业 ERP**：结构化流程、权限治理、可审计、跨部门协作
- **AI Agent 产品**：对话驱动、任务解释、自动补全、工具调用透明化

### 可迁移的 UX 模式

| 模式 | 来源 | 在本项目中的应用 |
|------|------|------------------|
| **稳定工作台骨架** | VSCode | 固定平台壳层 |
| **命令式与导航式并存** | VSCode | AI 输入、Command Palette、活动栏协同 |
| **固定容器承载动态内容** | VSCode + 企业后台 | 部门容器页、工作台主体、详情主体 |
| **状态分层反馈** | VSCode | StatusBar、通知、错误中心、同步状态 |
| **治理页固定化** | 企业平台 | 权限、租户、审计、模型、插件、MCP |
| **模板驱动业务差异** | AI 产品 + 低代码平台 | 动态表单、模板设计器、业务模板 |

### 要避免的反模式

| 反模式 | 说明 | 本项目应对 |
|--------|------|------------|
| **每个部门一套后台框架** | 导致系统割裂 | 强制统一 Workbench 壳层 |
| **AI 只是聊天窗** | 无法真正承担主入口 | AI 必须能导航、填表、解释、触发流程 |
| **所有页面都做成动态** | 失去治理与可测性 | 固定 / 混合 / 动态 三层分治 |
| **治理页跟业务页同级任意生长** | 权限与审计风险失控 | 治理页必须固定 UI |
| **视觉统一但交互割裂** | 看起来像一个产品，用起来像多个系统 | 部件级模式统一：列表壳、详情壳、工作台壳 |

### 设计灵感策略

- 用 VSCode 解决“复杂系统的固定壳层”问题
- 用 AI 解决“ERP 的高摩擦入口”问题
- 用模板系统解决“企业差异化内容”问题
- 用矩阵化边界解决“哪些能动态、哪些不能动态”的治理问题

## 设计系统基础

### 设计系统选择

AI-Automated-office 采用：

- **固定壳层设计参考**：VSCode Workbench
- **组件实现体系**：Shadcn/ui
- **样式系统**：Tailwind CSS
- **图标系统**：Lucide React
- **技术栈约束**：Tauri + React + TypeScript

### 选择理由

| 选择 | 理由 |
|------|------|
| **VSCode Workbench 结构** | 适合复杂桌面系统，壳层稳定、扩展边界清晰 |
| **Shadcn/ui** | 可复制、可改造、适合平台级设计系统落地 |
| **Tailwind CSS** | 适合 token 化与高一致性维护 |
| **Lucide React** | 统一、专业、禁止 emoji 图标 |

### 实施方法

| 层级 | 说明 |
|------|------|
| **固定壳层层** | TopBar、ActivityBar、Sidebar、Workbench、AI Chat Panel、StatusBar |
| **页面壳层层** | 部门首页壳、列表壳、详情壳、审批壳、编辑器壳 |
| **动态主体层** | 表单主体、详情主体、图表主体、模板主体 |
| **AI 协议层** | AI 如何打开、填充、解释、回写工作区 |

### 定制化策略

定制化不再发生在全局壳层，而发生在三个层次：

1. **视觉定制**：主题色、品牌标识、图标映射
2. **工作台定制**：活动栏项、侧栏容器、右侧 AI 面板显示策略
3. **业务定制**：动态表单、动态详情、动态图表、模板资产

## 主题系统架构

### 设计目标

主题系统采用**颜色注册表 + CSS 变量**模式，参考 VSCode 主题架构设计，支持多主题切换、主题继承、颜色变换和用户自定义。

### 核心架构

```
颜色定义（TypeScript） → 注册到 ColorRegistry → 生成 CSS 变量（--ao-{id}） → 注入到 DOM
```

### 主题类型

| 类型 | 说明 | CSS 类名 |
|-----|------|---------|
| `light` | 亮色主题 | `.light` |
| `dark` | 暗色主题 | `.dark` |
| `hc` | 高对比度主题 | `.hc` |
| `system` | 跟随系统 | 动态切换 |

### 颜色标识符规范

采用 `{category}.{component}-{state}` 格式命名：

```
foreground          # 基础颜色
border             # 边框颜色
button.background  # 按钮背景
button.foreground # 按钮文字
button.hoverBackground
input.background
input.foreground
input.border
sidebar.background
sidebar.foreground
sidebar.border
activityBar.background
activityBar.foreground
activityBar.activeBorder
statusBar.background
statusBar.foreground
```

### 目录结构

```
src/theme/
├── index.ts                    # 统一导出
├── colorRegistry.ts             # 颜色注册表
├── colorTypes.ts               # 类型定义
├── colorUtils.ts               # 颜色变换工具
├── ThemeProvider.tsx           # React 主题 Provider
├── useTheme.ts                 # useTheme Hook
└── colors/
    ├── baseColors.ts           # 基础颜色定义
    └── componentColors.ts      # 组件颜色定义
```

### 颜色注册表

```typescript
// 颜色默认值（针对四种主题类型）
interface ColorDefaults {
  light: ColorValue | null
  dark: ColorValue | null
  hc: ColorValue | null
}

// 注册颜色
export function registerColor(
  id: ColorIdentifier,
  defaults: ColorDefaults,
  description: string
): ColorIdentifier

// 转换为 CSS 变量名
export function toCssVariableName(id: ColorIdentifier): string
// 示例: 'button.background' -> '--ao-button-background'

// 获取 CSS 变量
export function toCssVariable(id: ColorIdentifier): string
// 示例: 'button.background' -> 'var(--ao-button-background)'
```

### 颜色变换函数

| 函数 | 说明 | 示例 |
|-----|------|------|
| `darken(color, factor)` | 使颜色变暗 | `darken('#FFFFFF', 0.2)` |
| `lighten(color, factor)` | 使颜色变亮 | `lighten('#000000', 0.1)` |
| `transparent(color, factor)` | 调整透明度 | `transparent('#0078D4', 0.5)` |
| `mix(color1, color2, ratio)` | 混合两种颜色 | `mix('#000', '#FFF', 0.5)` |

### React 集成

```tsx
// ThemeProvider.tsx
export function ThemeProvider({ children }) {
  const [themeType, setThemeType] = useState<'light' | 'dark' | 'hc' | 'system'>('system')
  
  // 监听系统主题变化（仅 system 模式）
  // 动态加载主题 CSS 变量
  // 注入到 document.documentElement
  
  return (
    <ThemeContext.Provider value={{ themeType, setThemeType }}>
      {children}
    </ThemeContext.Provider>
  )
}

// 使用方式
const Button = styled.button`
  background: var(--ao-button-background);
  color: var(--ao-button-foreground);
  border: 1px solid var(--ao-border);
  &:hover { background: var(--ao-button-hoverBackground); }
`
```

### 主题切换机制

1. 用户选择主题类型（亮色/暗色/高对比度/跟随系统）
2. ThemeProvider 更新 document.documentElement 的 class
3. 颜色注册表根据主题类型解析对应颜色值
4. CSS 变量通过 `element.style.setProperty()` 动态注入
5. 无需刷新页面，实时生效

### 主题文件

预设主题存储为 JSON 文件，支持 `extends` 继承机制：

```json
{
  "$schema": "ai-office://schemas/color-theme",
  "name": "Dark Modern",
  "type": "dark",
  "extends": "./darkPlus.json",
  "colors": {
    "background": "#1F1F1E",
    "foreground": "#CCCCCC",
    "button.background": "#0078D4"
  }
}
```

## 核心交互定义

### 定义性体验

**定义性体验：** 用户通过左侧活动栏进入部门上下文，通过中间工作区完成结构化任务，通过右侧 AI 面板发起或修正任务，通过状态栏和通知系统获得持续反馈。

### 用户心智模型

新的心智模型定义为：

**租户 > 工作台壳层 > 部门容器 > 页面壳层 > 动态业务主体 > AI 协同动作**

更具体地说：

- **租户** 决定可见模块与权限
- **工作台壳层** 决定所有页面的固定结构
- **部门容器** 决定用户当前在哪个业务域
- **页面壳层** 决定列表、详情、审批、工作台等通用形态
- **动态业务主体** 决定字段、图表、模板、流程内容
- **AI 协同动作** 决定用户是否能用自然语言完成或修正任务

### 成功标准

| 标准 | 说明 |
|------|------|
| **固定 UI 一眼可识别** | 用户进入任意模块都能立刻定位结构 |
| **AI 能带用户到正确的内容区** | 不是只回答文本，而是驱动实际界面 |
| **治理页无动态歧义** | 权限、审计、配置永远稳定 |
| **业务差异落在动态主体层** | 壳层不被企业差异侵蚀 |
| **部门扩展不破坏结构** | 新模块接入不改变全局心智模型 |

### 交互模式分析

| 模式 | 表现 |
|------|------|
| **工作台导航** | ActivityBar + Sidebar 定位业务域 |
| **任务驱动导航** | AI 直接打开正确页面与正确内容 |
| **结构化确认** | AI 生成草稿后，用户在固定壳层中确认 |
| **状态反馈** | StatusBar、Toast、消息中心、错误中心 |
| **治理操作** | 固定后台页内完成配置、授权、审计 |

### 核心交互流程

**流程 1：一句话发起业务任务**

1. 用户在 AI Chat Panel 输入“帮我生成报价单”
2. 系统识别销售上下文
3. Workbench 切到销售模块容器页
4. 中间内容区打开“报价单页面壳”
5. 动态主体区加载对应企业模板
6. AI 预填字段并高亮待确认项
7. 用户确认后提交或继续修改

**流程 2：进入治理与配置**

1. 管理员通过活动栏或命令式搜索进入系统设置
2. 页面固定壳层保持一致
3. 用户在固定治理页完成模型、MCP、插件、权限等配置
4. 变更写入审计与状态反馈链路

**流程 3：审批中心处理动态单据**

1. 用户进入审批中心固定壳层
2. 审批列表、过滤、分页、操作栏保持统一
3. 打开单据后，审批动作区固定
4. 单据主体区按模板动态渲染
5. 通过、驳回、加签、转交都在固定交互规则中完成

**流程 4：模板设计器修改业务页面**

1. 设计者打开模板设计器固定壳层
2. 设计器提供固定画布区、图层区、属性区、预览区
3. 模板主体在画布中动态编辑
4. 保存后作为部门模板资产进入运行时

### 检查点与回滚交互

AI-Automated-office 保留“AI 过程可回退”的设计要求，但表现方式要与 Workbench 协同：

- 对话侧记录检查点
- 中间工作区记录动态内容状态
- 回滚操作在 AI 与内容区之间联动显示
- 用户应始终知道“回滚对话”“回滚文件/模板”“回滚业务草稿”分别影响什么

### 上下文压缩与关键事实提示

相较旧版设计，本项目的上下文压缩要落实到界面层：

- 右侧 AI Chat Panel 展示关键事实摘要
- 中间工作区高亮 AI 已理解的结构化字段
- 顶部或状态栏显示当前部门、当前任务、当前草稿状态
- AI 记住的关键事实只展示可操作内容，不展示长段冗余摘要

### 审核界面设计

平台级审核视图必须固定化，包含但不限于：

- 审计日志
- 权限变更记录
- 模型调用与成本视图
- MCP 服务状态
- 插件授权与变更记录
- 同步冲突与恢复记录

业务审核则采用“固定审核壳 + 动态审核主体”模式。

## 视觉设计基础

### 颜色系统

品牌仍以原项目约束为基础，固定壳层采用稳定、专业、桌面化的配色策略：

| 角色 | 颜色方向 | 用途 |
|------|----------|------|
| **品牌主色** | 深蓝系 `#1E3A5F` | 顶层品牌识别、关键强调 |
| **工作台中性色** | 深浅中性灰蓝 | TopBar、Sidebar、Workbench、StatusBar 背景体系 |
| **AI 强调色** | 主色衍生高亮 | AI 建议、待确认、引导反馈 |
| **成功色** | 绿色 | 已完成、已同步、审批通过 |
| **警告色** | 橙色 | 风险预警、库存不足、待确认 |
| **危险色** | 红色 | 驳回、错误、删除、权限风险 |

### 字体系统

字体策略强调桌面系统的长期可读性：

- UI 文本：清晰、稳定、信息密度适中
- 数据/状态文本：强调对齐与扫描效率
- AI 输出文本：避免“聊天气泡过度装饰”，更接近工作助手风格
- 文档与模板编辑区：依场景区分为普通阅读字体与等宽编辑字体

### 间距与布局

整体布局遵循类 VSCode 框架，但映射到本项目如下：

| 区域 | 角色 | 说明 |
|------|------|------|
| **TopBar** | 顶层菜单和布局控制 | 固定 |
| **ActivityBar** | 一级导航 | 固定，代表部门与平台域 |
| **Sidebar** | 二级导航和视图容器 | 固定外壳，内容可按模块变化 |
| **Workbench** | 主工作区 | 固定容器，内容支持混合/动态 |
| **AI Chat Panel** | AI 助手区 | 固定外壳，统一交互协议 |
| **StatusBar** | 全局状态反馈 | 固定 |
| **Bottom Panel（预留）** | 日志、诊断、预览、输出 | 固定容器，当前可按阶段启用 |

### 圆角与边框

视觉上应继续采用“专业工具化”方向：

- 以边框和层级分隔代替大面积装饰
- 圆角保持克制
- 避免营销站式大阴影与漂浮卡片语言
- 让企业工作台看起来像“系统”，不是“活动页”

### 无障碍考虑

- 固定壳层区域要有明确语义与键盘焦点路径
- AI 面板、对话输入、列表、分页、审批动作必须键盘可达
- 颜色不能单独承担状态表达
- 错误、提醒、成功反馈要同时提供文案与状态标识

## 设计方向决策

### 参考设计

固定 UI 采用以下参考映射：

| VSCode Workbench | AI-Automated-office |
|------------------|---------------------|
| Title Bar | TopBar |
| Activity Bar | ActivityBar |
| Side Bar | Sidebar |
| Editor / Main Area | Workbench |
| Auxiliary Bar | AI Chat Panel |
| Status Bar | StatusBar |
| Command Palette | Command Palette / Quick Ask |
| Panel | Bottom Panel（保留扩展位） |

### 选定布局方案

最终选定为：

**TopBar + ActivityBar + Sidebar + Workbench + AI Chat Panel + StatusBar**

这意味着：

- 固定壳层全面参考 VSCode 的稳定工作台逻辑
- 右侧 AI 面板取代通用辅助栏，成为本产品的 AI 一级入口
- 底部 Panel 保留为固定容器能力，但不强制所有页面使用
- 中间 Workbench 是部门内容的主要承载区

### 设计理由

| 决策 | 理由 |
|------|------|
| **固定壳层参考 VSCode** | 已验证适合复杂桌面工作台 |
| **右侧 AI 面板固定化** | AI 是产品核心能力，不应漂浮不定 |
| **中间内容区做分层动态化** | 承接企业差异，同时控制治理风险 |
| **治理页全部固定** | 安全、权限、审计必须强一致 |

## UX 一致性模式

### 按钮层级

|------|------|
| **一级动作** | 顶层导航、部门切换、AI 发起、提交、审批 |

### 反馈模式

| 模式 | 用途 |
|------|------|
| **字段内联反馈** | 字段校验、缺失提示、就地纠偏 |
| **StatusBar** | 持续状态反馈 |
| **Toast / Dialog** | 即时提醒与确认 |
| **消息中心** | 汇总型通知 |
| **Problems Center / Validation Center** | 聚合校验错误、同步冲突、待确认变更与诊断信息 |
| **AI 提示** | 任务解释、纠偏、下一步建议 |
| **审计提示** | 敏感操作和配置变更 |

### 表单模式

本项目表单不再是纯手工录入界面，而是：

- AI 预填
- 用户确认
- 动态字段渲染
- 审批流程联动

### 导航模式

| 模式 | 说明 |
|------|------|
| **Workbench 导航** | ActivityBar + Sidebar |
| **AI 导航** | AI 直接打开目标壳层与主体 |
| **命令导航** | Command Palette / Quick Ask |
| **快速访问导航** | Quick Open / Quick Pick / 最近工作上下文 |
| **流程导航** | 审批流、工作台待办、消息中心 |

### 空状态与加载状态

- 空状态展示结构和能力说明，不展示模拟业务数据
- 加载态强调“正在做什么”
- 动态主体加载时，页面壳层仍保持稳定

### 确认模式

- 敏感操作必须二次确认
- 配置变更必须审计可见
- AI 自动动作必须透明

### 工作台交互增强规范

#### 命令中心与快速访问

- Command Palette / Quick Ask 是固定壳层中的一级入口，不只是“查命令”，还要承担跨模块资产访问。
- Quick Open / Quick Pick 结果至少覆盖页面、命令、项目/工作区、模板、知识条目、消息会话、协作者与治理入口。
- 结果排序优先考虑当前工作区、最近使用和权限可达性，避免把长尾结果推到前面。
- 命令中心必须保留最近命令、最近页面与最近工作上下文历史，帮助用户快速回到上一个业务现场。

#### 分层反馈与问题中心

- 字段层错误优先在字段内联反馈中解决，不把所有错误都提升到全局弹窗。
- StatusBar 只承载轻量持续反馈，如当前工作区、同步状态、草稿状态、当前任务。
- Toast / Dialog 用于即时确认、短时成功反馈和高风险动作确认。
- 消息中心承载异步通知汇总，Problems Center / Validation Center 承载需要处理的阻塞项和诊断项。
- Problems Center 至少聚合校验错误、同步冲突、权限阻塞、待确认 staged change 与关键输出日志。

#### 工作场景恢复与本地历史

- 系统重启或异常退出后，应恢复上次打开的标签、分栏、筛选条件、AI 面板状态与草稿上下文。
- 文档、模板和动态表单草稿都应具备本地历史快照能力，支持按时间点对比与恢复。
- 本地历史恢复不能直接覆盖已发布正式版本，而应先呈现差异并等待用户确认。
- 恢复失败时要给出明确的可操作提示，而不是只显示“恢复失败”。

#### 布局预设、设置来源与受控扩展

- 工作台支持保存与切换布局预设，如专注模式、审批模式、起草模式、审计模式。
- 平台可以提供推荐布局与默认入口，但用户应能在权限范围内做个性化覆盖。
- 设置面板需要展示当前值的来源，例如平台默认、租户策略、部门策略、工作区/项目、用户偏好、会话/Sub-Agent 覆盖。
- 扩展能力只能通过 Sidebar 视图、Bottom Panel 标签、StatusBar 条目、Command Palette 命令、上下文菜单、编辑器类型和模板资产等受控贡献点进入工作台。
- 扩展不得直接改写 TopBar、ActivityBar 与 Workbench 核心壳层，避免固定空间语言失控。

## 响应式设计与无障碍

### 响应式策略

本项目的响应式重点不是移动端，而是桌面工作区可伸缩：

- 左侧栏可收起
- 右侧 AI 面板可切换显示状态
- 中间 Workbench 支持多类型内容容器
- 固定壳层在不同宽度下保持结构不变

### 断点策略

| 档位 | 策略 |
|------|------|
| **宽屏** | 左中右完整工作台 |
| **中屏** | 右侧 AI 面板可收起 |
| **窄屏桌面** | 优先保留 Workbench 与必要导航 |

### 无障碍策略

- 所有固定壳层区域必须键盘可达
- AI 输入区与审批动作区必须支持清晰焦点状态
- 颜色、图标、文本共同表达状态
- 高风险操作必须可被清楚识别

### 测试策略

- 固定壳层在所有模块中是否保持一致
- 动态主体是否始终被限制在正确边界内
- AI 是否能正确打开和填充目标页面
- 治理页是否无动态歧义
- 无业务数据时是否只展示结构与能力说明

### 侧边栏定位

**侧边栏是系统的 L2 级导航区域**，位于 ActivityBar（一级导航）右侧，负责承载当前活动域下的视图切换、二级导航和上下文筛选功能。

### 侧边栏实现要求

#### 必须遵守的规则

1. **侧边栏导航状态必须全局管理**
   - 使用 zustand store 统一管理 `settingsActiveCategory` 和 `settingsActiveSection`
   - 不可在页面组件内部维护独立的导航状态

2. **侧边栏内容不得嵌入到业务页面内部**
   - 设置页面的侧边栏必须使用系统级 Sidebar 组件
   - 业务页面不得自行实现内嵌导航边栏

3. **侧边栏在不同 ActivityBar 项下可呈现不同内容**
   - 通过 `activeActivityItem` 判断当前活动域
   - 渲染对应的侧边栏内容模式

4. **侧边栏宽度必须可调节**
   - 使用 ResizablePanel 组件支持拖拽调节
   - 宽度变化时不得影响 Workbench 区域内容

5. **侧边栏状态必须持久化**
   - 侧边栏展开/折叠状态保存到 localStorage
   - 页面刷新后恢复之前状态

#### 状态管理规范

```typescript
// uiStore.ts 中必须包含的状态
interface UIState {
  // ... 其他状态
  settingsActiveCategory: SettingsCategoryKey
  settingsActiveSection: SettingsSectionKey
  setSettingsActiveCategory: (category: SettingsCategoryKey) => void
  setSettingsActiveSection: (section: SettingsSectionKey) => void
}
```

#### 组件结构规范

```
Sidebar (系统侧边栏容器)
├── Header (标题 + 搜索)
├── ScrollArea (可滚动内容区)
│   ├── SettingsSidebarContent (设置中心内容)
│   │   ├── CategoryButton (分类按钮)
│   │   └── SubItemList (子项列表)
│   │       └── SubItemButton (子项按钮)
│   ├── ResourceSidebarContent (资源浏览内容)
│   └── AdminSidebarContent (管理后台内容)
```

| 能力治理页 | 能力列表、风险级别、建议包入口、看板框架 | 健康指标卡、失败模式分布、建议包内容 |

#### 交互原则

1. 审批通过、驳回、要求修改、发布、回滚等决定必须保留在人类可见且可操作的固定壳层内
2. 审批完成后，Workbench 应明确展示“任务已恢复 / 等待修订 / 已终止”等恢复结果，而不是静默继续运行
3. 文档必须显式展示来源类型、修订状态与当前是否处于 `staged_review`
4. Trace 必须分层展示：普通用户看摘要，管理员看审计链路，平台治理角色看 Span 级诊断
5. 改进建议引擎输出必须呈现为“建议包”，只能由管理员或授权人员在固定治理页中采纳

### 交互细节对齐

- **模型与提供商治理**：主输入区持续展示 Provider/Model/Variant/预算徽章，点击可展开 inline 选择器（含推荐模型、思考变体、预算说明），切换前需触发治理审批或审批备注弹窗，模型策略受租户/部门白名单限制 [参考 `cline` ChatTextArea.tsx:1538、`kilocode` prompt-input.tsx:1390]
- **上下文与命令注入**：Context Window 面板须展示 token/成本、来源、压缩阈值与业务对象注入按钮；`@document`/`@approval`/`@knowledge` 等命令只有在租户/权限允许时生效，Context Inspector 展示会话上下文分解、系统提示与原始消息供授权用户检阅 [参考 `cline` ContextWindowSummary.tsx:129、`kilocode` session-context-tab.tsx:183]
- **Clarification Dock**：Ask Question 工具固定在输入区上方，展示问题进度、选项按钮、自由输入、与 Mode/Action 建议链接，回答后才允许继续高风险写回、审批或 Sub-Agent 委派 [参考 `kilocode` QuestionDock.tsx:215、session-question-dock.tsx:13]

### 迁移建议

1. 不重做固定 UI：登录、设置、权限、插件治理、系统配置保持固定  
2. 优先改造 Workbench 为渲染宿主  
3. 优先将工作台主体、审批单主体、详情页主体切到动态渲染  
4. 先完成模板运行时，再大规模推进部门页面动态化  

### 结论

最可行的策略是：

**固定平台壳 + 混合业务页 + 动态业务内容区**

这同时满足：

- 平台一致性
- 企业差异化
- 权限可控
- 可测试
- 可治理

### UX 铁律

1. 固定 UI 必须参考 VSCode Workbench 壳层来设计。  
2. AI 面板是固定 UI，不允许做成任意漂浮插件。  
3. 平台治理页全部固定，不参与动态化。  
4. 动态化优先发生在业务主体，而不是页面框架。  
5. 新部门模块接入时，不得突破固定壳层。  
6. 任何动态页面都必须可回到统一的列表壳、详情壳、审批壳或工作台壳。  
7. 无业务数据时只展示结构和能力说明，不展示模拟数据。  
8. 审批恢复状态、文档修订状态和 Trace 摘要必须在用户工作流中可见。  
9. 深度 Trace、能力健康度和建议包采纳界面必须停留在固定治理页，不进入业务动态主体。
