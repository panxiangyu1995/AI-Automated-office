# Settings Page UX Reorganization Plan - AI-Automated-office

## 文档目标

本方案用于重新整理 AI-Automated-office 的设置页，使其符合 canonical UX 文档中“固定 Workbench 壳层 + 固定治理页 + 业务主体动态化”的方向。

本方案不直接定义业务功能新增，而是解决以下问题：

- 设置页入口过多、层级失控
- 一级导航把配置、监控、审计、调试、市场、知识库等内容全部并列
- 当前设置页更像“功能堆放区”，而不是“平台治理中心”
- 页面结构没有体现 VSCode 式工作台下的固定治理页面逻辑

## 现状诊断

当前设置页的主要问题来自两个层面。

### 1. 信息架构失控

现有实现把以下内容全部做成左侧一级入口并列展示：

- 通用、快捷键、Agent、更新
- 提示词调试
- Sub-Agent 管理、角色、工具、权限、模型、路由、执行监控
- 知识文档、问答检索、自动生成、条目管理、权限控制、质量评估
- SKILL / SOUL 解析
- Plugin 适配、ClawHub 市场、私有市场
- 资源安全、执行审计
- 连接器框架、连接器健康

这使得“设置页”失去稳定层级，只剩下一组平铺按钮。

### 2. 治理页与运行页混杂

当前一级列表混合了四类本应区分的对象：

- 个人偏好：布局、快捷键
- 平台配置：模型、MCP、插件、知识库、连接器
- 安全治理：权限、审计、资源安全
- 运行诊断：执行监控、健康检查、调试模式

这些对象的频率、风险等级、受众角色完全不同，不应同级展示。

### 3. 与 canonical UX 文档不一致

canonical UX 已明确：

- 设置页属于固定 UI
- 平台治理、安全、权限、审计、配置统一采用固定 UI
- 固定 UI 需要参考 VSCode Workbench 的稳定壳层
- 设置不应是“分散的功能堆叠”，而应是“平台治理页集中管理”

因此当前设置页不是视觉问题，而是结构问题。

## 设计定位

### 新定位

设置页不再被定义为“所有配置项的集合”，而被定义为：

> AI-Automated-office 的平台治理中心

它服务的不是单个功能，而是整个平台的治理闭环：

- 工作台偏好
- AI 核心配置
- Sub-Agent 与 Skill 编排
- 知识库与内容治理
- 集成与连接器管理
- 插件与资源市场
- 安全、权限、审计
- 系统、更新、同步、诊断

### 设计原则

1. 一级只保留少量稳定域，不暴露所有叶子配置
2. 配置、监控、审计、调试必须分层
3. 所有治理页面继续保持固定 UI
4. 运行监控型页面可以存在，但不应与高频配置同级
5. 设置首页要先回答“这里能管什么”，再进入具体页
6. 页面语言要像企业平台治理后台，而不是实验功能目录

## 新的信息架构

建议将设置页固定为 1 个首页 + 8 个一级域。

### 设置首页

用于承接“治理中心”的总览，不直接承载细配置。

首页应包含：

- 平台治理总览卡片
- 最近修改项
- 风险提醒与待处理事项
- 常用治理入口
- 搜索入口
- 审计与健康摘要

### 一级域 1：工作台与个人偏好

面向个人使用体验与固定壳层偏好。

包含：

- 布局显示
- 快捷键
- 通知偏好
- 个人工作区偏好

- `general`
- `shortcuts`

- 叶子页面不再直接占用一级导航

## 页面结构建议

设置页应采用固定治理页壳层，而不是“左边按钮 + 右边内容”的纯切页式堆叠。

### 推荐结构

#### 顶部页头

包含：

- 页面标题
- 当前域说明
- 全局搜索框
- 最近修改提示
- 保存状态 / 未保存状态

#### 左侧治理导航

只展示一级域，支持：

- 当前域高亮
- 域级数量徽标或风险点
- 最近访问
- 收藏入口

#### 中央主工作区

按“首页总览 -> 二级列表 -> 具体配置表单”的节奏展开。

建议模式：

- 一级域首页使用概览卡片
- 二级页使用 Tab 或 Section Nav
- 具体配置使用统一表单卡片与说明区

#### 右侧上下文辅助区

不是必须常驻，但建议预留。

可承载：

- AI 解释当前设置项的作用
- 风险提示
- 依赖关系说明
- 审计影响提示
- 推荐值或最佳实践

这比把所有说明文案都塞进主表单更符合 AI-Automated-office 的产品定位。

## 交互规范建议

### 1. 首页先于详情

每个一级域先展示“这个域能管理什么”，再进入具体配置，不直接打开一张超长表单。

### 2. 低风险配置与高风险治理分离

例如：

- 快捷键、布局显示属于低风险
- 工具权限、资源安全、审计导出属于高风险

高风险操作必须：

- 有明确的风险说明
- 有审计提示
- 必要时二次确认

### 3. 监控页与配置页分离

配置回答“如何设”，监控回答“现在怎样”，审计回答“发生过什么”。

这三类内容可以属于同一个一级域，但不能同级平铺。

### 4. 调试能力下沉

`PromptDebugMode`、执行监控、健康检查这类开发或治理辅助能力，不应留在一级入口，应收敛到“系统、更新与诊断”。

### 5. 搜索优先于记忆

设置项多是事实，因此应增强搜索而不是逼用户记住入口路径。

建议支持：

- 按名称搜索
- 按域搜索
- 按风险级别搜索
- 按角色过滤

## 视觉与布局方向

### 视觉基调

设置页必须体现“企业平台治理中心”的专业感，而不是“实验功能目录”的工具感。

建议：

- 保持 Workbench 背景层级和固定壳层一致
- 内容区采用高密度但高秩序的信息编排
- 一级域使用清晰的标题、说明与状态标识
- 卡片和表单遵循统一宽度、间距和标题层级

### 与 canonical UX 的一致性

- 继续运行在固定 `Workbench` 容器中
- 设置页作为固定 UI 的治理页，不进入动态化
- 允许局部使用概览卡片、状态摘要、健康条，但不让内容区失去结构

## 分阶段迁移建议

### Phase 1：信息架构收敛

目标：

- 先减少一级入口数量
- 保持现有组件可复用
- 不急于重写每个配置组件

动作：

- 把 `SettingsPanel.tsx` 从“一级项平铺”改成“一级域 + 二级内容”
- 先建立 settings registry
- 把现有组件重新挂载到新分组下

### Phase 2：治理页壳层统一

目标：

- 建立统一页头、说明、搜索、状态反馈
- 统一卡片、表单、空态、风险提示样式

动作：

- 给所有二级页补统一 Header
- 区分配置页、监控页、审计页
- 建立统一的保存反馈和脏状态提示

### Phase 3：治理能力增强

目标：

- 让设置页具备真正的平台治理体验

动作：

- 加入设置搜索
- 加入最近修改记录
- 加入常用项收藏
- 加入风险摘要与健康摘要
- 和审计链路联动，展示“最后修改人 / 修改时间 / 审计入口”

---

## 最终结论

设置页接下来不应该继续“往左边列表里加按钮”，而应该做三件事：

1. 把设置页重新定义为平台治理中心
2. 把二十多个一级杂项收敛为少量稳定治理域
3. 把配置、监控、审计、调试重新分层

如果后续按本方案实施，设置页将从“功能堆放区”转变为：

- 结构稳定
- 角色清晰
- 风险可控
- 与 Workbench 壳层一致
- 与 canonical UX 文档一致

---

## 直接落地建议

第一步不要重做所有设置子组件，优先做以下最小改造：

1. 保留现有设置能力组件
2. 拆掉当前一级平铺导航
3. 新建“设置首页 + 8 个一级域”
4. 将现有项按本方案重新挂载
5. 将调试与监控类入口从一级导航移除

这会立刻改善设置页的秩序感，并为后续 UI 统一和功能扩展留出结构空间。
