# AI Agent 提示词设计模式总结

## 概述

基于对 OpenCode 和 OpenClaw 两个项目的深入分析，本文档总结了可复用的 AI Agent 提示词设计模式。

## 核心设计模式

### 模式 1: 分层知识架构

**问题**: 如何组织项目知识，使其既能全面覆盖又不过度占用上下文？

**解决方案**: 采用分层架构，按作用域组织知识。

```
┌─────────────────────────────────────────────────────────┐
│ 项目级 (AGENTS.md @ root)                                │
│ - 项目规范、编码风格、工作流程                             │
│ - 始终加载                                                │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 模块级 (AGENTS.md @ module)                              │
│ - 模块特定知识、技术细节                                   │
│ - 访问模块时加载                                          │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 任务级 (Agent/Command/Prompt)                            │
│ - 特定任务指令、工作流                                     │
│ - 触发任务时加载                                          │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 技能级 (Skill)                                           │
│ - 可复用技能、工具集成                                     │
│ - 按需加载                                                │
└─────────────────────────────────────────────────────────┘
```

**实现要点**：
- 知识就近原则：将知识放在最相关的作用域
- 自动加载机制：根据访问路径自动加载父目录知识
- 避免重复：知识只在一个地方定义

### 模式 2: 元数据驱动配置

**问题**: 如何让提示词具备可配置性，支持不同模型、工具和执行模式？

**解决方案**: 使用 YAML Frontmatter 声明元数据。

```yaml
---
name: skill-name
description: "触发条件描述"
model: provider/model-name
mode: primary | subagent
tools:
  "*": false
  "tool-name": true
metadata:
  custom:
    key: value
---
```

**元数据字段规范**：

| 字段 | 必需 | 说明 |
|------|------|------|
| name | 是 | 标识符，用于引用 |
| description | 是 | 触发条件描述 |
| model | 否 | 指定使用的模型 |
| mode | 否 | 执行模式 |
| tools | 否 | 工具权限控制 |
| metadata | 否 | 自定义元数据 |

**设计原则**：
- 声明式配置优于命令式
- 配置与内容分离
- 支持继承和覆盖

### 模式 3: 渐进式上下文加载

**问题**: 如何在有限上下文窗口中提供足够信息？

**解决方案**: 实现三级渐进式加载。

```
Level 1: 元数据层
├── name + description
├── 始终加载 (~100词)
└── 用于触发判断

Level 2: 核心内容层
├── SKILL.md / Agent.md 主体
├── 触发时加载 (<5000词)
└── 核心工作流和指令

Level 3: 资源层
├── scripts/ references/ assets/
├── 按需加载
└── 详细文档和工具
```

**实现策略**：
1. **元数据精简**: description 控制在 1-2 句话
2. **核心内容聚焦**: 只包含必要的工作流和规则
3. **资源按需引用**: 通过文件引用而非内联

### 模式 4: 确定性规则设计

**问题**: 如何减少 AI 的歧义和猜测？

**解决方案**: 为 AI 提供明确的判断规则。

**规则设计模板**：

```markdown
## 标签规则

### [标签名]
**触发条件**:
- 条件1
- 条件2

**排除条件**:
- 排除条件1
- 排除条件2

**示例**:
- ✅ 正确示例
- ❌ 错误示例
```

**规则设计原则**：

1. **明确边界**
```markdown
**Only** add if it's likely a RAM or CPU issue.
**Do not** add for LLM slowness.
```

2. **优先级声明**
```markdown
Determinism rules:
- If title + body does not contain "zen", do not add the "zen" label
- If "nix" label is added but title + body does not mention nix, drop it
```

3. **验证矩阵**
```markdown
| Field | Evidence |
|-------|----------|
| Claimed problem | ... |
| Evidence observed | ... |
| Root cause location | ... |
```

### 模式 5: 工具隔离与权限控制

**问题**: 如何确保 Agent 只能访问必要的工具？

**解决方案**: 实现工具权限控制机制。

**权限控制模式**：

```yaml
# 禁用所有工具，只启用特定工具
tools:
  "*": false
  "github-triage": true
  "github-pr-search": true
```

```yaml
# 启用所有工具，禁用特定工具
tools:
  "*": true
  "dangerous-tool": false
```

**文件权限控制**：

```jsonc
{
  "permission": {
    "edit": {
      "packages/opencode/migration/*": "deny",
      "packages/*/test/*": "require-approval"
    }
  }
}
```

### 模式 6: 知识累积机制

**问题**: 如何让 AI 从会话中学习并持久化知识？

**解决方案**: 实现自动知识提取和存储机制。

**知识提取流程**：

```
会话结束
    ↓
分析会话内容
    ↓
提取非显而易见的学习
    ↓
确定作用域（项目/模块/功能）
    ↓
更新对应层级的 AGENTS.md
    ↓
保持条目简洁（1-3行）
```

**知识分类**：

| 类型 | 示例 | 存放位置 |
|------|------|----------|
| 隐藏关系 | 模块A依赖模块B的非 obvious 路径 | 模块级 AGENTS.md |
| 配置陷阱 | 环境变量必须设置才能工作 | 项目级 AGENTS.md |
| 调试突破 | 错误信息误导，实际原因在别处 | 相关模块 AGENTS.md |
| API 怪癖 | 某API在特定条件下行为异常 | 功能级 AGENTS.md |

**排除内容**：
- 文档中已有的明显事实
- 标准语言/框架行为
- 已存在于 AGENTS.md 的内容
- 会话特定细节

### 模式 7: 安全护栏设计

**问题**: 如何防止 AI 执行危险或不当操作？

**解决方案**: 多层安全护栏。

**第一层: 禁止清单**

```markdown
## 禁止事项

- Agents MUST NOT modify baseline, inventory, ignore, snapshot files
- Never commit or publish real phone numbers, videos, or live configuration values
- Never update the Carbon dependency
- Do not edit files covered by security-focused CODEOWNERS rules
```

**第二层: 权限配置**

```jsonc
{
  "permission": {
    "edit": {
      "sensitive/*": "deny",
      "config/*": "require-approval"
    }
  }
}
```

**第三层: 真实性验证**

```markdown
## Hallucination Red Flags (treat as BLOCKER)

- claimed behavior not present in repo
- issue says "fixes #..." but changed files do not touch implicated path
- only docs/comments changed for a runtime bug claim
- vague AI-generated rationale without concrete evidence
```

### 模式 8: 工具调用标准化

**问题**: 如何让 AI 的工具调用格式统一且易于解析？

**解决方案**: 使用 JSON 格式标准化工具调用。

**标准格式**：

```json
{
  "action": "action-name",
  "param1": "value1",
  "param2": "value2"
}
```

**动作分组设计**：

```markdown
| Action group | Default | Notes                  |
| ------------ | ------- | ---------------------- |
| reactions    | enabled | React + list reactions |
| messages     | enabled | Read/send/edit/delete  |
| pins         | enabled | Pin/unpin/list         |
```

**示例**：

```json
// 发送消息
{
  "action": "sendMessage",
  "to": "channel:C123",
  "content": "Hello"
}

// 添加反应
{
  "action": "react",
  "channelId": "C123",
  "messageId": "1712023032.1234",
  "emoji": "✅"
}
```

### 模式 9: Skill 自由度设计

**问题**: 如何根据任务特性设置合适的约束程度？

**解决方案**: 根据任务脆弱性和变化性设置自由度。

**自由度矩阵**：

| 自由度 | 任务特性 | 实现方式 | 示例 |
|--------|----------|----------|------|
| 高 | 多种方法有效，决策依赖上下文 | 文本指令 | 代码审查建议 |
| 中 | 存在首选模式，允许变化 | 伪代码/参数化脚本 | API 调用模式 |
| 低 | 操作脆弱，一致性关键 | 具体脚本 | 数据库迁移 |

**设计原则**：
> 把 AI 想象成在探索路径：悬崖边的窄桥需要具体护栏（低自由度），
> 而开阔的田野允许多条路线（高自由度）。

### 模式 10: 明确边界声明

**问题**: 如何让 AI 明确知道何时使用/不使用某个能力？

**解决方案**: 使用 USE/DON'T USE 清单。

**模板**：

```markdown
## When to Use

✅ **USE this skill when:**
- 条件1
- 条件2
- 条件3

## When NOT to Use

❌ **DON'T use this skill when:**
- 排除条件1 → 使用替代方案1
- 排除条件2 → 使用替代方案2
```

**示例**：

```markdown
✅ **USE this skill when:**
- Checking PR status, reviews, or merge readiness
- Viewing CI/workflow run status and logs
- Creating, closing, or commenting on issues

❌ **DON'T use this skill when:**
- Local git operations → use `git` directly
- Non-GitHub repos → different CLIs
- Cloning repositories → use `git clone`
```

## 模式组合应用

### 场景 1: 创建新 Agent

```
1. 应用模式2 (元数据驱动) - 定义 frontmatter
2. 应用模式4 (确定性规则) - 编写判断规则
3. 应用模式5 (工具隔离) - 配置工具权限
4. 应用模式10 (明确边界) - 定义触发条件
```

### 场景 2: 创建新 Skill

```
1. 应用模式3 (渐进式加载) - 设计三级内容
2. 应用模式9 (自由度设计) - 确定约束程度
3. 应用模式8 (工具调用) - 标准化接口
4. 应用模式10 (明确边界) - 定义使用场景
```

### 场景 3: 知识管理

```
1. 应用模式1 (分层架构) - 确定存放位置
2. 应用模式6 (知识累积) - 提取和存储学习
3. 应用模式7 (安全护栏) - 添加必要约束
```

## 反模式警示

### 反模式 1: 过度解释

❌ **错误做法**：
```markdown
这个工具用于处理 GitHub 相关的操作。GitHub 是一个代码托管平台，
你可以使用它来管理代码仓库、提交 Pull Request、管理 Issues 等。
当你需要查看 PR 状态时，可以使用这个工具...
```

✅ **正确做法**：
```markdown
GitHub operations via `gh` CLI: issues, PRs, CI runs.
Use when: (1) checking PR status, (2) viewing CI, (3) creating issues.
```

### 反模式 2: 模糊触发条件

❌ **错误做法**：
```markdown
Use this skill when appropriate.
```

✅ **正确做法**：
```markdown
✅ USE when: checking PR status, viewing CI logs, creating issues
❌ DON'T USE when: local git ops → use git directly
```

### 反模式 3: 内联大量资源

❌ **错误做法**：
```markdown
## API Reference

[完整的 API 文档，数千行...]
```

✅ **正确做法**：
```markdown
## API Reference

See [REFERENCE.md](references/REFERENCE.md) for complete API documentation.
```

### 反模式 4: 缺乏安全约束

❌ **错误做法**：
```markdown
You can edit any file in the project.
```

✅ **正确做法**：
```markdown
## File Permissions

- Allowed: src/**, docs/**
- Denied: .env*, secrets/**
- Require approval: config/**
```

## 总结

这些设计模式相互关联，共同构成了一个完整的 AI Agent 提示词设计体系：

1. **架构层面**: 分层知识架构 + 渐进式加载
2. **配置层面**: 元数据驱动 + 工具隔离
3. **内容层面**: 确定性规则 + 明确边界
4. **安全层面**: 安全护栏 + 权限控制
5. **演进层面**: 知识累积 + 自由度设计

在实际应用中，应根据具体需求选择和组合这些模式，避免过度设计或设计不足。
