## 1. 想达到什么目的和效果

### 1.1 核心目标

让 Agent 在用户每次对话开始时**主动感知未读消息**，并通过**系统通知**告知用户。

### 1.2 预期效果

```
用户打开 Agent 对话窗口
    ↓
Agent 自动检查未读消息
    ↓
有未读 → 系统通知弹出 + 显示消息摘要
    ↓
用户点击通知 → 向 Agent 描述需求
    ↓
Agent 调用 ao-cli 获取消息详情
```

### 1.3 三版本预期效果差异

| 版本 | 主动机制 | 通知方式 | Agent 触发 |
|------|---------|---------|-----------|
| **简化版** | ❌ 无 | 系统通知 + 标记文件 | 用户看到通知后转述 |
| **进阶版** | ❌ 无 | 系统通知 + 标记文件 + OpenClaw Hook | 用户看到通知后转述，或 Hook 自动触发 |
| **OpenClaw** | ✅ 有 | 系统通知 + 标记文件 + OpenClaw Hook | OpenClaw 自动处理 |

## 2. 问题点

### 2.1 原有架构问题

**当前 CLI 轮询机制** (`/cli/cmd/poll.go`):
- CLI 每 60 秒轮询一次消息
- 有消息时 `fmt.Println` 输出到 stdout
- **Agent 无法感知**：大多数 Agent（Claude Code、Codex 等）没有主动轮询机制

### 2.2 问题根因

```
┌─────────────────────────────────────────────────────────┐
│  原架构: CLI 轮询 → stdout 输出 → 等待 Agent 解析       │
│                    ↓                                    │
│         大多数 Agent 没有主动解析 stdout 的能力          │
└─────────────────────────────────────────────────────────┘
```

### 2.3 Agent 类型限制

| Agent 类型 | 主动机制 | 被动机制 | 消息处理能力 |
|-----------|---------|---------|-------------|
| OpenClaw | ✅ 有 | ✅ | 可以主动轮询 |
| Claude Code | ❌ 无 | ✅ | 只能响应用户输入 |
| Codex | ❌ 无 | ✅ | 只能响应用户输入 |
| 其他 AI 对话助手 | ❌ 无 | ✅ | 只能响应用户输入 |

## 5. 设计的方案

### 5.1 整体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                    三版本兼容通知架构                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  [消息产生] → [API存储] → [CLI轮询]                              │
│                                     │                            │
│                    ┌────────────────┼────────────────┐          │
│                    ▼                ▼                ▼          │
│             [系统通知]      [标记文件]       [OpenClaw Hook]     │
│                 │                │                │             │
│                 ▼                ▼                ▼             │
│            [用户看到]     [.new_messages]    [Agent自动处理]     │
│                 │                │                │             │
│                 └────────────────┼────────────────┘             │
│                                  ▼                               │
│                         [用户/Agent 获取消息]                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 消息状态机

```
[未读] → 获取列表 → [已通知] → 查看详情 → [已读]
   │                        │
   └──── 用户主动标记 ───────┘
```

### 5.3 已读时机策略（混合模式）

| 消息类型 | 示例 | 获取列表时 | 查看详情时 |
|---------|------|----------|-----------|
| `announcement` | 系统公告 | ✅ 自动已读 | - |
| `notification` | 任务通知 | ✅ 自动已读 | - |
| `reminder` | 提醒 | ✅ 自动已读 | - |
| `message` | 私信 | ❌ | ✅ 手动已读 |
| `approval` | 审批 | ❌ | ✅ 手动已读 |

### 5.4 完整对话流程

```
用户向 Agent 发起对话
    │
    ▼
[Agent 前置 Hook: message_unread_check]
    │
    ├── 有未读消息 → 发送系统通知 → 显示消息摘要
    │
    └── 无未读 → 继续正常对话流程

用户: "帮我看看新消息"
    │
    ▼
Agent: ao-cli skill execute message_list
    │
    ├── 公告/通知/提醒 → 自动标记已读
    │
    └── 私信/审批 → 返回列表，等待用户选择

用户: "看看第一条的详细内容"
    │
    ▼
Agent: ao-cli skill execute message_detail --id xxx
    │
    └── 标记消息为已读
```

### 5.5 备选方案

| 方案 | 描述 | 缺点 |
|------|------|------|
| **A. 仅系统通知** | CLI 获取消息后只发系统通知 | Agent 不知道用户看了什么 |
| **B. WebSocket 推送** | 服务端主动推送消息到 Agent | 改动大，需要 Agent 支持 WebSocket |
| **C. 文件标记 + Agent 轮询** | 写标记文件，Agent 定期检查 | 依赖 Agent 主动轮询，不可靠 |
| **D. SSE (Server-Sent Events)** | 服务端推送，CLI 转发 | 同 WebSocket，需要 Agent 支持 |

**最终选择方案 A（系统通知）+ 前置 Hook**，原因：
- 实现简单，无外部依赖
- 三版本通用
- 用户体验好
- 不依赖 Agent 主动机制

## 10. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
