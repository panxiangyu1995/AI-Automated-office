## 1. 目的与效果

### 1.1 核心目标

让 Agent 在用户每次对话开始时**主动感知未读消息**，并通过**系统通知**告知用户。

### 1.2 预期效果

```
用户打开 Agent 对话窗口
    ↓
Desktop/CLI 自动检查未读消息
    ↓
有未读 → 系统通知弹出 + 显示消息摘要
    ↓
用户点击通知 → 向 Agent 描述需求
    ↓
Agent 调用 ao-cli 获取消息详情
```

### 1.3 三版本预期效果差异

| 版本 | 触发方式 | 通知方式 | Agent 触发 |
|------|---------|---------|-----------|
| **简化版** | 对话开始前自动 | 系统通知 + 标记文件 | 用户看到通知后转述 |
| **进阶版** | 对话开始前自动 | 系统通知 + 标记文件 + OpenClaw Hook | 用户看到通知后转述，或 Hook 自动触发 |
| **OpenClaw** | 对话开始前自动 | 系统通知 + 标记文件 + OpenClaw Hook | OpenClaw 自动处理 |

## 2. 问题点

### 2.1 原有架构问题

**当前 CLI 轮询机制** (`/cli/cmd/poll.go`):
- CLI 每 60 秒轮询一次消息
- 有消息时 `fmt.Println` 输出到 stdout
- **Agent 无法感知**：大多数 Agent（Claude Code、Codex 等）没有主动轮询机制

### 2.2 问题根因

```
┌─────────────────────────────────────────────────────────┐
│  原架构: CLI 轮询 → stdout 输出 → 等待 Agent 解析       │
│                    ↓                                    │
│         大多数 Agent 没有主动解析 stdout 的能力          │
└─────────────────────────────────────────────────────────┘
```

### 2.3 Agent 类型限制

| Agent 类型 | 主动机制 | 被动机制 | 消息处理能力 |
|-----------|---------|---------|-------------|
| OpenClaw | ✅ 有 | ✅ | 可以主动轮询 |
| Claude Code | ❌ 无 | ✅ | 只能响应用户输入 |
| Codex | ❌ 无 | ✅ | 只能响应用户输入 |
| 其他 AI 对话助手 | ❌ 无 | ✅ | 只能响应用户输入 |

## 4. 设计的方案（修正版）

### 4.1 整体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                    三版本兼容通知架构                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  [消息产生] → [API存储] → [CLI轮询 / Desktop 自动检查]           │
│                                     │                            │
│                    ┌────────────────┼────────────────┐          │
│                    ▼                ▼                ▼          │
│             [系统通知]      [标记文件]       [OpenClaw Hook]     │
│                 │                │                │             │
│                 ▼                ▼                ▼             │
│            [用户看到]     [.new_messages]    [Agent自动处理]     │
│                 │                │                │             │
│                 └────────────────┼────────────────┘             │
│                                  ▼                               │
│                         [用户/Agent 获取消息]                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 消息状态机

```
[未读] → 对话开始 → [已通知] → 查看详情 → [已读]
   │                    │
   └──── 用户主动标记 ───┘
```

### 4.3 消息已读时机策略（混合模式）

| 消息类型 | 示例 | 对话开始时 | 查看详情时 |
|---------|------|----------|-----------|
| `announcement` | 系统公告 | ✅ 自动已读 | - |
| `notification` | 任务通知 | ✅ 自动已读 | - |
| `reminder` | 提醒 | ✅ 自动已读 | - |
| `message` | 私信 | ❌ | ✅ 手动已读 |
| `approval` | 审批 | ❌ | ✅ 手动已读 |

### 4.4 完整对话流程

```
用户打开 Desktop/CLI 对话窗口
    │
    ▼
[对话开始前 Hook: 自动调用未读检查]
    │
    ├── 有未读消息 → 发送系统通知 → 显示消息摘要
    │
    └── 无未读 → 继续正常对话流程

用户: "帮我看看新消息"
    │
    ▼
Agent: ao-cli skill execute message_list
    │
    ├── 公告/通知/提醒 → 自动标记已读
    │
    └── 私信/审批 → 返回列表，等待用户选择

用户: "看看第一条的详细内容"
    │
    ▼
Agent: ao-cli skill execute message_detail --id xxx
    │
    └── 标记消息为已读
```

### 6.5 Desktop 端对话开始前检查（TypeScript）

```typescript
// /desktop/src/renderer/index.tsx
// 在 App 组件的 onMount 中调用

onMount(() => {
    // 对话开始前自动检查未读消息
    const checkMessages = async () => {
        try {
            const result = await window.api.messageCheck()
            if (result.hasUnread) {
                await window.api.messageNotify(
                    `您有 ${result.unreadCount} 条未读消息`,
                    result.messages.slice(0, 3).map(m => m.title).join(', ')
                )
            }
        } catch (error) {
            console.error('消息检查失败:', error)
        }
    }

    checkMessages()
})
```

## 9. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| macOS `osascript` 权限 | 通知无法弹出 | 用户首次需授权通知权限 |
| Windows Toast 需要 App ID | 可能失败 | 回退到简陋提示框 |
| OpenClaw Hook 超时 | 阻塞轮询 | 5秒超时，独立 goroutine |
| Desktop 端消息检查失败 | 通知不弹出 | 降级到日志输出，不阻塞主流程 |
