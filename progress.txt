发现关键架构问题：

当前中间件执行顺序：

- 后续 API 调用被 TenantMiddleware 拦截，要求提供 tenant_id
- AuthMiddleware 无法在 TenantMiddleware 之前运行来获取 tenant_id

影响：
- 所有需要认证的 API 都无法正常调用
- 用户无法访问部门、消息等核心功能

**根因分析**：
- middleware/auth.go:84-86 会在 token 验证后从数据库获取 tenant_id
- 但 TenantMiddleware (middleware/tenant.go:38-42) 先于 AuthMiddleware 执行
- TenantMiddleware 要求请求必须包含 tenant_id（通过 X-Tenant-ID header、path 或 query）

**需要的修复**：
1. 方案A：调整中间件顺序，AuthMiddleware 在 TenantMiddleware 之前
2. 方案B：修改 TenantMiddleware，在 AuthMiddleware 之后从已认证用户获取 tenant_id
3. 方案C：登录响应中返回 tenant_id

### 发现并修复的问题（6 类）

1. **GORM Statement 状态泄漏（严重）**：connDB 共享实例链式调用间 WHERE/表名残留
   - 根因：`r.db.Where(...)` 链式调用在同一实例累积条件
   - 修复：所有 repo 增加 `fresh()` 方法（`r.db.Session(&gorm.Session{NewDB: true})`），
     查询统一用 `r.fresh()` 开头。涉及 44+ repo 文件（含 message_repo.go 单文件）
   - 症状：employee 创建时 FindByEmail 查成 departments 表

2. **GORM 软删除 UPDATE..FROM 重复（严重）**：`Delete(&model{})` 在有软删除字段时
   生成 `UPDATE x SET ... FROM x`（表名重复 SQLSTATE 42712）
   - 修复：所有 Delete 改为 `Model(&model.X{}).Where(...).UpdateColumn("deleted_at", time.Now())`
   - 附带修复：sed 批量替换产生的错误表名（backupconfigs/customertags 等）

3. **岗位更新 Save bug**：`r.db.Save(position)` 生成 UPDATE..FROM 重复
   - 修复：改为 `Model(&model.Position{}).Where(...).Updates(map)`

4. **operator 角色权限不足**：operator 只有只读+系统权限，无法管理业务
   - 修复：operator 获得全部权限（user/department/employee/customer/product/order/
     contract/finance/workflow + 系统权限），符合"全平台管理"定位
   - 同步更新 rbac_test.go 和 middleware/rbac_test.go

5. **skills 表归属矛盾**：schema_callback 将 skills 固定 public，但企业自定义 skill
   写入 tenant schema
   - 修复：从 publicTables 移除 skills/skill_role_openings/skill_parameters，
     SkillHandler 用 svcFor(c)（connDB，search_path 优先 tenant 回退 public）

6. **billing/quota raw SQL 不兼容 sqlite 测试**：`NOW()` 函数 sqlite 不支持
   - 修复：改为 GORM `Model().Where().Updates(map)` 模式（含 time.Now()）
   - 附带：workflow_service_test 的 "end" 断言更新（end=流程结束是正确语义）
