## Context

当前项目的 RAG（检索增强生成）架构位于 `src-tauri/src/knowledge/`，已实现：
- 基础文档解析器（TxtParser、MarkdownParser）
- 基础分块器（FixedSize、Sentence、Paragraph、Recursive）
- 文档处理 Pipeline（框架存在，未完整实现）
- 向量检索（Qdrant、SQLite-Vec）
- Context 构建器（基础 Prompt 生成）

**存在的主要问题**：

| 问题 | 影响 |
|------|------|
| 嵌入缓存缺失 | 每次检索都调用嵌入 API，成本高、延迟大 |
| 无全文检索 | 仅支持向量检索，无法处理关键词精确匹配 |
| 无重排序 | 检索结果直接返回，无法优化排序 |
| 元数据过滤缺失 | 无法按部门、标签、日期等过滤 |
| 分块策略简单 | 仅按字符数分块，无法保留语义完整性 |

**参考实现**：Dify 的 RAG 架构（`开源库参考项目/dify/api/core/rag/`）

## Goals / Non-Goals

**Goals:**
- 实现嵌入缓存系统，减少 60-80% 的 API 调用
- 实现混合检索（向量 + BM25），提升检索质量
- 实现元数据过滤，支持精细化检索控制
- 实现智能分块，保留文档语义结构
- 实现检索结果重排序，提升相关性

**Non-Goals:**
- 不实现多模态检索（图片/视频理解）
- 不实现知识图谱检索
- 不实现复杂的 QA 生成（LLM 生成问答对）
- 不实现外部知识库集成

## Decisions

### Decision 1: 嵌入缓存策略

**选择**：SQLite 本地缓存 + 可选 Redis 二级缓存

**理由**：
- SQLite 持久化，重启后缓存不丢失
- 简单可靠，无需额外服务依赖
- 适合桌面端场景（Tauri）
- 可扩展：未来可添加 Redis 作为分布式缓存

**替代方案**：
- 仅内存缓存：重启后丢失，不适合生产
- 仅 Redis：依赖额外服务，增加运维成本

### Decision 2: 混合检索算法

**选择**：Reciprocal Rank Fusion (RRF)

**理由**：
- Dify 采用此算法，效果验证
- 计算简单，O(n) 复杂度
- 无需训练，直接使用排名信息
- 参数 k 控制融合程度（默认 60）

**替代方案**：
- 加权评分：需要手动调参，效果不稳定
- Rerank 模型：效果好但计算成本高（可选支持）

### Decision 3: 元数据过滤 DSL

**选择**：JSON 结构化过滤条件

**理由**：
- 结构清晰，易于扩展
- 与 Qdrant Filter 格式兼容
- 支持序列化/反序列化
- 前端可方便构建过滤条件

**替代方案**：
- SQL 风格：表达能力更强但解析复杂
- GraphQL 过滤：过度设计

### Decision 4: 分块策略

**选择**：句子边界 + 重叠窗口

**理由**：
- 保留句子完整性，避免语义割裂
- 重叠窗口确保上下文连续性
- 实现复杂度适中
- 可配置重叠比例

**替代方案**：
- 递归字符分块：Dify 方案，但过于复杂
- 语义分块：需要额外嵌入模型，成本高

## Risks / Trade-offs

| Risk | Impact | Mitigation |
|------|--------|------------|
| 缓存占用磁盘空间 | 大文档场景可能积累大量缓存 | 添加 TTL 清理，定期压缩 |
| BM25 实现性能 | 大规模文档可能慢 | 分级索引，按文档数选择检索策略 |
| 内存占用 | 批量嵌入时内存峰值高 | 分批处理，控制并发 |
| 向量维度不匹配 | 不同嵌入模型维度不同 | 缓存键包含模型名称 |

## Migration Plan

**Phase 1: 嵌入缓存**
1. 创建 `embedding_cache` 数据库表
2. 实现缓存读写逻辑
3. 修改 `EmbeddingService` 集成缓存
4. 灰度验证：5% 流量使用缓存

**Phase 2: 混合检索**
1. 实现 BM25 算法
2. 实现 RRF 合并
3. 添加检索配置参数
4. 灰度验证：逐步增加混合检索比例

**Phase 3: 元数据过滤**
1. 定义过滤 DSL
2. 实现 Qdrant Filter 转换器
3. 修改检索 API
4. 全量上线

**Phase 4: 智能分块**
1. 实现句子分块器
2. 添加重叠窗口支持
3. 修改 Pipeline 集成
4. 仅对新文档生效

## Open Questions

1. **Redis 缓存层是否必要？**
   - 当前桌面端场景可能不需要
   - 建议：Phase 1 先不实现，后续按需添加

2. **Rerank 模型集成时机？**
   - 当前 MVP 可跳过
   - 建议：作为 Phase 5（未来）

3. **缓存大小限制？**
   - 需要配置最大缓存条目数
   - 建议：默认 10 万条，定期清理 LRU
