# Proposal: User Admin APIs

## Why (背景与动机)

Epic 2 的目标是构建完整的用户认证与部门权限系统。Story 2.2 负责用户管理工作台的云端 API 基础设施。当前系统缺少用户管理的后端支持，无法进行用户的增删改查和状态管理。

本变更将实现用户管理的核心 API，为后续的前端 UI 提供数据支撑。

## What Changes (变更内容)

### 新增功能
1. 用户列表分页查询 API
   - 支持按姓名、工号、部门、状态筛选
   - 返回用户基本信息、部门归属、角色信息
   
2. 用户详情查询 API
   - 返回完整用户档案
   - 包含权限摘要

3. 用户创建 API
   - 基本信息录入
   - 密码初始化策略
   - 部门/岗位/角色绑定

4. 用户更新 API
   - 基本信息修改
   - 部门/岗位/角色变更

5. 用户状态管理 API
   - 启用/停用用户
   - 强制重置密码

### 技术实现
- 在 Go 云端实现 RESTful API
- 遵循 ADR-005 多租户数据库级隔离
- 所有写操作写入审计日志

## Capabilities 影响

### 新增 Capabilities
- `admin-api`: 用户管理 API 服务

### 修改 Capabilities
- 无（新增能力，不修改现有功能）

## 影响范围

| 影响点 | 说明 |
|--------|------|
| Go 云端 API | 新增用户管理相关端点 |
| 数据库 | 使用现有 users 表，可能需要新增索引 |
| 审计系统 | 所有写操作需要记录审计日志 |
| 前端 | 本变更不涉及，由 E2-S2.2-02 实现 |

## 依赖分析

### 前置依赖
- **E2-S2.1-01**: 需要认证模块基础设施（用户表结构、认证中间件）

### 后续依赖
- **E2-S2.2-02**: User admin UI 依赖本变更提供的 API

## 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 用户数据量增长影响查询性能 | 中 | 实现分页、添加索引 |
| 并发更新冲突 | 低 | 使用乐观锁或版本控制 |
| 敏感信息泄露 | 高 | API 返回时过滤敏感字段 |

## 时间估算
- 设计与评审: 1 天
- 核心实现: 2-3 天
- 测试与修复: 1 天
- **总计**: 4-5 天
