## Why

Epic 2 用户认证与部门权限系统需要建立完整的三层权限模型。Story 2.5 定义基础权限、部门权限、审批权限三层模型，为整个系统的权限控制奠定数据基础。

根据 PRD 定义：
- **FR29**: 管理员可以按部门分配用户权限
- **FR30**: 系统支持部门权限模型（基础权限+部门权限+审批权限）

本 Story 解决以下问题：
1. 如何组织角色和权限的数据结构
2. 如何实现三层权限的分层管理
3. 如何支持按部门分配权限的业务需求

## Technical Decisions

### 权限命名规范
遵循 ADR-017，权限编码采用 `{module}_{resource}_{action}` 格式：
- `auth_user_read` - 查看用户信息
- `auth_user_write` - 编辑用户信息
- `hr_employee_read` - 查看员工信息
- `hr_employee_write` - 编辑员工信息

### 三层权限定义

| 层级 | 编码 | 适用范围 | 继承关系 |
|------|------|---------|---------|
| 基础权限 | base | 所有用户 | 无 |
| 部门权限 | department | 部门内用户 | 可继承基础权限 |
| 审批权限 | approval | 有审批权限的用户 | 可继承部门权限 |

### 默认角色

| 角色名称 | 角色编码 | 层级 | 说明 |
|---------|---------|------|------|
| 超级管理员 | super_admin | base | 租户级最高权限 |
| 部门管理员 | dept_admin | department | 部门内管理权限 |
| 普通员工 | employee | base | 基础员工权限 |
| 审批人 | approver | approval | 审批流程权限 |

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
| 权限模型过于复杂 | 采用分层设计，简化权限理解成本 |
| 权限膨胀问题 | 控制默认权限数量，支持动态扩展 |
| 多租户隔离 | 所有权限数据按 tenant_id 隔离 |
| 性能问题 | 权限计算结果缓存，定期刷新 |

## Migration Plan

1. 创建数据库迁移脚本，建立权限相关表
2. 编写种子数据，初始化默认角色和权限
3. 开发权限计算服务的基础接口
4. 编写单元测试验证权限模型正确性
5. 与 E2-S2.5-02 权限中心 UI 集成验证
