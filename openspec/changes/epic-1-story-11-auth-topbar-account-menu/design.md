## Context

当前应用已具备登录与注册能力，但登录后在主界面缺少可见的账号管理入口。`AuthStore` 保存了用户与 token，`AuthGuard` 负责登录态保护，`TopBar` 为全局高频操作入口。为保证账号生命周期完整，需要在 TopBar 增加统一账号菜单，承载账户信息、切换账号与退出登录操作，并与现有路由守卫和状态管理保持一致。

## Goals / Non-Goals

**Goals:**
- 在 TopBar 新增账号图标按钮与下拉菜单，形成统一身份操作入口。
- 提供“查看账户信息”能力，展示当前账号的用户名、姓名、部门、角色等信息。
- 提供“切换账号”与“退出登录”动作，统一调用认证状态清理并跳转登录页。
- 在未登录场景下，账号入口可引导用户进入登录页。
- 保持现有登录/注册流程与路由守卫行为一致，不引入状态冲突。

**Non-Goals:**
- 不实现多账号并存会话管理。
- 不新增后端账户资料编辑接口。
- 不在本次变更中实现忘记密码完整流程。
- 不改造权限模型或租户模型。

## Decisions

### 1) 账号入口放置于 TopBar 并使用现有菜单组件体系
- 决策：在 `TopBar` 中新增账号图标按钮，复用项目既有菜单/弹层交互模式（Shadcn 组件栈）。
- 原因：TopBar 是所有页面可达的全局入口，用户心智最稳定；复用现有组件可减少一致性风险。
- 备选方案：
  - 放在侧边栏底部：可见性受折叠状态影响，跨页可达性不如 TopBar。
  - 放在独立设置页：路径更深，无法满足“快速切换/退出”的高频操作诉求。

### 2) 切换账号与退出登录统一复用 AuthStore 清理动作
- 决策：两种动作都先执行统一 `logout` 状态清理，再通过路由导航到 `/login`。
- 原因：最小化分支逻辑，避免 token/user 残留；与 `AuthGuard` 的未登录重定向机制天然一致。
- 备选方案：
  - 新增 `switchAccount` 独立状态：会与现有 `logout` 逻辑重复，增加维护成本。

### 3) 账户信息采用前端已持有用户态展示，不增加同步请求
- 决策：账户信息直接读取 `AuthStore.user` 并展示，缺失字段提供占位。
- 原因：信息已在登录响应中返回，避免新增 API 调用与错误链路。
- 备选方案：
  - 每次打开菜单请求 `get_current_user`：当前后端能力未完整，增加失败面且收益低。

### 4) 非登录态入口行为定义为“跳转登录”
- 决策：若 `isAuthenticated` 为 false，账号按钮触发后直接导航 `/login`。
- 原因：行为明确，避免出现“空菜单”或误导操作。
- 备选方案：
  - 弹出登录弹窗：需新增弹窗态管理，影响范围更大。

## Risks / Trade-offs

- [风险] TopBar 改动影响现有快捷操作布局 → [缓解] 使用最小视觉占位，复用现有 spacing/token，并补充回归测试。
- [风险] 退出后路由跳转与 Guard 重定向重复触发 → [缓解] 统一由业务动作显式导航，Guard 仅兜底。
- [风险] 用户信息字段缺失导致 UI 异常 → [缓解] 显示占位文案，避免直接渲染空值。
- [权衡] 选择前端本地展示而非实时拉取，信息可能非实时 → [缓解] 当前场景以会话内展示为主，可在后续 Story 引入刷新机制。
