# 持续产品迭代优化器

**核心理念：** 产品不是一次性做出来的，而是迭代出来的。本 skill 提供从"现状分析→差距识别→方向澄清→迭代执行→效果验证→下轮建议"的完整闭环，帮助产品持续进化。支持单轮和多轮自动迭代。

**与 prd-driven-iteration 的关键区别：**

| 维度 | prd-driven-iteration        | product-iterate（本skill）         |
| ---- | --------------------------- | ---------------------------------- |
| 视角 | 代码质量维度（6大维度扫描） | 产品目标维度（需求对齐+体验+价值） |
| 交互 | 分析后直接生成任务          | 主动询问用户澄清方向和优先级       |
| 输出 | task.json + OpenSpec变更    | 迭代报告 + 方向建议 + 执行计划     |
| 循环 | 单次执行                    | 持续迭代循环（每次给出下一轮建议） |
| 多轮 | 不支持                      | 支持N轮自动迭代                    |
| 重点 | 修复问题                    | 让产品变得更好                     |

## N轮自动迭代机制

### 指令格式识别

当用户输入包含轮数指定时，自动进入多轮迭代模式：

| 用户指令示例               | 解析结果                   |
| -------------------------- | -------------------------- |
| "帮我进行XX模块的10轮迭代" | 模块=XX, 轮数=10           |
| "对产品做5轮优化迭代"      | 模块=全局, 轮数=5          |
| "自动迭代3轮"              | 模块=全局, 轮数=3          |
| "迭代销售模块，8轮"        | 模块=销售, 轮数=8          |
| "持续迭代直到无法改善"     | 模块=全局, 轮数=自动(无限) |

### 多轮迭代执行流程

```
用户指定N轮迭代
     ↓
解析：模块范围 + 轮数N
     ↓
┌─ 第1轮 ────────────────────────────────────────────┐
│  Phase 1: 现状感知（首次完整分析）                    │
│  Phase 2: 差距识别（完整8维度评估）                  │
│  Phase 3: 方向澄清（询问用户，获取首轮方向）         │  ← 仅首轮完整询问
│  Phase 4: 迭代规划 → iteration.json → OpenSpec变更   │
│  Phase 5: 执行迭代（按OpenSpec变更实施）              │
│  Phase 6: 效果验证                                   │
│  Phase 7: 复盘建议 + 更新iteration.json              │
└───────────────────────────────────────────────────┘
     ↓
┌─ 第2轮~第N轮 ──────────────────────────────────────┐
│  Phase 1: 现状感知（增量分析，基于上轮变化）         │
│  Phase 2: 差距识别（更新评估，对比上轮）             │
│  Phase 3: 方向确认（本轮方向=上轮建议，仅确认）      │  ← 后续轮次自动确认
│  Phase 4: 迭代规划 → 更新iteration.json → OpenSpec   │
│  Phase 5: 执行迭代（按OpenSpec变更实施）              │
│  Phase 6: 效果验证                                   │
│  Phase 7: 复盘建议 + 更新iteration.json              │
└───────────────────────────────────────────────────┘
     ↓
第N轮完成后输出总结报告 + HTML报告
```

### 多轮迭代的关键规则

**首轮完整，后续精简：**

- 第1轮：完整执行所有7个Phase，包括方向澄清（Phase 3 询问用户）
- 第2~N轮：
  - Phase 1 增量分析（基于上轮变化，不重新分析全量）
  - Phase 2 更新评估（对比上轮分数，标注变化）
  - Phase 3 **方向确认而非询问** —— 使用上轮的"下一轮建议"作为本轮方向，仅输出确认信息
  - Phase 4-7 正常执行

**每轮输出精简报告：**
多轮迭代时，每轮的输出应精简，聚焦关键变化：

- 差距评分变化（与上轮对比）
- 本轮变更清单（3-5个变更）
- 验证结果
- 下一轮方向（1-3条）

**自动停止条件：**
在"直到无法改善"模式下，以下情况自动停止迭代：

- 所有8维度评分达到4分以上
- 连续2轮差距评分无改善（变化<0.5分）
- 用户手动中断

**阻塞处理：**
如果某轮迭代在执行阶段遇到阻塞：

- 记录阻塞信息到 `iteration-log.md`
- 跳过当前轮次，进入下一轮
- 在总结报告中标注被跳过的轮次及原因

## Phase 1: 现状感知

**目标：** 全面理解产品当前状态。不是机械扫描，而是LLM深入理解"产品现在是什么样"。

**分析方式：** 所有分析由LLM直接完成——读取代码、理解架构、评估体验，而不是依赖脚本机械统计。

### 1.1 读取产品铁律文档

在任何分析之前，先读取以下文档建立产品目标基准：

```
必读文档（按优先级）：
1. _bmad-output/planning-artifacts/prd.md          —— 产品要做什么
2. _bmad-output/planning-artifacts/architecture.md  —— 技术架构怎么支撑
3. _bmad-output/planning-artifacts/ux-design-specification.md —— 用户体验目标
4. _bmad-output/planning-artifacts/epics.md         —— 实现路线图
5. _bmad-output/planning-artifacts/testing-specification.md —— 质量标准
```

提取关键信息：

- 产品定位和核心价值主张
- 目标用户画像和使用场景
- MVP范围和当前迭代重点
- 已定义的功能需求列表（FR编号）
- UX设计原则和交互规范

### 1.2 深度分析代码实现现状

LLM直接读取和分析代码，不是用脚本跑统计数字，而是真正理解：

**阅读代码理解实现程度：**

- 读取各模块的核心文件，理解当前实现了什么
- 识别哪些FR需求已有代码实现、哪些还没有
- 评估代码架构是否与PRD/架构文档对齐
- 检查组件间数据流是否通畅

**用户体验评估：**

- 从用户视角遍历核心流程：入口→操作→反馈→结果
- 识别交互断点：哪里缺反馈、哪里步骤冗余、哪里不直观
- 对比UX设计规范检查差异
- 检查错误处理、空状态、加载状态是否完善

**增量分析（多轮迭代第2轮起）：**

- 聚焦上轮变更涉及的区域
- 分析变更是否引入新问题
- 评估上轮"下一轮建议"的执行情况
- 不需要重新分析全量代码

### 1.3 任务完成度检查

读取 `task.json` 了解当前进度：

- 统计总任务数和已完成数
- 识别各模块的完成率
- 找出阻塞中的任务和原因

## Phase 2: 差距识别

**目标：** 系统性识别产品现状与目标之间的差距，识别"哪些差距最影响产品价值"。

### 2.1 八维度差距评估

参考 `references/iteration-dimensions.md` 获取完整维度说明。以下为核心框架：

| 维度          | 评估内容                                 | 权重       |
| ------------- | ---------------------------------------- | ---------- |
| 🎯 需求对齐度 | 代码实现与PRD需求的对齐程度              | ⭐⭐⭐⭐⭐ |
| 🧭 产品方向性 | 功能是否符合产品核心价值和定位           | ⭐⭐⭐⭐⭐ |
| ✨ 用户体验度 | 交互是否流畅、反馈是否及时、流程是否高效 | ⭐⭐⭐⭐   |
| 🔧 技术健康度 | 代码质量、架构合理性、技术债务           | ⭐⭐⭐     |
| 🔗 集成完整度 | 前后端、各模块间、与云端的数据流通       | ⭐⭐⭐     |
| 🔒 安全合规度 | 数据安全、权限控制、隐私保护             | ⭐⭐⭐     |
| 📊 数据价值度 | 数据采集、分析能力、决策支持             | ⭐⭐       |
| 🚀 扩展准备度 | 架构是否支持下一阶段需求                 | ⭐⭐       |

**LLM评估方式：** 不是机械统计，而是LLM基于代码阅读和文档对比，给出专业判断。每个维度的评分应有具体的代码层面发现作为依据。

### 2.2 差距评分

对每个维度给出1-5分评价和具体发现：

```markdown
### 差距评估报告

#### 🎯 需求对齐度：X/5

**发现：**

- [具体差距1，附代码位置]
- [具体差距2，附代码位置]
  **影响：** [为什么这个差距重要]

#### ✨ 用户体验度：X/5

**发现：**

- [具体差距1，附代码位置]
- [具体差距2，附代码位置]
  **影响：** [为什么这个差距重要]

... （其他维度类似）
```

### 2.3 关键差距排序

不是所有差距都同等重要。基于以下原则排序：

1. **用户可感知 > 用户不可感知：** 影响用户体验的差距优先
2. **核心流程 > 边缘功能：** 影响核心业务流程的差距优先
3. **数据安全 > 功能增强：** 安全合规差距在高优先级
4. **阻塞其他差距的 > 独立的：** 被依赖的差距优先修复

输出排序后的 Top 5 关键差距列表，每个差距附带：

- 差距描述
- 影响范围
- 修复难度（S/M/L）
- 依赖关系
- 建议优先级

## Phase 3: 方向澄清

**目标：** 主动与用户交互，澄清迭代方向，确保"做正确的事"而不仅仅是"把事做对"。

### 3.1 首轮 vs 后续轮次

- **第1轮 / 单次迭代：** 完整询问用户方向
- **第2轮~第N轮：** 使用上轮"下一轮建议"作为方向，仅输出确认信息，不再重复询问

### 3.2 澄清问题模板（首轮使用）

根据差距分析结果，向用户提出以下类型的问题：

**方向类问题：**

- "当前迭代最想解决的用户痛点是什么？"
- "下一版本最想让用户感知到的变化是什么？"
- "有没有收到用户反馈需要优先处理的问题？"

**优先级类问题：**

- "我识别了这些关键差距：[列出]，您觉得哪个最应该优先解决？"
- "如果要选一个维度重点迭代，您选哪个？"
- "有没有某个功能是用户特别在意的？"

**取舍类问题：**

- "快速实现一个 MVP 功能 vs 精细打磨已有功能，当前更倾向哪个？"
- "如果要暂时牺牲一个维度来加强另一个，您会怎么取舍？"

**预期类问题：**

- "这次迭代期望达到什么效果？（如：用户完成某任务的时间减半）"
- "有没有什么量化指标想要提升？"

### 3.3 澄清原则

1. **每次最多问3-5个问题**，不要一次轰炸用户
2. **提供选择而非开放式问题**，给用户2-3个选项
3. **附带自己的建议**，说明"我倾向于X因为Y，您觉得呢？"
4. **尊重用户决定**，用户的选择是最终优先级
5. **记录所有澄清结果**，形成"迭代方向文档"

### 3.4 方向确认输出

```markdown
## 迭代方向确认

**迭代目标：** [一句话描述本次迭代要达成的目标]

**核心方向：** [1-3个关键词描述方向]

**优先级排序：**

1. [最高优先级差距/功能]
2. [次高优先级差距/功能]
3. [第三优先级差距/功能]

**预期效果：** [量化或可观测的成果]

**用户确认：** ✅ / 需要调整
```

## Phase 4: 迭代规划

**目标：** 将澄清后的方向转化为具体可执行的迭代计划，写入 `iteration.json`，然后据此生成 OpenSpec 变更。

| `version`                           | string       | iteration.json 格式版本                                          |
| `module`                            | string       | 迭代模块范围，"global" 表示全局                                  |
| `totalRounds`                       | number       | 计划总轮数                                                       |
| `currentRound`                      | number       | 当前轮次                                                         |
| `mode`                              | string       | 迭代模式："deep" 或 "quick"                                      |
| `scores.initial`                    | object       | 迭代前的8维度分数                                                |
| `scores.current`                    | object       | 当前最新的8维度分数                                              |
| `rounds`                            | array        | 每轮迭代的详细记录                                               |
| `rounds[].changes`                  | array        | 本轮的变更列表                                                   |
| `rounds[].changes[].openspecChange` | string\|null | 对应的OpenSpec变更目录名，null表示尚未生成                       |
| `rounds[].changes[].status`         | string       | "planning"/"openspec_ready"/"implementing"/"completed"/"blocked" |
| `techDebts`                         | array        | 累计的技术债务                                                   |
| `risks`                             | array        | 累计的风险预警                                                   |
| `nextSuggestions`                   | array        | 下一轮建议                                                       |

### 4.2 变更粒度控制

- 每个变更应该是**可独立验证**的最小单位
- 单个变更不超过**5个文件**的修改
- 单次迭代包含**3-7个变更**为宜
- 变更之间依赖关系明确，形成清晰的执行链

### 4.3 风险评估

每个变更标注风险等级：

- 🟢 low：局部修改，无依赖，易于回滚
- 🟡 medium：涉及多个模块，需要集成测试
- 🔴 high：涉及架构修改或数据迁移，需要仔细规划

### 4.4 生成 OpenSpec 变更

**核心原则：迭代计划写入 `iteration.json` 后，必须为每个变更生成 OpenSpec 变更，且 OpenSpec 变更足够完善后才能进入实施阶段。**

执行流程：

```
iteration.json 写入完成
     ↓
为每个变更生成 OpenSpec 变更
     ↓
检查 OpenSpec 变更是否完善
     ├─ 完善 → 更新 iteration.json 中 changes[].openspecChange 字段
     └─ 不完善 → 补充完善后才继续
     ↓
OpenSpec 变更全部就绪
     ↓
进入 Phase 5 执行
```

**为每个变更生成 OpenSpec 变更的步骤：**

1. 读取 `iteration.json` 中本轮的 `changes` 列表
2. 对每个 change，在 `openspec/changes/` 目录下创建对应的变更目录，命名规则：`iterate-{round}-{change序号}-{简短描述}`
   - 例如：`iterate-1-1-chat-loading-skeleton`
3. 每个变更目录包含：
   - `proposal.md` —— 变更提案（为什么做、做什么、预期效果）
   - `design.md` —— 技术设计（涉及文件、修改方案、数据流变化）
   - `tasks.md` —— 任务拆分（具体步骤清单）
   - `specs/spec.md` —— 详细规格（接口定义、类型定义、验收标准）
4. **完善性检查** —— 在进入 Phase 5 之前，逐项确认：
   - `proposal.md` 是否清晰描述了变更背景和目标
   - `design.md` 是否列出了所有涉及文件和修改方案
   - `tasks.md` 是否有可执行的步骤清单
   - `specs/spec.md` 是否有明确的验收标准
   - 如果任何一项不完善，**必须补充完善后再继续**
5. 全部 OpenSpec 变更完善后，更新 `iteration.json` 中对应 change 的 `openspecChange` 字段为变更目录名，`status` 更新为 `"openspec_ready"`

## Phase 5: 执行迭代

**目标：** 根据 `iteration.json` 中记录的、已经通过完善性检查的 OpenSpec 变更，执行代码实施。

### 5.1 执行前检查

```
1. 读取 iteration.json，确认所有变更的 status 为 "openspec_ready"
2. 确认当前 git 分支干净（无未提交修改）
3. 创建迭代分支：git checkout -b iterate/r{round}-{描述}
4. 备份关键文件（如需要）
5. 确认开发服务器可正常运行
```

**前置条件：所有变更必须已有完善的 OpenSpec 变更文档。如果没有，回到 Phase 4.4 补充完善。**

### 5.2 按 OpenSpec 变更执行实施

按照 `iteration.json` 中的变更顺序，逐个读取对应的 OpenSpec 变更文档执行：

1. 读取变更的 `proposal.md`、`design.md`、`tasks.md`、`specs/spec.md`
2. 按照设计文档和任务清单实施修改
3. 每个子任务完成后进行**局部验证**（lint + build）
4. 变更全部完成后更新 `iteration.json` 中 `changes[].status` 为 `"completed"`
5. 所有变更完成后进行**整轮验证**

### 5.3 执行原则

- **OpenSpec 先行：** 没有 OpenSpec 变更文档的变更不实施，必须先生成并完善
- **小步提交：** 每个变更完成后即可提交（可选），保持原子性
- **持续可运行：** 任何时刻代码都应处于可运行状态
- **遵循项目规范：** 严格遵守 AGENTS.md 中的铁律和编码规范
- **UX优先：** 用户体验相关的变更优先执行

### 5.4 实施过程中的状态管理

每个变更在 `iteration.json` 中的状态流转：

```
planning → openspec_ready → implementing → completed
                                    ↓
                                blocked（遇到阻塞）
```

- **planning：** 变更已规划，OpenSpec 变更尚未生成
- **openspec_ready：** OpenSpec 变更已生成且通过完善性检查
- **implementing：** 正在实施中
- **completed：** 实施完成且验证通过
- **blocked：** 遇到阻塞，需人工介入

## 快速模式 vs 深度模式

本 skill 支持两种运行模式：

### 快速模式（快速迭代）

触发条件：用户说"快速迭代"、"小改进"、"快速看看"等

- 跳过详细的差距评分（Phase 2 简化为Top 3差距）
- 跳过方向澄清（Phase 3 简化为1个问题）
- 直接从现状感知给出迭代建议
- 适合：小修小补、日常迭代、紧急修复

### 深度模式（完整迭代）

触发条件：用户说"深度迭代"、"完整分析"、"全面迭代"等，或未指定模式时默认

- 完整执行所有7个Phase
- 深度差距分析和方向澄清
- 详细的迭代计划和复盘报告
- 适合：版本迭代、功能增强、体验优化

### 模式选择逻辑

```
用户触发
  ├─ 明确指定模式 → 使用指定模式
  ├─ 提到"快速/小改进" → 快速模式
  ├─ 提到"深度/全面/完整" → 深度模式
  └─ 未指定 → 询问用户选择模式
      ├─ "建议深度模式，因为[原因]。选择：深度/快速？"
      └─ 根据用户选择执行
```

## 特殊场景处理

### 场景1：用户指定特定模块

当用户说"迭代XX模块"时：

- 聚焦该模块的差距分析
- 但仍评估该模块对整体产品的影响
- 建议：不要只看模块本身，要看模块与产品的连接点

### 场景2：用户只想看建议不想执行

当用户说"帮我看看有什么要改的"、"给我建议"时：

- 执行 Phase 1-3，输出差距分析和建议
- 不执行 Phase 4-6
- 保存分析结果供后续使用

### 场景3：连续多轮迭代

当用户说"继续迭代"时：

- 读取 `iteration-log.md` 获取上轮建议
- 从 Phase 1 开始新的循环
- 上轮的"下一轮建议"作为本轮的初始方向参考

### 场景4：N轮自动迭代

当用户说"帮我进行XX模块的N轮迭代"时：

- 按照本skill顶部"N轮自动迭代机制"执行
- 首轮完整分析+方向澄清，后续轮次自动推进
- 每轮输出精简报告
- N轮完成后输出总结报告

### 场景5：迭代中断

如果 Phase 5 执行过程中遇到阻塞：

- 按 AGENTS.md 规定的阻塞处理流程执行
- 不提交代码
- 记录阻塞原因到 progress.txt 和 iteration-log.md
- 输出明确的阻塞信息
- 多轮迭代时：跳过当前轮次，尝试下一轮（如果阻塞原因可能自行消除）

6. **差距变化追踪** —— 列表展示每个维度从初始到最终的分数路径

8. **下一轮建议** —— 推荐的迭代方向和理由

1. 读取模板文件
2. 将迭代数据填充到模板的占位符中
3. 写入目标路径

### 数据填充规范

| 占位符                   | 数据来源   | 格式                    |
| ------------------------ | ---------- | ----------------------- |
| `{{REPORT_DATE}}`        | 当前日期   | YYYY-MM-DD              |

| `{{SCORES_AFTER}}`       | 迭代后分数 | JSON数组，1-5           |
| `{{ROUNDS_DATA}}`        | 每轮数据   | JSON数组，见下方结构    |
| `{{CHANGES_TABLE}}`      | 变更详情   | HTML表格行              |
| `{{TECH_DEBTS}}`         | 技术债务   | HTML列表                |
| `{{RISKS}}`              | 风险预警   | HTML列表                |
| `{{NEXT_SUGGESTIONS}}`   | 下轮建议   | HTML列表                |
| `{{DIMENSION_TRACKING}}` | 维度追踪   | HTML                    |

**ROUNDS_DATA 结构：**

```json
[
  {
    "round": 1,

    "changes": ["变更1描述", "变更2描述"],
    "scores": [2, 3, 3, 2, 2, 2, 1, 2]
  }
]
```
